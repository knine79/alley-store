# ADR-0075: 출시 소식은 출시할 때마다 사람이 고르고, 스토어 봇이 앱의 채널에 올린다

- 상태: 수락됨
- 날짜: 2026-10-07

## 맥락

앱이 새로 나오거나 업데이트돼도 그 사실을 아는 사람이 없습니다. 스토어 앱을 열어봐야
알 수 있고, 받으러 오는 사람은 대개 이미 알고 오는 사람입니다 (이슈 #63).

알림 구조는 이미 있습니다. 앱 관리자가 받는 알림(피드백, 서명 실패)은 앱에 붙인 Slack
웹훅이나 개별 전송으로 가고 (ADR-0059), 사람에게 가는 DM 은 스토어의 봇 토큰으로
보냅니다. 출시 소식은 받는 사람이 다릅니다. 앱 관리자가 아니라 그 앱을 쓸 만한 사람들입니다.

출시는 네 길로 일어납니다. 웹 콘솔, API, CLI, MCP 입니다. CLI 와 MCP 는 API 를 부르므로
서버에서 출시하는 곳은 웹과 API 두 핸들러였고, 두 곳이 각자 상태를 바꾸고 있었습니다.
번들 ID 검사(ADR-0034)는 웹에만 있었습니다.

## 결정

**출시 소식 채널은 앱마다 앱 관리자가 등록하고, 알릴지는 출시할 때마다 출시하는 사람이
고릅니다. 글은 스토어의 Slack 봇이 채널 ID 로 올립니다.**

- 앱 상세에 "출시 소식 알림" 섹션을 둡니다. 앱 관리자가 채널 이름(또는 ID)을 적으면
  서버가 봇으로 채널을 찾고, **봇이 그 채널에 들어가 있을 때만** 받아 둡니다. 채널은
  알림 대상(`notification_targets`)과 다른 테이블(`release_channels`)에 둡니다
- 웹에서 출시를 누르면 팝업이 뜹니다. 채널이 있으면 "알리지 않고 출시" 와 "출시하고
  알리기" 중에 고르고, 채널이 없거나 봇이 연결되지 않았으면 그 사실과 무엇을 하면
  되는지를 보여주고 출시만 합니다. 취소가 맨 앞입니다
- API 는 본문의 `announce` 가 true 일 때만 알립니다. **비우면 알리지 않습니다.** MCP 의
  `release_version` 은 `announce` 인자를 받고, 알릴지를 사람에게 물어보라고 적었습니다
- 웹과 API 는 `VersionRelease.release` 하나를 부릅니다. 출시 소식과 번들 ID 검사가 모두
  여기서 일어납니다
- 한 버전은 한 번만 알립니다. 버전의 `announced_at` 을 비어 있을 때만 채우는 UPDATE 로
  먼저 차지한 요청만 보냅니다. 철회했다가 다시 출시해도 다시 알리지 않습니다. 단,
  **한 채널에도 보내지 못했으면** 차지한 것을 내려놓습니다. 고친 뒤 철회했다 다시
  출시하면 그때 보냅니다
- 알림이 실패해도 출시는 그대로 됩니다. 실패한 이유는 채널 목록에 남깁니다. Slack 이
  답하지 않을 때는 5초까지만 기다립니다
- 다른 버전이 출시돼 있거나 알린 적이 있으면 업데이트("✨... 로 업데이트되었습니다.")로,
  아니면 새 앱("🎉... 이 Alley Store에 출시되었습니다.")으로 씁니다
- 스토어 앱은 알리지 않습니다. 스스로 업데이트하고, 공유 링크도 상세가 아니라 설치
  페이지로 갑니다
- 스토어 전체 소식을 모아 공용 채널에 알리는 일은 여기서 하지 않습니다. 관리자에게 주기
  요약을 보내고 관리자가 전하는 방식으로 따로 다룹니다 (이슈 #65)

## 대안과 기각 사유

### 관리자가 정한 공용 채널 하나에 모든 출시를 알린다

**이슈가 풀려던 문제에 가장 바로 닿습니다.** 앱을 모르는 사람도 그 채널 하나만 보면
새 앱을 압니다. 앱 관리자가 할 일도 없습니다.

기각한 이유는 자주 올리는 앱이 채널을 덮고, 무엇을 알릴지를 관리자가 앱마다 정해야
하기 때문입니다. 앱을 가장 잘 아는 사람은 앱 관리자입니다. 스토어 전체 소식은 관리자가
요약을 받아 사람의 손으로 전하는 쪽(이슈 #65)이 소음이 적다고 봤습니다.

### 웹훅으로 보낸다 (지금 알림 채널과 같은 방식)

**봇 토큰이 없는 스토어에서도 됩니다.** 이미 있는 대상 등록 화면과 발송 코드를 그대로
쓸 수 있습니다.

기각한 이유는 보낸 사람이 웹훅을 만든 Slack 앱으로 보이기 때문입니다. 앱 관리자는
스토어 봇 앱에 웹훅을 만들 권한이 없어서 저마다 다른 앱으로 만들게 되고, 출시 소식이
제각각의 이름으로 올라갑니다. 웹훅 주소는 채널에 글을 쓸 수 있는 자격증명이라, 앱마다
받아 두면 그만큼 흩어집니다. 봇이면 채널에 초대하기만 하면 됩니다.

### 업로드할 때 알릴지 정해 둔다

**출시하는 순간에 묻지 않아도 됩니다.** 올리는 사람이 릴리즈 노트를 쓰면서 함께 정합니다.

기각한 이유는 알림이 나가는 때가 출시라서입니다. 서명과 공증을 거치는 사이에 마음이
바뀔 수 있고, CI 가 배포 토큰으로 올리면 고를 화면이 없습니다.

### 웹과 API 에 각각 알림을 붙인다

**고칠 곳이 작습니다.** 출시 핸들러 두 곳에 한 줄씩이면 됩니다.

기각한 이유는 한 곳에서 빠지기 때문입니다. 실제로 번들 ID 검사가 웹에만 있었고, API 로
출시하면 그 검사를 건너뛰었습니다.

## 결과

**좋은 점**

- 출시 소식이 언제나 스토어 이름으로 올라가고, 채널에 글을 쓰는 자격증명이 늘지 않습니다
- 알릴지를 출시하는 사람이 매번 고르므로 시험 출시나 잦은 업데이트가 채널을 덮지 않습니다
- 출시가 한 곳을 지나게 되어 API 로 출시해도 번들 ID 검사가 걸립니다

**나쁜 점**

- 봇 토큰이 없는 스토어에서는 쓸 수 없습니다. 화면은 관리자에게 연결을 요청하라고만 합니다
- 봇에 `channels:read`, `groups:read` 권한을 더 줘야 합니다. 운영 중인 봇 앱에 권한을
  추가하고 다시 설치해야 합니다
- API 의 기본값이 "알리지 않음" 이라 CI 로 출시하는 앱은 `announce` 를 넣지 않는 한
  알려지지 않습니다
- 앱 관리자가 채널을 등록하지 않으면 그 앱의 출시는 아무 데도 알려지지 않습니다. 이슈가
  지적한 "아는 사람만 온다" 는 공용 채널 없이는 남습니다 (이슈 #65 로 보완)
- 봇이 나중에 채널에서 빠지면 출시할 때에야 실패합니다. 다른 채널에는 갔다면 빠진
  채널에 다시 보낼 길이 없고, 채널 목록에 마지막 실패 이유가 남을 뿐입니다
- 채널 수만큼 Slack 을 차례로 부르는 동안 출시 응답이 늦어집니다. 채널이 많고 Slack 이
  느리면 채널마다 5초까지 늘어납니다
- 알림 대상과 출시 소식 채널이 서로 다른 테이블과 화면에 있어, 알림을 고치는 사람이 두
  곳을 봐야 합니다
