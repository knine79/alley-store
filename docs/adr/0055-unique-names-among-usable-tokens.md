# ADR-0055: 쓸 수 있는 토큰끼리는 이름이 겹치지 않게 한다

- 상태: 수락됨
- 날짜: 2026-09-16

## 맥락

"폐기한 운영 토큰이 목록에 다시 나타난다" 는 말이 나왔습니다. 확인해 보니 다시
나타난 것이 아니라 **이름이 같은 다른 토큰**이었습니다. `ops-local` 이라는 이름의
운영 토큰이 세 개 있었고, 그중 하나는 폐기된 것이었습니다.

화면이 보여주던 것은 이름과 마지막 사용 시각뿐입니다. 쓴 적 없는 토큰끼리는 이름도
같고 마지막 사용도 "쓴 적 없음" 이라 **두 줄이 글자 하나까지 같습니다.** 목록은 발급
순서로 정렬하는데 그 기준이 화면에 없어서, 왜 이 순서인지도 알 수 없었습니다.

이름이 겹친 경위에는 발급 화면의 성질도 있습니다. 토큰 발급은 리다이렉트하지 않습니다.
토큰 원문이 그 응답에만 있고 서버는 해시만 들고 있어서 다음 화면에서 다시 보여줄
방법이 없기 때문입니다([ADR-0013](0013-worker-token-authentication.md)). 그래서
브라우저에는 POST 한 자리가 그대로 남고, **새로고침하면 같은 폼이 다시 제출됩니다.**
그렇게 생긴 토큰은 이름도 값도 발급한 사람도 같아 보입니다.

이름은 사람이 토큰을 가리키는 유일한 손잡이입니다. 그것이 겹치면 "CI 시크릿에 든 것이
이 줄인가 저 줄인가" 를 화면에서 답할 수 없고, 폐기 버튼을 누를 때 무엇을 끊는지
모르게 됩니다.

## 결정

**쓸 수 있는 토큰끼리는 이름이 겹치지 않게 합니다.** 네 종류 모두에 같은 규칙을
둡니다.

| 토큰 | 이름이 유일해야 하는 범위 |
| --- | --- |
| 워커(ADR-0013) | 서버 전체 |
| 운영 토큰(ADR-0043) | 서버 전체 |
| 배포 토큰(ADR-0015) | 앱 하나 안 |
| 피드 토큰(ADR-0017) | 앱 하나 안 |

- **폐기한 이름은 다시 쓸 수 있습니다.** 맥을 교체하고 같은 이름을 붙이는 것은 오히려
  흔한 일입니다. 막으면 이름이 `build-mac-01-2` 로 자랍니다
- 배포·피드 토큰을 앱 안에서만 보는 이유는 파이프라인 이름이 앱마다 같기 때문입니다.
  `github-actions` 가 앱마다 하나씩 있는 것이 정상입니다
- 목록에 **발급 시각**(워커는 등록 시각)을 함께 보여줍니다. 규칙이 생겨도 폐기한
  줄과 지금 줄은 여전히 이름이 같을 수 있고, 그때 남는 단서가 이것입니다
- 발급 화면은 그려진 뒤 주소를 목록 주소로 바꿉니다(`no-resubmit.js`). 새로고침이
  POST 가 아니라 GET 이 되게 하는 것뿐이고, **없어도 위 규칙이 토큰을 막습니다**

## 대안과 기각 사유

**일회용 폼 키(nonce)를 발급 응답에 심는다** — 재제출을 정면으로 막는 방법입니다.
이름 규칙과 달리 "무엇을 만드는가" 와 무관하게 통하고, 발급 말고 다른 폼에도 그대로
씁니다.

기각한 이유는 **이 서버에 폼 키를 둘 자리가 없기 때문입니다.** 세션은 JWT 쿠키
하나뿐이고 서버는 세션 상태를 들고 있지 않습니다([ADR-0008](0008-session-token-design.md)).
폼 키를 넣으려면 프로세스 메모리에 두거나(재시작하면 열려 있던 화면의 폼이 전부
깨집니다) 테이블과 마이그레이션을 새로 만들어야 합니다. 새로고침 한 번을 막자고
저장소를 만드는 것은 값이 맞지 않고, 이름 규칙이 같은 결과를 냅니다.

**이름에 유니크 인덱스를 건다** — 데이터베이스가 보장하니 경쟁 조건이 없습니다.

기각한 이유는 **폐기한 행이 남기 때문입니다.** 토큰은 지우지 않고 폐기 시각만 찍습니다.
잡 이력과 업로드 이력이 그 행을 가리키기 때문입니다(ADR-0013). 그냥 유니크 인덱스를
걸면 폐기한 이름을 영영 못 쓰게 됩니다. `WHERE revoked_at IS NULL` 부분 인덱스면
되지만 Fluent 마이그레이션에서 raw SQL 을 써야 하고, 이 화면은 관리자 몇 사람이
가끔 누르는 곳이라 경쟁이 실제로 문제 되는 규모가 아닙니다.

**목록에 토큰 id 앞자리를 보여준다** — 이름이 겹쳐도 사람이 가릴 수 있습니다.

기각한 이유는 **문제를 사람에게 떠넘기는 것이기 때문입니다.** UUID 앞 여덟 자를
읽고 CI 시크릿의 것과 대조하는 일은 아무도 하지 않습니다. 시각은 읽힙니다.

**목록만 고치고 이름 규칙은 두지 않는다** — 발급 시각만 보여줘도 두 줄은 갈립니다.
발급하는 쪽에 제약이 없어 쓰던 대로 씁니다.

기각한 이유는 **구별이 되는 것과 헷갈리지 않는 것이 다르기 때문입니다.** 시각이
보여도 `ops-local` 이 셋 있는 상태는 그대로이고, 그중 무엇이 파이프라인에 들어 있는지는
여전히 서버가 답해주지 못합니다. 이름이 하나면 물을 필요가 없습니다.

## 결과

**좋은 점**

- 쓸 수 있는 토큰의 이름이 그 토큰을 가리킵니다. "어느 쪽을 폐기해야 하나" 가
  화면에서 끝납니다
- 발급 화면을 새로고침해도 토큰이 늘지 않습니다. 스크립트가 꺼져 있어도 그렇습니다
- 폐기한 줄과 지금 줄이 이름이 같아도 발급 시각으로 갈립니다. 목록 정렬 기준도
  화면에 드러납니다

**나쁜 점**

- **JSON 관리 API 가 409 를 새로 냅니다.** `POST /api/v1/admin/workers` 로 같은
  이름의 워커를 거듭 등록하던 자동화가 있으면 그 시점부터 실패합니다. 화면과 API 가
  같은 규칙을 공유하므로 한쪽만 예외로 둘 수 없습니다
- **검사와 저장 사이에 틈이 있습니다.** 데이터베이스 제약이 아니라 저장 전에 한 번
  읽어보는 것이라, 같은 이름을 동시에 두 번 보내면 둘 다 통과할 수 있습니다. 이
  화면에서 그런 동시성은 사실상 생기지 않지만, 보장은 아닙니다
- **폐기한 직후의 재제출은 여전히 통합니다.** 발급 → 폐기 → 새로고침 순서면 이름이
  비어 있어서 새 토큰이 생깁니다. 스크립트가 도는 브라우저에서는 주소가 이미 바뀌어
  있어 일어나지 않습니다
- 같은 이름을 다시 쓰려면 먼저 폐기해야 합니다. 새 토큰을 만들어 옮겨 붙인 뒤 옛것을
  폐기하는 순서로 회전하던 사람은 이름을 잠깐 다르게 잡아야 합니다
- 워커 표가 일곱 칸이 됐습니다. 폭이 좁은 화면에서 먼저 눌립니다
