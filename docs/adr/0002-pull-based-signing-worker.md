# ADR-0002: 서명을 별도 macOS 워커에 pull 방식으로 분리한다

- 상태: 수락됨
- 날짜: 2026-08-12

## 맥락

Developer ID로 앱을 배포하려면 `codesign`과 `notarytool`을 돌려야 하고, 둘 다
macOS에서만 동작합니다. 서명에는 Developer ID Application 인증서의 **개인키**가
필요합니다.

서버는 Linux 컨테이너로 돌리려 합니다. 그러면 서명을 어디서 하느냐, 그리고 개인키를
어디에 두느냐를 정해야 합니다.

## 결정

서명 전용 macOS 머신에 워커 데몬을 두고, 워커가 서버의 잡 큐를 **폴링**합니다
(long-poll). 개인키는 그 머신의 키체인에만 존재하고 서버로 올라가지 않습니다.

통신은 워커 → 서버 방향으로만 일어납니다. 서명 키를 보관한 머신에 인바운드 포트를
열 필요가 없습니다.

공증 자격증명도 환경변수가 아니라 `notarytool store-credentials`로 저장한 키체인
프로필을 씁니다. 자격증명이 프로세스 환경에 노출되지 않습니다.

`SigningJob` DTO에는 서명 identity도 공증 자격증명도 담기지 않습니다. 개인키가
서버를 거치지 않는다는 원칙을 타입 수준에서 지킵니다.

## 대안과 기각 사유

**서버가 개인키를 보관하고 서명까지 대행** — UX는 가장 단순합니다. 그러나 개인키가
서버에 올라가고, 서명하려면 어차피 macOS 러너가 필요해서 인프라가 오히려 복잡해집니다.
키가 유출되면 조직 전체 앱의 신뢰가 무너지므로 감수할 위험이 아닙니다.

**서명 머신에 서버 전체를 올린다** — 바이너리 왕복 전송이 없어집니다. 그러나 서비스
가용성이 빌드 머신에 묶이고, macOS에서의 서버 운영(재부팅, 업데이트, launchd 관리)
부담이 커지며, "호스팅하려면 Mac이 필요하다"는 셀프호스팅 진입장벽이 생깁니다.

**워커에 인바운드 포트를 열고 서버가 푸시** — 큐 구현이 단순해집니다. 그러나 서명
키를 가진 머신에 외부 접근점을 만드는 것이라 pull 방식 대비 이득이 없습니다.

## 결과

**좋은 점**
- 개인키가 한 머신을 벗어나지 않습니다
- 서명 머신에 인바운드 포트가 필요 없습니다
- 서버는 평범한 Linux 컨테이너로 남아 셀프호스팅이 쉽습니다
- 워커를 여러 대 등록할 수 있고, 큐가 서버에 있으므로 워커가 죽어도 복구 시
  이어서 처리합니다

**나쁜 점**
- 바이너리가 서버 ↔ 워커를 왕복합니다. 다만 공증 대기(수 분)에 비하면 무시할 수준입니다
- 워커 머신이 단일 장애점입니다. 하트비트로 감지하고 알림을 보냅니다 (Phase 3)
- 워커 설치·운영이라는 절차가 하나 늘어납니다. `alley-worker preflight`로 설치 직후
  환경 문제를 걸러내 완화합니다

**후속**
- restricted entitlement를 쓰는 앱은 `embedded.provisionprofile`이 서명 이전에 번들에
  있어야 합니다. 워커가 서명하는 구조이므로 개발자가 업로드하는 번들에 이미 포함돼
  있어야 하고, 워커는 서명 전에 이를 검사해 실패시킵니다
