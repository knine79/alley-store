# ADR-0029: 번들 ID 는 서명 전에 워커가 대조한다

- 상태: 수락됨
- 날짜: 2026-09-08

## 맥락

앱을 등록할 때 관리자가 번들 ID 를 타이핑합니다. 그 값은 프리픽스 검사를 거칩니다
(`AppRegistration`, `BundleIdentifier.validate`). 하지만 **올라온 번들이 정말 그
번들인지는 아무도 확인하지 않았습니다.** 프리픽스 검사는 등록 화면에서 입력한
문자열만 봅니다. 그 뒤에 올라오는 zip 은 검사 대상이 아니었습니다.

그래서 다음이 가능했습니다.

1. `com.example.tool` 로 앱을 등록한다
2. 아무 관계 없는 `.app` 을 zip 으로 올린다
3. 워커가 그것을 조직의 Developer ID 로 서명하고, Apple 에 공증까지 받는다

피해가 두 갈래입니다.

**되돌릴 수 없는 쪽.** 공증 티켓은 회수할 수 없습니다. Apple 에 인증서 폐기를
요청하면 그 인증서로 서명한 **모든** 앱이 함께 죽습니다. 그 사이 누가 받아갔는지도
알 수 없습니다. 조직 이름이 붙은 서명은 "이 조직이 이 앱을 배포한다"는 진술인데,
그 진술을 아무 검증 없이 발행하고 있었습니다.

**조용히 고장나는 쪽.** 스토어 앱은 설치된 앱을 `CFBundleIdentifier` 로 찾습니다
(`InstalledApps`). 등록된 ID 와 실제 번들의 ID 가 어긋나면 업데이트가 영영 감지되지
않습니다. 스토어 목록에는 보이는데 사용자 머신에서는 계속 "설치 안 됨" 입니다.
이쪽은 서명이 정상으로 끝나기 때문에 실패로도 보이지 않습니다.

업로더가 악의를 가질 필요는 없습니다. 앱을 두 개 만드는 사람이 zip 을 잘못 고르는
것으로 충분하고, 빌드 설정의 번들 ID 를 바꾼 것을 잊는 것으로도 충분합니다.

## 결정

**워커가 `validating` 단계에서, 서명 대상을 고르기 전에** 대조합니다.

지시서(`SigningJobDTO`)에 이미 `appBundleID` 가 들어 있습니다. 서버가 DB 의
`version.app.bundleID` 를 채워 보냅니다. 워커는 zip 을 푼 뒤 최상위 `.app` 의
`Contents/Info.plist` 에서 `CFBundleIdentifier` 를 읽어 그것과 비교합니다.

- 다르면 `bundle_identifier_mismatch` 로 실패시킵니다. 재시도하지 않습니다
- `CFBundleIdentifier` 가 **없으면** 역시 실패시킵니다
- 문자열 완전 일치로 봅니다. 대소문자를 구분하고, 프리픽스만 같은 것은 통과시키지
  않습니다

번들 ID 가 없을 때 실패시키는 것은 따로 고민한 자리입니다. 관대하게 넘기면 서명은
되지만 스토어 앱이 그 앱을 영영 찾지 못합니다. 배포된 뒤에 드러나는 고장을 만드는
쪽보다, 올리는 자리에서 막는 쪽을 골랐습니다.

`mainExecutableName` 은 `Info.plist` 를 못 읽으면 번들 이름으로 넘어갑니다. 이쪽은
그러지 않습니다. 실행 파일 이름을 잘못 짚으면 같은 파일을 한 번 더 서명할 뿐이지만,
번들 ID 를 잘못 짚으면 검사 자체가 무의미해집니다.

## 대안과 기각 사유

**서버가 업로드를 받을 때 검사한다** — 가장 이른 시점에 막습니다. 업로더는 잡이
큐에 들어가기 전에 답을 받고, 워커가 없어도 검사가 됩니다. 이것이 가장 그럴듯한
대안이었습니다.

기각한 이유는 서버가 그러려면 zip 을 풀어야 한다는 것입니다. 지금 서버는 아티팩트를
**한 번도 열지 않습니다.** 브라우저와 CLI 는 presigned URL 로 오브젝트 스토리지에
직접 올리고, 서버는 키와 해시만 기록합니다. 검사를 위해 서버가 zip 을 내려받아
풀기 시작하면 (1) 신뢰할 수 없는 압축 파일을 서버 프로세스 안에서 다루게 되고
(zip bomb, 경로 탈출), (2) 컨테이너에 앱 하나 크기의 디스크와 그만큼의 전송이
필요해지고, (3) 업로드 응답이 파일 크기에 비례해 느려집니다. 워커는 이미 그 일을
하는 곳입니다. 신뢰할 수 없는 번들을 푸는 것이 원래 자기 일이고, 격리된 작업
디렉터리와 디스크가 이미 있습니다.

**CLI 가 올리기 전에 검사한다** — 사용자가 가장 빨리 알게 되고, 잘못된 업로드가
네트워크를 타지도 않습니다. 다만 이것은 **신뢰 경계 밖**입니다. CLI 는 업로더의
머신에서 돌고 고쳐 쓸 수 있습니다. 편의로는 좋아서 나중에 넣을 만하지만, 이것만
두면 검사가 없는 것과 같습니다. 서명을 실제로 하는 쪽에 검사가 있어야 합니다.

**프리픽스만 맞으면 통과시킨다** — `com.example.*` 안이면 우리 조직 앱이라는
논리입니다. 그러나 막으려는 것이 "조직 밖 앱" 이 아니라 "이 앱 자리에 다른 앱"
입니다. 같은 조직의 다른 앱을 올리는 사고가 가장 흔하고, 프리픽스 검사는 그것을
전부 통과시킵니다. 스토어 앱의 업데이트 감지가 깨지는 문제도 그대로 남습니다.

**경고만 남기고 서명한다** — 기존 배포를 깨지 않습니다. 그러나 서명은 되돌릴 수
없는 발행 행위입니다. 되돌릴 수 없는 일 앞에서 경고를 남기는 것은 아무것도 하지
않는 것과 같습니다 (ADR-0027 에서 같은 판단을 했습니다).

## 결과

**좋은 점**

- 조직의 Developer ID 로 서명되는 것이 등록된 그 앱임을 기계가 보장합니다. 사람의
  주의력에 기대지 않습니다
- 서명 **전에** 멈추므로 실패한 잡이 밖으로 남기는 흔적이 없습니다. 공증에 올라가지
  않고, 티켓도 발행되지 않습니다
- 스토어 앱의 업데이트 감지가 깨진 채 배포되는 경로가 막힙니다
- 실패 코드가 따로 있어서 화면이 "무엇을 하면 되는지" 를 말할 수 있습니다
  (`SigningFailureGuidance`)

**나쁜 점**

- **번들 ID 가 바뀌면 앱을 새로 등록해야 합니다.** 지금은 등록된 번들 ID 를 고칠
  방법이 없습니다. 리브랜딩으로 번들 ID 를 바꾼 팀은 앱을 새로 등록하고 버전
  이력을 잃습니다. 번들 ID 수정 기능이 필요해지는 날이 오면 그때 만듭니다
- **`CFBundleIdentifier` 없는 번들은 이제 서명되지 않습니다.** 그런 번들이 예전에
  통과한 적이 있다면 이 버전에서 막힙니다. macOS 가 앱으로 다루지 않는 번들이라
  막는 쪽이 맞다고 봤지만, 되짚어보면 기존 동작을 깨는 변경입니다
- 검사가 워커에 있어서 **워커가 없으면 검사도 없습니다.** 잘못된 zip 은 잡이 잡힐
  때까지 큐에 남아 있고, 업로더는 그동안 자기 실수를 모릅니다. 서버나 CLI 쪽 사전
  검사를 나중에 더하면 이 대가가 줄어듭니다. 그때도 워커 검사는 남깁니다
- 검사가 최상위 `.app` **하나만** 봅니다. 번들 안의 헬퍼 앱이 밝히는 번들 ID 는
  보지 않습니다. 헬퍼가 엉뚱한 ID 를 밝히고 있어도 통과합니다
