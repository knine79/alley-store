# ADR-0006: 앱 업데이트를 스토어 앱과 Sparkle 두 경로로 지원한다

- 상태: 수락됨
- 날짜: 2026-08-13

## 맥락

초기 설계에는 "설치된 앱의 버전을 추적해 업데이트를 표시한다" 한 줄만 있었고,
어떻게 하는지가 비어 있었습니다. 실제로 구현하려면 답해야 할 것들이 남아 있었습니다.

- 설치된 앱을 어떻게 찾는가
- 실행 중인 앱을 어떻게 교체하는가
- 스토어 앱이 실행 중인 자기 자신을 어떻게 갈아끼우는가

세 번째는 별도 헬퍼 프로세스가 필요한 까다로운 작업입니다.

## 결정

두 경로를 모두 지원합니다.

**경로 A (기본): 스토어 앱이 관리**

1. `/Applications`와 `~/Applications`를 스캔해 각 번들의 `CFBundleIdentifier`와
   `CFBundleVersion`을 읽고 스토어 등록 앱과 대조합니다. 다른 위치에 설치된 앱은
   `NSWorkspace.urlForApplication(withBundleIdentifier:)`로 보완 조회합니다
2. 새 버전의 서명·Team ID·해시를 검증합니다 (ADR-0007)
3. 대상 앱이 실행 중이면 동의를 받고 `NSRunningApplication.terminate()`로 정상 종료를
   요청합니다. **응답이 없으면 강제 종료하지 않고 업데이트를 미룹니다**
4. 기존 번들을 휴지통으로 옮기고 새 번들을 같은 위치에 놓습니다. 실패하면 되돌립니다
5. 업데이트 전에 실행 중이었다면 다시 실행합니다

**경로 B: Sparkle appcast**

서버가 앱별로 `GET /api/v1/apps/:id/appcast.xml`을 서빙합니다. 앱에 Sparkle을
통합하고 이 URL을 `SUFeedURL`로 지정하면 스토어 앱 없이 자체 업데이트가 됩니다.
appcast에는 released 상태인 버전만 나갑니다.

**스토어 앱 자신의 업데이트는 Sparkle을 씁니다.** 실행 중인 자기 자신을 교체하는
문제를 직접 푸는 것은 이미 풀린 문제를 다시 푸는 것입니다.

## 대안과 기각 사유

**스토어 앱만으로** — 중앙 관리가 명확하고 다운로드 이력이 사용자 단위로 남습니다.
그러나 스토어 앱이 떠 있을 때만 업데이트가 되고, 스토어 앱 자신의 자기 교체 문제를
직접 풀어야 합니다.

**Sparkle만으로** — 구현이 가장 가볍고 macOS 생태계 표준을 따릅니다. 그러나 모든
앱에 SDK를 통합해야 하고, 통합하지 않은 앱은 영영 업데이트되지 않습니다. 앱
개발자에게 부담을 전가하는 구조입니다.

**응답 없는 앱을 강제 종료** — 업데이트 성공률이 올라갑니다. 그러나 사용자의 저장하지
않은 작업을 날립니다. 업데이트가 늦는 편이 낫습니다.

## 결과

**좋은 점**
- 앱 개발자가 상황에 맞게 고를 수 있습니다
- 이미 Sparkle을 쓰던 앱은 `SUFeedURL`만 바꿔서 그대로 흡수됩니다
- appcast는 XML 엔드포인트 하나라 두 경로를 여는 비용이 거의 없습니다
- 스토어 앱의 자기 교체를 직접 구현하지 않습니다

**나쁜 점**
- 경로 B는 인증이 약합니다. Sparkle이 세션 토큰을 들고 있지 않아 앱별 피드 토큰으로
  인증하는데, **사용자 단위 다운로드 이력이 남지 않습니다**. 이력이 중요한 앱은
  경로 A를 써야 합니다
- 업데이트 경로가 둘이라 문제가 생겼을 때 어느 쪽인지 먼저 가려야 합니다
- 사용자가 앱을 옮겨두면 경로 A의 탐지가 실패할 수 있습니다. 설치 시 중복이 감지되면
  알리는 것으로 완화합니다

**미결**
- 조직 내부 배포 특성상 누가 받았는지 추적이 중요하다면 경로 B를 아예 막는 선택지도
  있습니다. Phase 4 착수 전에 정합니다
