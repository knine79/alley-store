# ADR-0023: 서명 실패에 오류 코드를 붙인다

- 상태: 수락됨
- 날짜: 2026-09-02

## 맥락

서명 잡이 실패했을 때 워커가 서버에 넘기는 것은 자유 문자열뿐이었습니다.

```swift
let reason = String(describing: error)
try? await client.report(
    SigningJobUpdate(state: .failed, log: reason, failureReason: summarize(reason)), for: job.id)
```

`summarize` 는 첫 줄을 300자로 자르는 함수입니다. 분류가 아닙니다. 여기서 두 가지가
따라옵니다.

**서버가 재시도 여부를 판단할 근거가 없습니다.** 인증서가 만료된 잡과 Apple 이 잠깐
답하지 않은 잡이 서버에게는 똑같이 "실패 문자열 하나"입니다. 앞은 몇 번을 다시 해도
같은 결과라 곧장 사람에게 넘겨야 하고, 뒤는 다시 하면 되는 일이라 사람을 부를 것이
없습니다. 지금은 둘 다 같은 길로 갑니다.

**실패 직전의 맥락이 사라집니다.** `WorkerController` 에 `if let log = update.log { job.log = log }`
가 있습니다. 열 하나에 **덮어씁니다.** 단계가 바뀔 때마다 이전 것이 지워지고, 실패하면
실패 메시지 하나만 남습니다. 원인 파악에 가장 필요한 것은 그 직전 단계가 무엇을
하다가 죽었는가인데, 그것이 없습니다.

워커 쪽에는 이미 재료가 있습니다. `SigningPipeline.PipelineError`,
`Entitlements.ValidationError`, `AppBundle.BundleError` 가 case 로 나뉘어 있습니다.
그것을 서버까지 실어 보내지 않고 문자열로 뭉갠 것이 문제입니다.

## 결정

실패의 갈래를 `SigningFailureCode` 로 만들어 서버·워커·콘솔이 함께 씁니다.
`AlleyShared` 에 둡니다.

### 갈래와 재시도

**재시도 여부의 판단을 코드 자신이 갖습니다** (`isRetriable`). 서버가 문자열을 다시
해석하는 자리는 만들지 않습니다.

| 갈래 | 다시 해볼 만한가 |
| --- | --- |
| `signing_identity_unavailable` (identity 없음·만료) | 아니오 |
| `codesign_failed` (identity 문제가 아닌 서명 실패) | 아니오 |
| `entitlements_rejected` (누락·프로필 필요·형식) | 아니오 |
| `bundle_layout_invalid` (`.app` 이 없거나 여러 개) | 아니오 |
| `unsigned_code_remains` (지나친 미서명 코드) | 아니오 |
| `notarization_rejected` (Apple 이 내용을 보고 거절) | 아니오 |
| `unknown` (분류하지 못함) | 아니오 |
| `transfer_failed` (네트워크·스토리지) | 예 |
| `apple_service_unavailable` (공증 제출·티켓 첨부) | 예 |
| `timed_out` (제한 시간 초과) | 예 |

갈래는 워커가 오류 타입에서 뽑습니다(`SigningFailureCode.classify`). `PipelineError`
는 던지는 자리에서 갈래를 함께 담습니다. 나중에 `step` 문자열을 보고 되짚지 않으려는
것입니다. 그 문자열은 화면에 보이는 말이라 언제든 다듬게 되는데, 분류가 거기 매달려
있으면 말을 고치는 순간 조용히 틀립니다.

문자열을 보는 자리는 두 곳뿐이고, 둘 다 다른 방법이 없어서 그렇게 합니다.

- `SigningPipeline.codesignCode` — `codesign` 은 인증서가 없는 것과 번들이 깨진 것에
  같은 종료 코드 1 을 씁니다. 무엇이 문제였는지는 사람에게 하는 말에만 있습니다
- `SigningPipeline.isRejection` — `notarytool` 이 JSON 으로 주는 `status` 가
  `"Invalid"` 인지 봅니다. 제출조차 못 했으면 그 필드가 없고, 그건 앱 내용과 무관한
  실패라 다시 해볼 만합니다

### `unknown` 은 재시도하지 않습니다

어느 쪽으로 두든 대가가 있어 오래 고민한 자리입니다. 재시도 쪽에 두면 영영 안 될 일을
세 번 하고, 포기 쪽에 두면 일시적 문제에 사람이 개입해야 합니다. 포기 쪽으로 정했고
근거는 셋입니다.

첫째, 잘못된 재시도에는 **우리 밖으로 나가는 부수효과**가 있습니다. 같은 버전이 공증에
두 번 올라갑니다. ADR-0018 이 멈춤 판정을 15분으로 길게 잡은 것도 같은 이유였습니다.
이 레포는 이미 "의심스러우면 다시 내보내지 않는다" 쪽으로 정해둔 곳이고, 여기서만
반대로 가면 두 판단이 어긋납니다.

둘째, 분류하지 못했다는 것은 **우리가 그 실패를 아직 모른다**는 뜻입니다. 조용히 세 번
돌려버리면 그 사실이 아무 데도 드러나지 않습니다. 실패로 확정하면 사람이 로그를 보고
갈래를 하나 더 만듭니다. 재시도를 기본값으로 두면 분류가 낡아가는 것을 아무도 모릅니다.

셋째, 워커가 서버보다 새로워 서버가 모르는 코드를 받는 경우에도 `unknown` 이 됩니다.
그때 재시도하지 않는 쪽이 **코드가 없던 시절과 같은 동작**입니다. 버전이 어긋났을 때
없던 동작이 튀어나오는 것보다 낫습니다.

대가는 분명합니다. 갈래로 만들지 못한 일시적 실패는 사람이 다시 올려야 합니다. 그
대가를 줄이는 방법은 기본값을 뒤집는 것이 아니라 갈래를 늘리는 것입니다.

### 갈래가 없는 것과 분류하지 못한 것은 다릅니다

섞으면 안 되는 두 사건입니다.

- **워커가 실패를 보고했다.** 갈래가 함께 옵니다. 위 표대로 판단합니다
- **워커에게서 소식이 끊겼다** (`StalledJobSweep`, ADR-0018). 워커가 죽었으니 아무것도
  보고하지 못했습니다. **갈래가 아예 없습니다(nil).** 워커 한 대가 재부팅된 것일 수
  있으니 예전처럼 시도 상한(3회)까지 큐로 되돌립니다

`nil` 은 보고 자체가 없었다는 뜻이고 `unknown` 은 보고했지만 우리가 분류하지 못했다는
뜻입니다. 판단은 `SigningRetryPolicy` 한 곳에 있고, 두 자리가 시도 횟수(`attempt`)를
함께 씁니다. 나눠 쓰면 "일시 실패 보고 → 재시도 → 워커 죽음 → 재시도"를 오가는 잡이
어느 상한에도 걸리지 않습니다.

여기서 동작이 하나 바뀝니다. 지금까지 워커가 보고한 실패는 **무조건** 잡과 버전을
`failed` 로 확정했습니다. 이제 다시 해볼 만한 갈래는 잡을 큐로 되돌리고 버전은
건드리지 않습니다. 되돌릴 때 `worker_id`·`claimed_at`·`heartbeat_at` 을 지우는 것은
멈춘 잡 회수와 같습니다.

### 로그는 쌓습니다

`job.log` 를 덮어쓰지 않고 단계마다 붙입니다. 줄머리에 서버 시각과 단계 이름을 답니다.

**표를 새로 만들지 않았습니다.** 잡 하나가 만드는 것은 단계 여섯 개에 실패 메시지
하나입니다. 일곱 줄을 위해 표와 조인과 마이그레이션을 늘릴 이유가 없습니다. 화면도
이미 `<pre>` 하나에 그대로 펴는 자리입니다.

상한은 **16KB** 이고, 넘으면 **앞을 버립니다.** 실패 원인은 거의 언제나 끝에 있습니다.
잘랐다는 사실은 첫 줄에 남깁니다. 그것이 없으면 앞부분이 원래 없었는지 잘렸는지 읽는
사람이 알 수 없습니다. 16KB 는 `codesign` 출력과 공증 로그 전문이 다 들어가면서 앱
상세 화면이 로그 하나로 뒤덮이지는 않는 크기입니다.

### 사람이 읽는 쪽

`SigningFailureGuidance` 가 갈래마다 한 줄 이름과 "무엇을 해야 하는가"를 들고 있습니다.
`EntitlementsGuidance` 와 같은 이유로 한곳에 모읍니다. 서버 화면과 CLI 가 같은 실패를
각자 다른 문장으로 설명하면 읽는 사람은 매번 처음 보는 문제를 만납니다.

**코드를 문장 대신 내보내지 않습니다.** `unsigned_code_remains` 를 보고 무엇을 해야
하는지 아는 사람은 그 코드를 쓴 사람뿐입니다. 화면에는 문장을 쓰고, 코드는 지원 문의에
적을 수 있도록 문장 옆에 작게 둡니다. 관리 > 서명 워커의 최근 잡 표와 앱 상세의 버전
줄 양쪽에 같은 모양으로 붙입니다.

### 스키마

`signing_jobs` 에 `failure_code` 열(문자열)을 더하는 마이그레이션을 새로 추가합니다.
데이터베이스 enum 이 아닙니다. 갈래는 워커가 늘리는 값이라 enum 으로 묶으면 코드
하나를 더할 때마다 마이그레이션이 따라옵니다. `phase` 열과 같은 판단입니다.

## 대안과 기각 사유

### 문자열을 그대로 둔다

아무것도 안 하는 선택입니다. 실패 메시지에는 이미 사람이 읽을 것이 다 들어 있고,
실제로 원인을 찾는 사람은 그 문자열을 읽습니다. 코드를 붙인다고 그 문자열을 안 읽게
되지도 않습니다. 갈래 목록을 유지할 필요도, 워커와 서버의 버전을 맞출 필요도
없습니다.

기각한 이유는 **자동으로 판단하는 쪽이 아무것도 못 하기 때문**입니다. 사람이 읽어서
아는 것과 서버가 아는 것은 다릅니다. 재시도할지 말지는 사람이 화면을 보기 전에 서버가
정해야 하는 일이고, 그 자리에 있는 것은 문자열뿐입니다. 문자열에서 갈래를 뽑으려면
정규식으로 남의 도구 출력을 파싱해야 하는데, 그건 코드를 붙이는 것보다 훨씬 잘
깨집니다.

### 워커가 재시도 여부를 직접 정해 보낸다

`retriable: true` 한 칸이면 끝납니다. 갈래 목록도 필요 없고, 무엇이 일시적인지 가장
잘 아는 것은 오류를 손에 쥔 워커입니다. 서버는 그 불리언만 보면 됩니다. 새 실패
유형이 생겨도 워커만 고치면 되고 서버 배포가 필요 없습니다.

기각한 이유는 **정책이 워커 쪽으로 새어 나가기 때문**입니다. "몇 번까지 다시
내보내는가", "같은 버전을 두 번 공증에 올려도 되는가"는 큐를 가진 서버의 판단입니다.
워커가 그것을 정하기 시작하면 워커 여러 대의 판단이 서로 다를 수 있고, 판단을 바꾸려면
사람 책상 아래의 맥들을 전부 갱신해야 합니다. 그리고 불리언 하나로는 화면에 아무것도
쓸 수 없습니다. "다시 시도합니다"만 나오고 무엇 때문인지는 여전히 로그를 뒤져야
합니다. 갈래를 보내면 재시도 판단과 안내 문장을 둘 다 만들 수 있습니다.

### HTTP 상태 코드류를 재사용한다

숫자 코드는 이미 모두가 아는 어휘입니다. 4xx 는 보낸 쪽 잘못이라 다시 보내도 소용없고
5xx 는 받는 쪽 사정이라 다시 해볼 만하다는 관례가 그대로 재시도 규칙이 됩니다. 새
타입을 만들 것도 없고, 로그와 모니터링 도구가 숫자를 이미 잘 다룹니다.

기각한 이유는 **이것이 HTTP 가 아니기 때문**입니다. "인증서가 만료됐다"에 401 을 붙이면
읽는 사람은 서버 인증을 의심합니다. 공증 거절은 422 인가 400 인가를 매번 다시
고민하게 되고, 그 고민의 답이 사람마다 다르면 같은 실패에 다른 숫자가 붙습니다.
숫자는 아는 척하기 쉬운 만큼 틀린 연상을 부릅니다. 이 도메인에는 열 개짜리 자기
어휘가 있는 편이 낫습니다.

### 실패 로그를 별도 표로 뺀다

로그가 잡 행을 부풀리지 않고, 단계별로 조회할 수 있으며, 상한을 열 단위가 아니라 행
단위로 관리할 수 있습니다. 로그를 오래 보관하다가 잡만 지우는 것도 가능합니다.

기각한 이유는 **양이 그것을 요구하지 않기 때문**입니다. 잡 하나가 만드는 것은 일곱
줄입니다. 표 하나와 조인 하나를 늘려서 얻는 것이 "16KB 를 32KB 로 늘릴 수 있다"
정도라면 지금은 필요 없습니다. 나중에 로그가 실제로 문제가 되면 그때 빼는 쪽이
쉽습니다. 반대 방향은 어렵습니다.

## 결과

**좋은 점**

- 인증서 만료처럼 다시 해도 소용없는 실패가 즉시 사람에게 갑니다. 세 번을 기다리며
  큐 뒤를 밀지 않습니다
- 반대로 네트워크가 한 번 끊긴 것 때문에 수백 MB 를 다시 올리는 일이 없어집니다.
  지금까지 워커가 보고한 실패는 무조건 버전을 `failed` 로 만들었습니다
- 실패 직전 단계의 로그가 남습니다. "무엇을 하다가 죽었나"를 화면에서 볼 수 있습니다
- 화면에 무엇을 해야 하는지가 한국어로 나옵니다. 코드는 지원 문의용으로 옆에 있습니다
- 재시도 판단이 `SigningRetryPolicy` 한 곳에 있습니다. 보고받는 자리와 멈춘 잡 회수가
  같은 상한을 함께 씁니다

**나쁜 점**

- **워커와 서버의 버전이 어긋날 수 있습니다.** 갈래를 늘리면 새 워커가 보내는 코드를
  옛 서버가 모릅니다. 그때는 `unknown` 으로 접고 재시도하지 않습니다. 다시 해볼 만한
  갈래를 새로 만들었더라도 옛 서버에서는 한 번에 실패로 끝납니다. 서버를 먼저
  올리는 것이 맞지만, 워커는 사람 책상 아래의 맥이라 그 순서를 강제할 방법이 없습니다
- **모르는 코드는 원래 문자열이 남지 않습니다.** `unknown` 으로 접히면서 사라집니다.
  지원 문의 때는 잡 로그의 실패 메시지에서 찾아야 합니다
- **분류가 틀리면 재시도해야 할 것을 포기합니다.** 특히 `codesign` 과 `notarytool` 의
  출력에 기대는 두 자리는 Apple 이 문구를 바꾸면 조용히 틀립니다. `codesign` 쪽은
  두 결과가 모두 재시도하지 않는 갈래라 안내 문장만 엉뚱해지지만, `notarytool` 의
  `status` 값이 바뀌면 진짜 거절을 일시 오류로 보고 세 번 제출하게 됩니다
- **잡 하나가 큐를 세 번까지 돌 수 있게 됐습니다.** 일시적 실패가 실제로는 영구적인
  것이었다면 그만큼 늦게 사람에게 갑니다. 상한 3회가 그 최악을 묶고 있을 뿐입니다
- **로그 상한 16KB 는 짐작입니다.** 공증 로그가 유난히 긴 앱에서는 앞의 단계 기록이
  잘려 나갑니다. 정작 필요했던 것이 잘린 쪽일 수 있습니다
- 갈래 목록이 코드 상수입니다. 새 실패 유형을 다루려면 배포가 필요합니다

**후속 과제**

- `unknown` 이 얼마나 자주 오는지 세는 방법이 없습니다. 이 결정의 전제("분류하지 못한
  실패는 드물다")가 맞는지 확인하려면 그 숫자가 필요합니다
- 되돌린 잡이 상한까지 가서 실패로 끝났을 때 알림을 보낼지는 정하지 않았습니다.
  ADR-0018 이 남긴 같은 과제입니다
- 재시도 사이에 기다리는 시간이 없습니다. `transfer_failed` 로 되돌린 잡을 다음 워커가
  1초 안에 집어가면 같은 네트워크 문제를 그대로 만납니다
