# ADR-0021: 서버를 컨테이너 이미지로 발행한다

- 상태: 수락됨
- 날짜: 2026-09-02

## 맥락

지금까지 `docker-compose.yml` 의 server 는 `build: context: .` 로 소스에서 직접
지었습니다. CI 의 docker 잡도 이미지를 만들어보기만 하고 `push: false` 였습니다.

그래서 서버를 올리는 곳마다 제품 소스 체크아웃과 Swift 툴체인이 필요했고, 새 버전을
올리는 방법은 `git pull` 후 재빌드뿐이었습니다. Swift 릴리즈 빌드는 느려서 배포
때마다 몇십 분이 서버에서 지나갑니다.

운영 설정(도메인, 시크릿, 배포 매니페스트)은 이 레포 밖 비공개 레포로 분리할
계획입니다 ([ADR-0003](0003-organization-neutral-by-construction.md),
[ADR-0004](0004-docker-selfhosting-s3-abstraction.md)). 그런데 이미지가 없으면 운영
쪽에도 제품 소스가 또 있어야 해서, 분리한 값이 나오지 않습니다.

배포 이력도 문제입니다. 지금 돌고 있는 것이 무엇인지 말하려면 그 서버에 들어가
체크아웃된 커밋을 봐야 합니다.

## 결정

CI 가 서버 이미지를 `ghcr.io/<소유자>/<레포>` 에 발행합니다. 운영은 소스 없이 이
이미지를 받아 씁니다.

- **주소는 `github.repository` 에서 뽑습니다.** 레포 이름도 소유자도 하드코딩하지
  않습니다. 포크해도 자기 레포로 나갑니다
- **인증은 `GITHUB_TOKEN`** 입니다. 별도 시크릿을 요구하지 않습니다. 쓰기 권한
  (`packages: write`)은 docker 잡에만 줍니다
- **PR 에서는 짓기만 하고 밀지 않습니다.** 포크에서 온 PR 의 토큰에는 쓰기 권한이
  없어 밀면 실패합니다
- **테스트를 통과한 커밋만 발행합니다.** docker 잡이 리눅스 빌드·테스트 잡을
  기다립니다
- 태그 규칙:

  | 언제 | 붙는 태그 |
  | --- | --- |
  | 언제나 | `sha-<40자리 커밋 SHA>` |
  | main 에 밀 때 | `main` |
  | `v1.2.3` 태그를 밀 때 | `1.2.3`, `1.2`, `latest` |

  `latest` 는 버전 태그에만 붙습니다. 브랜치를 민다고 움직이지 않습니다.
  **운영에서는 `main` 이나 `latest` 를 쓰지 않습니다.** 움직이는 태그로 배포하면 다시
  받을 때마다 다른 것이 뜨고, 지금 무엇이 돌고 있는지 아무도 말할 수 없습니다
- **linux/amd64 만 발행합니다** (아래 대안 참조)
- compose 는 기본이 이미지이고, 소스 빌드는 `docker-compose.override.yml` 이 맡습니다.
  compose 가 override 를 자동으로 읽으므로 레포를 클론한 사람의 절차는 그대로입니다.
  운영은 `docker-compose.yml` 과 `.env` 만 가져가면 override 가 없어 이미지를 받습니다

## 대안과 기각 사유

**지금처럼 소스를 체크아웃해 빌드한다** — 레지스트리도 인증도 필요 없고, 이미지를
어디에 두고 누가 볼 수 있는지 고민할 일이 없습니다. 보관 비용도 없습니다. 그러나
서버마다 소스와 툴체인을 두어야 하고, 배포 단위가 "커밋" 이라 되돌리는 것도 재빌드가
됩니다. 몇십 분 걸리는 롤백은 롤백이 아닙니다.

**레지스트리를 사내에 둔다 (Harbor 같은 것을 직접 운영)** — 이미지가 밖으로 나가지
않아 공개 여부를 따질 필요가 없고, 당기는 것도 내부망에서 끝납니다. 그러나 오픈소스
레포가 특정 조직 인프라를 전제하게 되어 ADR-0003 과 정면으로 부딪칩니다. 포크한
사람은 그 워크플로를 쓸 수 없습니다. 사내로 옮기고 싶다면 ghcr 에서 당겨 사내
레지스트리로 미는 일을 **운영 레포 쪽에서** 하면 됩니다. 그건 그쪽의 결정이지 이
레포가 강요할 것이 아닙니다.

**이미지 대신 릴리즈에 바이너리를 붙인다** — 크기가 훨씬 작고 레지스트리가 필요
없습니다. 그러나 서버는 실행 파일 하나로 끝나지 않습니다. Swift 런타임 공유
라이브러리, `Public/` 의 정적 파일, Leaf 템플릿이 함께 있어야 합니다. Dockerfile 이
이미 그 조립을 하고 있는데, 바이너리만 내보내면 그 조립을 받는 쪽이 다시 해야 합니다.

**멀티아키텍처(amd64 + arm64)로 발행한다** — 사내 서버가 Apple Silicon 이거나 arm
인스턴스일 때 그대로 돕니다. 실제로 서명 워커용 맥을 서버로 겸하는 구성도 가능합니다.
그러나 방법이 둘 다 값이 큽니다. QEMU 크로스빌드는 Swift 컴파일러처럼 무거운
워크로드에서 몇 배로 느려져, 지금도 느린 이미지 빌드를 CI 에서 감당하기 어려운
수준으로 밀어올립니다. 네이티브 arm 러너를 매트릭스로 붙이는 방법은 빠르지만 잡이
둘로 늘고 다이제스트를 합치는 잡이 더 붙습니다. 게다가 arm 러너는 공개 레포에서만
무료라, 비공개로 포크한 사람의 CI 가 조용히 깨집니다. **필요해진 뒤에 붙입니다.**
그때는 QEMU 가 아니라 네이티브 러너 매트릭스로 갑니다.

## 결과

**좋은 점**
- 운영 레포는 태그 한 줄만 바꾸면 됩니다. 그 커밋이 "언제 무엇을 올렸는지" 이력이
  됩니다
- 롤백이 이전 태그로 되돌리는 일이 됩니다. 재빌드가 아닙니다
- 운영 호스트에 제품 소스도 Swift 툴체인도 두지 않습니다
- 커밋 SHA 태그가 언제나 있어서, 어떤 빌드든 정확히 하나를 가리킬 수 있습니다

**나쁜 점**
- **이미지가 GitHub Packages 에 남습니다.** 패키지 공개 여부는 레포 공개 여부와 따로
  관리해야 합니다. 처음 발행된 패키지는 비공개이고, 레포를 공개해도 자동으로 따라가지
  않습니다. 반대로 공개로 바꾼 뒤에는 누구나 당길 수 있습니다. 이미지 안에 비밀값을
  넣지 않는 것이 지금보다 더 중요해집니다
- 커밋마다 이미지가 쌓이는데 지우는 정책이 아직 없습니다. 저장 용량은 언젠가 손봐야
  합니다
- **워커와 스토어 앱은 이 경로를 쓸 수 없습니다.** macOS 바이너리라 리눅스 컨테이너에
  담기지 않습니다. 배포 방법이 둘로 갈립니다. 워커는 소스에서 짓고
  `install-worker.sh` 로 깔고, 스토어 앱은 첫 배포만 사람이 나눠준 뒤 자기 자신을
  갈아끼웁니다 ([ADR-0014](0014-store-app-without-xcode-project.md))
- amd64 만 발행하므로 Apple Silicon 호스트에서는 에뮬레이션으로 돕니다. 돌기는 하지만
  느립니다
- GHCR 에 묶입니다. GitHub 이 아닌 곳에서 CI 를 돌리는 포크는 이 워크플로를 그대로
  쓸 수 없습니다
- 버전 태그를 미는 것이 곧 발행이라, 태그를 잘못 밀면 되돌리기가 번거롭습니다. 같은
  태그로 다시 발행하면 다이제스트가 바뀌어, 그 태그를 이미 받아간 곳과 달라집니다

**후속**
- 마이그레이션은 여전히 사람이 돌립니다. 서버는 부팅할 때 스키마를 건드리지 않습니다.
  이미지만 바꾸고 마이그레이션을 잊으면 새 코드가 없는 열을 찾습니다. 업그레이드
  절차를 [운영 가이드](../operations.md#서버-업그레이드)에 적었지만, 절차를
  문서에 적는 것으로 끝낼 일인지는 다시 볼 필요가 있습니다
- 오래된 sha 태그를 정리하는 보관 정책
- arm64 가 실제로 필요해지면 네이티브 러너 매트릭스로 추가
