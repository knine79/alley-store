# ADR-0068: 스토어 앱은 기본 브라우저로 로그인하고 PKCE 로 코드를 지킨다

- 상태: 수락됨
- 날짜: 2026-10-01

## 맥락

스토어 앱은 `ASWebAuthenticationSession` 으로 로그인했습니다 (ADR-0008). 서버가
로그인을 끝내면 커스텀 스킴(`<scheme>://auth?code=…`)으로 돌려보내고, 세션이 그
URL 을 앱에 넘겨줍니다.

macOS 14 부터 이 세션은 기본 브라우저가 지원하면 Safari 대신 **그 브라우저에 로그인을
맡깁니다.** Chrome 이 그렇습니다. 운영에서 이런 일이 있었습니다.

1. Chrome 에서 Google 로그인을 끝까지 했는데 앱은 로그인되지 않았다. 서버 기록을 보면
   코드는 발급됐고 아무도 교환하지 않은 채 만료됐다
2. 그 뒤로는 버튼을 누르면 Chrome 으로 포커스만 넘어가고 아무 일도 없었다. **앱을 새로
   띄워도 같았다.** 사용자 맥의 로그에는 세션 시작까지만 있고, 서버에는 요청이 오지
   않았다
3. Chrome 을 껐다 켜자 풀렸다

막힌 곳은 Chrome 안이었습니다. 끝나지 않은 인증 요청을 Chrome 이 쥐고 있었습니다.
그런데 **그 구간은 앱이 들여다볼 수도, 끊을 수도 없습니다.** 세션의 완료 처리기가
불리지 않으면 앱은 기다릴 뿐이고, 사람에게 "브라우저를 껐다 켜세요" 말고는 해줄 말이
없습니다.

## 결정

**로그인 주소를 기본 브라우저로 그냥 열고, 돌아오는 커스텀 스킴 URL 은 앱이 Apple
Event(GetURL)로 직접 받습니다.** 코드를 커스텀 스킴에 싣는 것은 그대로이고, 코드를
세션 토큰으로 바꾸는 단계(ADR-0008)도 그대로입니다.

```
스토어 앱                            브라우저                       서버
  verifier 를 만든다
  challenge = S256(verifier)
  NSWorkspace.open ───────────────▶ /auth/google?client=app
                                     &code_challenge=…  ─────────▶ state 에 challenge 를 서명해 싣는다
                                     (공급자 로그인)    ◀─────────▶
                                                        ◀───────── 302 <scheme>://auth?code=…
                                                                    코드에 challenge 를 묶어 저장
  GetURL ◀──────────────────────── LaunchServices
  POST /api/v1/auth/token {code, codeVerifier} ──────────────────▶ S256(verifier) == challenge 인가
```

### 커스텀 스킴을 남이 받을 수 있으므로 PKCE 를 붙입니다

`ASWebAuthenticationSession` 은 콜백을 **로그인을 시작한 그 앱에만** 돌려줬습니다.
LaunchServices 로 넘기면 그렇지 않습니다. 같은 스킴을 등록한 앱은 누구든 받을 수
있습니다. 그래서 RFC 7636 의 PKCE 를 붙입니다.

- 앱은 로그인할 때마다 32바이트 verifier 를 만들고, 그 SHA-256(`S256`)만 주소에 싣습니다
- 서버는 challenge 를 서명된 OAuth `state` 에 실어 공급자에게 갔다 오고, 콜백에서
  발급하는 코드에 묶어 저장합니다
- 교환할 때 verifier 를 함께 가져와야 하고, 그 해시가 맞아야 합니다

코드를 가로챈 앱에는 verifier 가 없습니다. 반대로 남이 자기 코드를 우리 앱에 밀어
넣어도, 그 코드에는 우리 앱의 challenge 가 묶여 있지 않아 교환되지 않습니다.
`plain` 방식은 받지 않습니다. 주소를 본 쪽이 verifier 도 알게 됩니다.

### 틀린 verifier 는 코드를 태우지 않습니다

가로챈 쪽이 틀린 값으로 한 번 불러 코드를 소진시키면 진짜 앱이 로그인을 다시 해야
합니다. verifier 는 256비트라 소진하지 않아도 2분 안에 맞힐 수 없습니다.

### 앱이 받은 코드는 CLI 교환에서 바꿔주지 않습니다

CLI 교환(ADR-0064)도 같은 `auth_codes` 표를 씁니다. 막지 않으면 앱 콜백에서 가로챈
코드를 verifier 없이 CLI 교환으로 가져가 **90일짜리 사람 토큰**으로 바꿀 수 있습니다.
CLI 교환은 challenge 가 묶인 코드를 거절합니다.

### challenge 없는 로그인을 당분간 받습니다

challenge 를 보내지 않는 예전 스토어 앱이 남아 있습니다. 그 앱은 스스로를 스토어에서
업데이트하므로, 바뀌기 전까지는 challenge 가 없는 로그인과 교환을 예전처럼 받습니다.

### SwiftUI `onOpenURL` 대신 Apple Event 처리기를 직접 겁니다

`WindowGroup` 은 URL 이 들어오면 그것을 받을 창을 고르고, 고르지 못하면 새 창을
띄웁니다. 이 앱은 창이 하나여야 합니다. `NSAppleEventManager` 에 직접 걸면 창과
상관없이 받습니다.

## 대안과 기각 사유

### `ASWebAuthenticationSession` 을 두고 앱 쪽만 다듬는다

**바꿀 것이 가장 적고, 콜백이 그 앱에만 돌아온다는 보장을 그대로 누립니다.** 다시
누르면 앞 세션을 `cancel()` 하고, 시간 제한을 두고, GetURL 처리기를 대비책으로 거는
정도면 됩니다.

기각한 이유는 이번에 막힌 곳이 앱이 아니라 Chrome 이었기 때문입니다. 새로 띄운
앱에서도 똑같이 멈췄습니다. 앱 쪽에서 아무리 다듬어도 Chrome 이 요청을 쥐고 있으면
고칠 수 없습니다.

### `prefersEphemeralWebBrowserSession` 을 켜서 Safari 로 고정한다

**Chrome 을 피해 가면서 지금 구조를 지킵니다.** ephemeral 세션은 기본 브라우저에
맡기지 않는다는 이야기가 있습니다.

기각한 이유는 둘입니다. 그 동작은 문서에 약속된 것이 아니라 관찰된 것이라 다음 OS 에서
바뀌어도 할 말이 없습니다. 그리고 ephemeral 은 브라우저에 남은 공급자 세션을 쓰지
못합니다. 사람이 매번 계정을 고르고 비밀번호를 칩니다.

### 루프백 주소로 받는다 (CLI 처럼)

**스킴을 가로챌 다른 앱이 없습니다.** 127.0.0.1 의 빈 포트를 잠깐 열고 받으면 되고,
CLI 가 이미 그렇게 합니다 (ADR-0064). 브라우저가 "이 앱을 여시겠습니까" 를 묻지도
않습니다.

기각한 이유는 앱이 HTTP 서버를 띄우고, 브라우저 탭에 보여줄 화면까지 그려야 하기
때문입니다. 그만큼 얻는 것은 가로채기를 막는 것인데, 커스텀 스킴에 PKCE 를 붙이면
그것도 막힙니다. 스킴은 이미 번들에 등록돼 있습니다.

### 앱 안 웹뷰로 로그인한다

**브라우저에 전혀 기대지 않습니다.**

기각한 이유는 Google 이 앱 안에 박힌 웹뷰 로그인을 막고, 사용자의 비밀번호가 앱을
지나기 때문입니다. ADR-0008 이 이 길을 이미 버렸습니다.

## 결과

**좋은 점**

- 로그인이 기본 브라우저의 인증 세션 구현에 기대지 않습니다. 커스텀 스킴은 어느
  브라우저든 LaunchServices 로 넘깁니다
- 앱이 기다리는 상태를 직접 쥡니다. 다시 누르면 앞 시도를 접고, 10분(state 수명)이
  지나면 그만둡니다. 화면에 "브라우저에서 로그인을 마치면 돌아옵니다" 와 취소가 보입니다
- 로그인 경로에 로그가 생겼습니다(`category == "sign-in"`). 이번에는 시스템 로그를
  뒤져야 했습니다
- 앱 콜백에서 가로챈 코드를 CLI 교환으로 가져가는 길이 닫혔습니다. 이것은 이 결정
  이전부터 있던 구멍입니다

**나쁜 점**

- **브라우저가 "이 앱을 여시겠습니까" 를 묻습니다.** 처음 한 번은 사람이 눌러야 하고,
  거기서 취소하면 앱은 기다리다 시간이 다 됩니다. 다시 누르면 되지만 한 단계가
  늘었습니다
- **로그인을 마친 브라우저 탭이 남습니다.** `ASWebAuthenticationSession` 은 창을 알아서
  닫았습니다
- **같은 스킴을 등록한 다른 앱이 있으면 그 앱이 콜백을 받습니다.** PKCE 로 코드는
  지키지만, 그때 우리 앱은 로그인이 끝난 줄 모르고 시간이 다 될 때까지 기다립니다.
  스킴은 조직마다 정하므로 겹치지 않게 짓는 것이 운영자 몫으로 남습니다
- 예전 앱을 위해 challenge 없는 교환을 열어두는 동안은 그 앱의 코드가 가로채기에
  열려 있습니다. 예전과 같은 수준이지 더 나빠지지는 않았습니다
- 앱이 떠 있지 않을 때 들어온 콜백은 받지 못합니다. 로그인은 앱이 기다릴 때만
  시작하므로 실제로는 생기지 않지만, 앱을 강제 종료하고 브라우저 로그인을 마치면 그
  코드는 그대로 만료됩니다

**후속**

- 스토어 앱이 모두 이 버전 이상이 되면 `/auth/google?client=app` 에 challenge 를
  필수로 올리고, 앱 교환에서 challenge 없는 코드를 거절합니다
- 로그인을 마친 브라우저 탭에 "앱으로 돌아가세요" 를 보여줄지 검토합니다. 지금은 302 로
  바로 스킴으로 보내서, 사람이 확인 창에서 취소하면 탭에 남는 것이 없습니다
