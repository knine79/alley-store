# ADR-0010: 세션 토큰을 쿠키와 Authorization 헤더 양쪽에서 받는다

- 상태: 수락됨
- 날짜: 2026-08-14

## 맥락

ADR-0008에서 세션 토큰의 내용과 발급 경로를 정했습니다. 웹 콘솔은 로그인 후
`alley_session` HttpOnly 쿠키를 받고, 스토어 앱은 일회용 코드를 교환해 토큰을
직접 손에 쥡니다.

그런데 인증 미들웨어는 `Authorization: Bearer` 헤더만 읽고 있었습니다. 즉 웹
콘솔은 쿠키를 받아도 API를 부를 수 없었습니다. Phase 1-1 로그인을 실제로
확인하다가 발견했습니다.

두 클라이언트가 같은 API를 쓰는데 토큰을 담는 자리가 다릅니다. 하나로 맞추거나,
양쪽을 다 받거나 정해야 했습니다.

## 결정

인증 미들웨어가 두 자리를 모두 봅니다. **헤더를 먼저 보고, 없으면 쿠키를 봅니다.**

순서가 중요합니다. 브라우저는 같은 출처의 모든 요청에 쿠키를 자동으로 붙입니다.
헤더를 명시한 요청은 그 신원으로 부르겠다는 뜻이므로, 자동으로 붙은 쿠키가
이겨서는 안 됩니다. 반대로 두면 디버깅 도구에서 다른 계정 토큰을 헤더에 넣어도
브라우저 세션으로 동작해 사람을 헷갈리게 합니다.

쿠키는 `HttpOnly`, `SameSite=Lax`, 그리고 공개 주소가 HTTPS일 때 `Secure`로
내보냅니다.

CSRF 방어는 `SameSite=Lax`에 맡깁니다. Lax는 다른 사이트에서 시작한 POST,
PATCH, DELETE 요청에 쿠키를 붙이지 않습니다. 상태를 바꾸는 요청은 전부 이
메서드들이므로, 남의 사이트가 사용자 브라우저를 시켜 앱을 출시하게 만들 수
없습니다.

## 대안과 기각 사유

**헤더만 받는다 (쿠키를 인증에 쓰지 않는다)** — 인증 경로가 하나뿐이라 단순하고,
CSRF를 아예 생각하지 않아도 됩니다. 그러나 그러려면 웹 콘솔이 토큰을 자바스크립트가
읽을 수 있는 곳(`localStorage` 등)에 둬야 합니다. 그 순간 HttpOnly 쿠키의 이점이
사라집니다. XSS 하나로 7일짜리 토큰이 통째로 나갑니다. CSRF는 `SameSite`로 막을
수 있지만 XSS로 새어나간 토큰은 막을 방법이 없습니다.

**쿠키만 받는다** — 스토어 앱이 쿠키 저장소를 관리해야 합니다. 네이티브 앱에서
쿠키는 다루기 번거롭고, `URLSession`의 쿠키 저장소는 앱 전체가 공유해서 다른
요청에 섞여 나갈 수 있습니다. 앱은 토큰을 키체인에 두고 헤더로 보내는 편이 자연스럽습니다.

**쿠키를 받되 CSRF 토큰을 따로 요구한다 (double submit)** — `SameSite`를 지원하지
않는 브라우저까지 막습니다. 그러나 이 스토어는 사내 macOS 사용자가 대상이고,
Safari와 Chrome 최신 버전만 상대하면 됩니다. 둘 다 `SameSite`를 오래전부터
지원합니다. 모든 폼과 요청에 토큰을 실어 나르는 비용이 지금은 이득보다 큽니다.

**두 자리를 다 보되 쿠키를 우선한다** — 웹 콘솔에서 항상 로그인한 계정으로
동작해서 헷갈릴 일이 없습니다. 그러나 헤더로 명시한 신원을 무시하는 것이라
API 클라이언트를 브라우저에서 테스트할 때 원인 모를 동작을 만듭니다.

## 결과

**좋은 점**

- 웹 콘솔의 토큰이 자바스크립트에 노출되지 않습니다. XSS가 나도 토큰은 못 가져갑니다
- 스토어 앱과 웹 콘솔이 같은 API를 그대로 씁니다. 인증 때문에 갈라지는 코드가 없습니다
- 브라우저 주소창으로 API를 열어보면 로그인한 상태로 보입니다. 개발 중에 편합니다

**나쁜 점**

- 인증 경로가 둘이라 권한 관련 테스트를 두 배로 해야 합니다
- CSRF 방어가 `SameSite=Lax`라는 브라우저 동작 하나에 걸려 있습니다. 이 설정이
  빠지거나 잘못되면 조용히 뚫립니다. 코드를 봐서는 방어가 어디 있는지 안 보입니다
- `GET` 요청은 Lax에서도 쿠키가 붙습니다. 남의 사이트가 사용자를 다운로드
  엔드포인트로 이동시키면 응답은 못 읽어도 다운로드 이력은 남습니다. 이력이
  더러워지는 정도라 지금은 받아들입니다
- 쿠키 이름(`alley_session`)이 서버와 웹 콘솔이 공유하는 또 하나의 규약입니다

**후속**

- 웹 콘솔(Phase 1-4)을 만들 때 로그아웃 경로가 필요합니다. 쿠키를 지우는 것만으로는
  토큰이 무효화되지 않습니다(ADR-0008의 한계와 같습니다)
- 상태를 바꾸는 요청에 `Origin` 헤더 검사를 덧붙이면 `SameSite`에만 기대지 않게
  됩니다. 방어가 코드에 드러난다는 이점도 있습니다
