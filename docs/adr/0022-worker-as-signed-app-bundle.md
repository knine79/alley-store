# ADR-0022: 서명 워커를 서명·공증된 `.app` 번들로 배포한다

- 상태: 수락됨
- 날짜: 2026-09-02

## 맥락

지금까지 서명 워커는 설치 스크립트가 그 자리에서 빌드해 만든 맨 실행 파일이었습니다.
`swift build -c release --product alley-worker` 를 돌리고 결과 바이너리를
`~/Library/Application Support/alley-worker/` 에 복사한 뒤 launchd 에 등록했습니다.

여기서 세 가지가 걸립니다.

**워커 맥마다 소스 체크아웃과 Swift 툴체인이 필요합니다.** 워커는 코드 서명
인증서를 보관하는 맥이지 개발 머신이 아닙니다. 그런 맥에 레포를 클론하고 Swift 를
깔아야 한다면 워커를 두 대 이상 붙이는 일이 사실상 막힙니다. 인증서를 나눠 갖는
비용은 그대로인데 설치 비용만 늘어납니다.

**워커 자신이 서명되어 있지 않습니다.** 회사 Developer ID 개인키를 다루는
프로세스이고, 그 프로세스가 하는 일이 남의 앱을 서명하고 공증하는 것입니다. 정작
자기는 출처를 확인할 수 없는 바이너리로 돌고 있었습니다. 누가 슬쩍 바꿔치기해도
알아볼 방법이 없습니다.

**갱신 방법이 사람 손밖에 없습니다.** 워커 버그는 그 워커가 서명한 모든 앱의 배포
품질을 망칩니다. 그런데 고쳐도 퍼뜨릴 방법이 없습니다.

이번 결정은 앞의 둘을 다룹니다. 세 번째(자동 업데이트)는 별도로 정합니다.

## 결정

워커를 `.app` 번들로 조립하고, Developer ID 로 서명하고 공증한 뒤, 그 번들을
설치합니다.

- `scripts/build-worker-app.sh` 가 번들을 조립합니다. `--sign` 을 주면 Hardened
  Runtime 으로 서명하고 공증과 스테이플까지 마친 zip 을 내놓습니다
- `scripts/install-worker.sh --bundle <경로>` 가 이미 만들어진 번들이나 zip 을
  설치합니다. 인자 없이 부르면 예전처럼 이 레포에서 빌드합니다. 앞의 경로가 이번
  변경의 핵심이고, 그 경로에는 소스도 Swift 툴체인도 필요 없습니다
- launchd 는 `<번들>/Contents/MacOS/alley-worker` 를 직접 부릅니다. LaunchAgent 인
  이유는 그대로입니다. 서명 개인키가 로그인 키체인에 있습니다(ADR-0002)
- 조직마다 다른 값은 환경변수로 받고 기본값은 `com.example` 계열입니다(ADR-0003)

**UI 가 없는데도 번들로 만드는 이유는 공증 티켓입니다.** `xcrun stapler` 는 티켓을
박을 자리가 필요해서 맨 실행 파일에는 스테이플할 수 없습니다. 스테이플하지 않으면
Gatekeeper 가 매번 Apple 서버에 물어봐야 하고, 그 조회가 실패하는 순간 워커가
뜨지 않습니다. 번들이면 티켓이 안에 박혀 오프라인에서도 통과합니다.

**`Info.plist` 에는 `LSUIElement` 가 아니라 `LSBackgroundOnly` 를 넣습니다.**
Apple 의 Launch Services Keys 문서가 둘을 이렇게 나눕니다. `LSUIElement` 는 agent
app 으로 Dock 에 뜨지 않지만 "can come to the foreground to present a user
interface if desired" 입니다. 메뉴 막대 앱이 그 자리입니다. `LSBackgroundOnly` 는
"runs only in the background ... faceless background apps" 이고 앞으로 나올 수
없습니다. 워커는 아무것도 그리지 않고 AppKit 을 링크하지도 않으므로 실제 성질을
그대로 적은 쪽은 후자입니다. 다만 평소에는 이 키가 쓰이지 않습니다. launchd 가
실행 파일을 직접 exec 하면서 Launch Services 를 거치지 않기 때문입니다. 이 키가
일하는 때는 누군가 번들을 Finder 에서 더블클릭할 때입니다.

**entitlements 는 붙이지 않습니다.** Hardened Runtime 이 막는 것은 JIT, 서명되지
않은 실행 메모리, 라이브러리 검증 우회, DYLD 환경변수, 디버거 붙이기입니다. 자식
프로세스를 띄우는 것은 그 목록에 없습니다. 워커가 하는 일은 `codesign`, `ditto`,
`xcrun` 을 exec 하는 것뿐이라 필요한 예외가 없습니다. 예방 차원으로 넣어두면 그
예외가 실제로 필요해졌을 때 아무도 알아채지 못합니다.

**키체인 ACL 은 워커의 서명이 바뀌어도 영향받지 않습니다.** 워커는 개인키를 직접
읽지 않습니다. `SigningPipeline` 은 `/usr/bin/codesign` 에 `--sign <identity>` 를
넘길 뿐이고, 키를 꺼내는 것은 `codesign` 프로세스입니다. 공증도 마찬가지로
`xcrun notarytool --keychain-profile` 이 자격증명을 읽습니다. 키체인 항목의 ACL 이
평가하는 대상은 접근하는 그 프로세스이므로 목록에 올라 있는 것은 Apple 이 서명한
`codesign` 과 `notarytool` 입니다. 워커를 새로 서명하거나 새 버전으로 갈아끼워도
"항상 허용" 이 풀리지 않습니다. 자동 업데이트를 붙일 때 이 사실이 전제가 됩니다.

**두 조립 스크립트의 공통 부분은 `scripts/lib/bundle.sh` 로 뺐습니다.** 서명·압축·
공증·스테이플이 스토어 앱과 글자 그대로 같고, 그 안에는 `--options runtime` 과
`--timestamp` 처럼 빠지면 배포가 통째로 막히거나 인증서 만료와 함께 조용히 죽는
값들이 있습니다. `Info.plist` 는 각자 만듭니다. 스토어 앱은 URL 스킴과 Dock
아이콘이 필요하고 워커는 UI 자체가 없어서, 하나의 템플릿에 조건을 붙이면 양쪽 다
읽기 나빠집니다.

## 대안과 기각 사유

**맨 바이너리를 유지하고 서명만 붙인다** — 가장 작은 변경입니다. `codesign` 은
단일 Mach-O 실행 파일도 서명하고, `notarytool` 은 그것을 담은 zip 도 공증합니다.
번들 디렉터리 구조도 `Info.plist` 도 필요 없습니다. 그러나 공증 티켓을 스테이플할
수 없습니다. 티켓 없이 배포하면 Gatekeeper 평가마다 Apple 서버 조회가 필요하고,
그 조회는 네트워크가 막힌 사내망에서 자주 실패합니다. 워커가 조용히 안 뜨는 실패
모드를 사려고 서명한 것이 아닙니다.

**pkg 설치본으로 만든다** — macOS 가 원래 준비해둔 소프트웨어 배포 형식입니다.
`productbuild` 로 만들고 Developer ID Installer 로 서명하면 공증도 스테이플도
됩니다. 파일을 어디에 놓을지, 설치 전후에 무엇을 돌릴지가 선언으로 표현되고,
관리자가 MDM 으로 밀어 넣기도 좋습니다. 실제로 가장 아까운 대안이었습니다. 그러나
인증서가 하나 더 필요합니다. Developer ID Installer 는 Application 과 별개로
발급받아야 하고, 셀프호스팅하는 조직에 "인증서를 두 종류 준비하세요" 를 요구하게
됩니다. 게다가 pkg 는 관리자 권한을 요구하는데, 워커 설치는 그 사람의 홈 디렉터리
안에서만 일어납니다. 필요 없는 권한을 요구하는 설치본을 만들 이유가 없습니다.

**Homebrew tap 으로 배포한다** — `brew install` 한 줄이면 끝나고, `brew upgrade`
가 갱신 문제까지 함께 풉니다. 세 번째 문제를 공짜로 가져가는 셈이라 가장 매력적인
제안이었습니다. 그러나 tap 을 두려면 공개 저장소 하나를 더 운영해야 하고, 조직마다
자기 tap 을 만들어야 합니다. 오픈소스로 공개하되 각 조직이 자기 서버를 띄우는
구조(ADR-0004)에서 배포 채널만 우리 것을 강제하는 모양이 됩니다. 무엇보다 Homebrew
는 bottle 을 다운로드할 때 SHA-256 만 확인하고 공증은 보지 않습니다. 워커가 서명된
채로 도는지는 여전히 우리가 챙겨야 합니다.

**그냥 소스 빌드를 유지한다** — 워커 맥이 한 대라면 실제로 아무 문제가 없습니다.
빌드가 곧 출처 증명이라 서명이 주는 것도 절반은 이미 가진 셈입니다. 그러나 워커 맥은
인증서를 보관하는 맥이고, 그런 맥에 개발 도구 일습을 깔아두는 것 자체가 공격
표면입니다. Swift 툴체인은 컴파일러와 네트워크로 의존성을 끌어오는 패키지 매니저를
함께 데려옵니다. 인증서만 있으면 되는 머신에 필요 없는 것들입니다.

## 결과

**좋은 점**

- 워커 맥에 소스도 Swift 도 필요 없습니다. 번들 하나를 만들어 여러 대에 나눠줍니다
- 워커 자신이 Developer ID 로 서명되고 공증됩니다. 인증서를 다루는 프로세스의 출처를
  이제 확인할 수 있습니다
- 공증 티켓이 번들에 박혀 있어 네트워크가 막힌 사내망에서도 Gatekeeper 를 통과합니다
- 서명·공증 절차가 스토어 앱과 한 파일에 모여 있어 한쪽만 낡는 일이 줄어듭니다
- 설치 경로가 고정된 번들이라, 자동 업데이트를 붙일 때 갈아끼울 자리가 이미 있습니다

**나쁜 점**

- **`Info.plist` 를 만드는 코드는 여전히 둘입니다.** 공통 부분을 뺀 것은 서명 쪽뿐이라
  번들 구조가 갈라질 여지가 남습니다. 대신 파일이 셋으로 늘어 한 스크립트만 읽어서는
  전체 절차를 알 수 없게 됐습니다. 어느 쪽이 나은지는 시간이 지나야 압니다
- **워커 릴리스를 누가 언제 만드는지 정해지지 않았습니다.** 지금은 인증서를 가진
  사람이 자기 맥에서 `--sign` 을 돌리는 것 말고는 절차가 없습니다. CI 에서 만들려면
  Developer ID 개인키를 CI 에 두어야 하는데, 그것은 이 프로젝트가 워커를 따로 둔
  이유(ADR-0002)를 정면으로 거스릅니다
- **자동 업데이트가 아직 없습니다.** 여전히 사람이 각 워커 맥에 가서 설치합니다. 이
  결정은 그 일을 쉽게 만들 뿐 없애지 못합니다
- `.app` 확장자가 사람을 헷갈리게 합니다. Dock 에도 안 뜨고 더블클릭해도 아무 일이
  일어나지 않는데 Finder 는 앱으로 보여줍니다
- 번들의 버전(`CFBundleShortVersionString`)과 코드 안의 `workerVersion` 이 따로
  관리됩니다. 지금은 둘 다 `0.1.0` 이지만 어긋나도 아무도 모릅니다
- 설치 스크립트는 번들의 서명이 유효한지만 봅니다. **누가 서명했는지는 확인하지
  않습니다.** 다른 Team ID 로 서명된 번들을 줘도 그대로 설치합니다
- 공증이 Apple 서버에 달려 있어 워커 릴리스 하나에 몇 분에서 몇십 분이 듭니다

**후속**

- 자동 업데이트를 붙입니다. 위의 버전 이원화와 "사람이 설치한다" 는 그때 함께 풉니다
- 릴리스를 누가 만드는지 정합니다. 인증서를 CI 에 두지 않는다면 사람이 만든 결과물을
  어디에 올리고 워커가 어떻게 찾을지가 그 결정의 내용입니다
- 설치 스크립트에 Team ID 확인을 더할지 검토합니다. 조직마다 다른 값이라 환경변수로
  받아야 하고, 그러면 안 넣은 사람에게는 아무 보호가 없다는 점을 같이 봐야 합니다
