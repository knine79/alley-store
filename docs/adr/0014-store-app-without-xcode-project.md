# ADR-0014: 스토어 앱을 Xcode 프로젝트 없이 SwiftPM 과 조립 스크립트로 만든다

- 상태: 수락됨
- 날짜: 2026-08-31

## 맥락

스토어 앱은 macOS SwiftUI 앱입니다. 보통 이런 것은 Xcode 프로젝트로 만듭니다.

그런데 이 레포는 이미 SwiftPM 모노레포입니다(ADR-0001). 서버, 워커, 공유 코드가 한
`Package.swift` 안에 있고 `swift build` 하나로 전부 빌드됩니다. 여기에 `.xcodeproj`
를 더하면 빌드 시스템이 둘이 됩니다.

앱이 하는 일도 봐야 합니다. 창 하나, 화면 셋, 스토리보드 없음, 에셋 카탈로그도
아직 없습니다. Xcode 프로젝트가 주는 것들(빌드 설정 GUI, 타깃 편집기, 에셋 관리)이
지금은 대부분 빈칸입니다.

## 결정

`Package.swift` 에 `AlleyStoreCore`(라이브러리)와 `AlleyStore`(실행 파일) 타깃을
두고, `scripts/build-store-app.sh` 가 `.app` 번들을 조립합니다.

- 스크립트가 `Info.plist` 를 생성해 껍데기를 씌우고, `--sign` 을 주면 Hardened
  Runtime 으로 서명하고 공증까지 진행합니다
- 번들 ID, 앱 이름, URL 스킴, 버전은 환경변수로 넘깁니다. 조직마다 다른 값이고
  코드에 박히면 안 되는 것들입니다(ADR-0003)
- 앱 코드는 라이브러리 타깃에 두고 실행 타깃은 `AlleyStoreApp.main()` 한 줄만
  갖습니다. 그래야 테스트가 앱 코드를 그대로 임포트합니다
- 스토어 앱 타깃은 `#if os(macOS)` 로 감쌉니다. 리눅스 CI 는 서버와 공유 코드만
  빌드하고, 앱은 macOS 잡이 빌드합니다

## 대안과 기각 사유

**Xcode 프로젝트를 만들어 커밋한다** — 가장 익숙한 길입니다. SwiftUI 프리뷰가 바로
돌고, 에셋 카탈로그와 앱 아이콘을 GUI 로 다루고, 서명 설정을 Xcode 가 알아서
관리합니다. 앱이 커지면 결국 필요해질 것들입니다. 그러나 `pbxproj` 는 사람이 읽고
합칠 수 없는 형식입니다. 두 사람이 파일을 추가하면 충돌이 나고, 충돌을 푸는 사람은
자기가 무엇을 고치는지 모릅니다. 오픈소스로 공개하는 레포에서 리뷰할 수 없는 파일이
가장 자주 바뀌는 것은 나쁜 조합입니다.

**XcodeGen 을 쓴다** — `project.yml` 만 커밋하고 `.xcodeproj` 는 생성물로 둡니다.
위의 병합 문제가 사라지면서 Xcode 경험은 그대로입니다. 실제로 가장 아까운
대안이었습니다. 그러나 셀프호스팅하는 사람이 앱을 직접 빌드하려면 Homebrew 로
도구를 하나 더 깔아야 하고, 그 도구의 버전이 프로젝트 파일의 형식을 좌우합니다.
지금 앱의 크기에서 그 의존을 감수할 이유가 약합니다.

**Tuist 를 쓴다** — 프로젝트를 Swift 로 기술해서 모노레포와 언어가 통일됩니다.
모듈이 여러 개로 갈라질 때 강합니다. 그러나 앱 하나에는 무겁고, XcodeGen 과 같은
"도구를 하나 더 깐다" 문제를 그대로 갖습니다.

**앱을 별도 레포로 뺀다** — 서버와 앱의 릴리즈 주기를 따로 가져갈 수 있습니다.
그러나 `AlleyShared` 를 패키지로 배포해서 버전을 맞춰야 하고, DTO 를 하나 고칠
때마다 두 레포를 오가게 됩니다. Phase 1 에서 가장 자주 하는 일이 그것입니다.

## 결과

**좋은 점**

- 빌드 시스템이 하나입니다. `swift build` 로 서버·워커·앱이 함께 빌드되고,
  DTO 를 고치면 세 곳의 컴파일 오류가 한 번에 드러납니다
- 리뷰할 수 없는 파일이 없습니다. 앱 설정이 `Package.swift` 와 셸 스크립트에만
  있고 둘 다 diff 로 읽힙니다
- 셀프호스팅하는 사람이 Xcode 없이도 앱을 빌드합니다. Command Line Tools 면 됩니다
- 앱 코드가 라이브러리에 있어서 설치 검증 같은 핵심 로직에 테스트가 닿습니다

**나쁜 점**

- **SwiftUI 프리뷰를 쓸 수 없습니다.** 화면을 고칠 때마다 빌드하고 앱을 띄워
  눈으로 봐야 합니다. UI 작업의 속도가 확실히 느려집니다
- 앱 아이콘과 에셋 카탈로그를 넣으려면 스크립트가 `actool` 을 부르도록 손봐야
  합니다. 지금은 아이콘이 없습니다
- `Info.plist` 가 셸 스크립트 안의 heredoc 입니다. 항목이 늘어나면 읽기 나빠지고,
  실수해도 앱을 띄워보기 전까지 모릅니다
- Xcode 로 열어 디버깅하려면 패키지를 열어 스킴을 골라야 하고, 그렇게 실행한 것은
  `.app` 번들이 아니라 맨 실행 파일입니다. 번들 ID 가 필요한 동작(키체인 접근,
  URL 스킴 등록)이 그 상태에서는 다르게 굽니다

**후속**

- 화면이 늘어나거나 디자이너가 붙으면 XcodeGen 으로 옮기는 것을 다시 검토합니다.
  그때는 프리뷰의 값이 도구 하나의 비용을 넘습니다
- 앱 아이콘이 필요해지면 `actool` 호출을 스크립트에 더합니다
- `Info.plist` 항목이 열 개를 넘으면 템플릿 파일로 빼고 스크립트는 치환만 합니다
