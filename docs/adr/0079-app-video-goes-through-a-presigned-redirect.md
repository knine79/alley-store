# ADR-0079: 앱 동영상은 하나만 두고, 로그인 확인 뒤 스토리지 주소로 넘겨 튼다

- 상태: 수락됨
- 날짜: 2026-10-26

## 맥락

앱 상세에 스크린샷을 둘 수 있게 됐지만(ADR-0071) 정지 화면으로는 동작을 전하기
어려운 앱이 있습니다. 화면 전환이나 인터랙션이 핵심이면 짧은 영상 하나가 스크린샷 여러
장보다 낫습니다 (이슈 #73).

동영상은 그림과 두 가지가 다릅니다.

- **크기.** 화면 녹화 1분이 수십 MB 입니다. 스크린샷은 한 장에 5MB 라서 서버가 스토리지에서
  받아 그대로 넘겨도 됐습니다
- **받는 방식.** 플레이어는 파일을 한 번에 받지 않고 필요한 구간(`Range`)을 따로 청합니다.
  Safari 는 구간을 받지 않는 서버의 영상은 아예 틀지 않습니다

사내 화면이 찍힐 수 있다는 사정은 스크린샷과 같습니다. 로그인한 사람에게만 보여야 합니다.

## 결정

**앱마다 동영상 하나를 둡니다. 내줄 때는 서버가 로그인과 볼 권한을 확인한 뒤 잠깐 쓰는
스토리지 presigned 주소로 넘깁니다(302).**

- 스크린샷 5장과 따로 둡니다(`apps.video_key`). 보여줄 때는 스크린샷보다 앞에 둡니다
- MP4·MOV, 60초, 50MB 까지입니다. 서버가 파일 머리(`ftyp`)와 `moov/mvhd` 의 길이를 직접
  읽어 거릅니다 (`VideoInspection`). 서버는 리눅스라 AVFoundation 도 ffmpeg 도 없지만, 두
  값은 상자 몇 개만 따라가면 나옵니다
- 새로 올리면 앞의 것과 바뀝니다. 행을 잠그고 키를 바꾸면서 그 순간의 옛 키를 돌려받아
  지웁니다. 둘이 동시에 올려도 아무도 가리키지 않는 오브젝트가 남지 않습니다
- 올리기는 스크린샷처럼 서버가 본문을 받습니다. 받은 뒤에 길이를 봐야 해서입니다
- `GET /api/v1/apps/:id/video` 가 302 로 넘기고 `Cache-Control: no-store` 를 붙입니다.
  넘김을 기억해 두면 만료된 주소로 갑니다. 출시 전 앱은 손댈 수 있는 사람에게만
  넘깁니다 (ADR-0051)
- 콘솔은 같은 출처라 `<video src>` 가 쿠키를 싣고 넘김을 따라갑니다. CSP 에 `media-src` 로
  스토리지 주소를 엽니다
- 스토어 앱은 넘김을 따라가지 않고 `Location` 만 받아 `AVPlayer` 에 넘깁니다. 토큰은 서버
  주소에만 싣습니다 (ADR-0071 과 같은 출처 규칙)
- 포스터 이미지는 받지 않고 첫 프레임을 씁니다. 스스로 재생하지 않습니다
- 사람 토큰 허용 목록에 `GET`·`PUT`·`DELETE` 를 더하고, MCP 에 `set_video`·`remove_video` 를
  냅니다 (ADR-0077 과 같은 까닭)

## 대안과 기각 사유

**스크린샷처럼 서버가 받아 넘긴다** - 주소가 하나로 끝나고 스토어 앱이 그림과 같은 길로
받습니다. 그러나 볼 때마다 수십 MB 를 서버 메모리에 올리고, 구간 요청을 직접 구현하지
않으면 Safari 에서 재생되지 않으며, 앞뒤로 넘길 때마다 처음부터 받습니다.

**`AppDTO` 에 presigned 주소를 담는다** - 플레이어가 바로 씁니다. ADR-0071 이 스크린샷에서
버린 까닭과 같습니다. 목록을 내려줄 때마다 서명을 만들어야 하고, 노트북을 덮었다 열면
주소가 만료돼 있습니다. 302 로 넘기면 볼 때 만들어서 이 문제가 없습니다.

**스크린샷 목록에 섞는다(동영상도 5장 중 하나)** - 자리 하나를 공유하니 규칙이 하나입니다.
그러나 상한이 다른 두 종류가 한 목록에 들어가 "5장" 이 무엇을 세는지 흐려지고, 동영상이
여럿이면 무엇부터 틀지 정해야 합니다. App Store 도 미리보기를 앞에 따로 둡니다.

**브라우저가 스토리지로 직접 올린다(presigned PUT)** - 서버가 50MB 를 받지 않아도 되고 앞단
프록시의 본문 상한을 걱정하지 않습니다. 그러나 길이를 보려면 서버가 올라간 파일을 다시
받아 읽어야 하고, 거절하면 이미 올라간 오브젝트를 치워야 합니다. 운영 앞단은 120MB 본문도
넘기는 것을 확인했습니다(2026-10-26).

**포스터 이미지를 따로 받는다** - 첫 프레임이 검은 화면인 영상도 보기 좋게 보입니다.
그러나 올릴 것이 하나 더 늘고, 서버는 프레임을 뽑을 수 없어 사람이 따로 만들어야 합니다.

## 결과

**좋은 점**
- 서버는 동영상을 내줄 때 바이트를 만지지 않습니다. 넘김 한 번이 전부입니다
- 앞뒤로 넘기기와 Safari 재생을 스토리지가 맡습니다
- 주소가 새어도 로그인 없이는 넘김을 받지 못합니다

**나쁜 점**
- 넘겨받은 presigned 주소 자체는 만료 전까지(운영 15분) 누구나 엽니다. 스크린샷 주소보다
  약합니다
- 코덱은 보지 않습니다. HEVC 로 녹화한 영상은 맥에서는 재생되지만 일부 브라우저의 콘솔
  화면에서는 재생되지 않을 수 있습니다
- 올릴 때 50MB 를 서버 메모리에 한 번 올립니다
- 스토어 앱은 앱 상세를 열 때마다 넘김 주소를 새로 받습니다. 상세를 오래 열어두면 그 주소가
  만료돼 다시 열어야 앞뒤로 넘길 수 있습니다
- 길이 상한은 반올림해서 봅니다. 60.4초까지는 받습니다

**후속**
- 동영상이 여럿 필요하다는 요청이 오면 그때 목록으로 넓힙니다
