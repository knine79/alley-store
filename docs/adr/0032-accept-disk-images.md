# ADR-0032: dmg 도 받고, 내용을 보고 형식을 가른다

- 상태: 수락됨
- 날짜: 2026-09-09

## 맥락

업로드가 zip 만 받았습니다. 폼의 `accept` 도, 워커의 압축 풀기(`ditto -x -k`)도
그렇습니다. 그런데 **맥 앱 빌드 도구가 뱉는 것은 대개 dmg 입니다.** electron-builder,
create-dmg, Xcode 의 배포 내보내기가 모두 그렇습니다.

그래서 올리는 사람이 매번 이걸 합니다.

1. dmg 를 더블클릭해 마운트한다
2. `.app` 을 어딘가로 복사한다
3. 다시 압축한다
4. 마운트를 뺀다

**없어도 되는 수고입니다.** 게다가 3번에서 Finder 로 압축하면 `__MACOSX` 가 딸려
들어가고, 그건 워커가 걸러내야 하는 또 다른 것입니다.

파일 선택 대화상자에서 dmg 가 회색으로 비활성화되는 것도 문제였습니다. 받지 않는
형식이라는 신호이긴 하지만, 왜 안 되는지는 화면 어디에도 없었습니다.

## 결정

**dmg 를 입력으로 받습니다. 출력은 zip 그대로 둡니다.**

### 형식은 내용을 보고 가릅니다

파일 이름을 믿지 않습니다. 워커가 받는 것은 오브젝트 스토리지의 키일 뿐이고 확장자는
올린 사람이 정합니다. `.zip` 이라고 적힌 dmg 를 받으면 푸는 데 실패하고, 그 실패는
"압축이 깨졌다" 로 보고됩니다. 올린 사람은 자기 파일이 멀쩡한 것을 알고 있어서 원인을
찾지 못합니다.

`ArtifactFormat` 이 앞뒤 몇 바이트로 가릅니다.

| 형식 | 판정 |
| --- | --- |
| zip | 앞 4바이트가 `PK\x03\x04` |
| dmg (UDIF) | 파일 **끝** 512바이트가 트레일러이고 그 앞 4바이트가 `koly` |

dmg 는 앞머리가 압축 방식마다 달라서 뒤를 봐야 합니다.

### 마운트는 우리가 정한 자리에만 붙입니다

신뢰할 수 없는 디스크 이미지를 붙이는 자리입니다.

- `-readonly` — 이미지 자체가 바뀌지 않게
- `-nobrowse` — Finder 에 뜨지 않게. 워커 맥에는 사람이 로그인해 있습니다
- `-noautoopen` — 이미지 안의 것이 저절로 열리지 않게
- `-mountpoint <작업 디렉터리>/mnt` — `/Volumes` 에 붙이지 않습니다. 이름이 겹칠 때
  남의 볼륨을 건드릴 수 있고, 잡이 여럿이면 서로 밟습니다

붙인 것은 성공하든 실패하든 뗍니다. `defer` 는 async 를 기다리지 못해서 쓸 수
없습니다. 떼기 전에 작업 디렉터리가 지워지면 마운트가 워커 맥에 남고, 쌓이면 다음
잡의 마운트도 실패하기 시작합니다.

떼기가 실패해도 던지지 않습니다. 던지면 원래 실패 원인이 "떼지 못했습니다" 로
덮입니다. 대신 잡 로그에 남겨 사람이 알아챌 수 있게 합니다.

### 출력은 zip 입니다

서명·공증을 마친 결과물은 지금처럼 zip 으로 냅니다. 스토어 앱이 그것을 자동으로
설치하는데, zip 은 `ditto -x -k` 한 줄이고 dmg 는 마운트·복사·떼기 세 단계입니다.
떼기가 실패하면 사용자 맥에 마운트가 남습니다.

서명 뒤에 dmg 를 다시 만드는 것도 답이 아닙니다. 그건 **올린 사람이 만든 dmg 가
아닙니다.** 배경 이미지도 아이콘 배치도 사라집니다. 그럴 거면 zip 이 낫습니다.

## 대안과 기각 사유

**dmg 를 그대로 배포한다** — 올린 것과 받는 것이 같아서 이해하기 쉽고, Sparkle 도
dmg 를 지원합니다. 그러나 스토어 앱의 설치 경로가 통째로 바뀝니다. 지금은 받아서
`ditto` 로 풀면 끝인데, 마운트를 붙이고 떼는 코드가 사용자 맥에서 돌게 됩니다.
떼기 실패는 사용자에게 보이는 고장입니다. 얻는 것에 비해 대가가 큽니다.

**서버가 dmg 를 zip 으로 바꿔준다** — 워커를 건드리지 않아도 되고 형식이 한 가지로
통일됩니다. 그러나 서버가 아티팩트를 열게 됩니다. [ADR-0009](0009-presigned-artifact-transfer.md)
와 [ADR-0029](0029-verify-bundle-identifier-before-signing.md) 에서 두 번 기각한
구조입니다. 게다가 서버는 리눅스 컨테이너라 `hdiutil` 이 없습니다. **애초에 불가능합니다.**

**확장자로 가른다** — 훨씬 간단합니다. 그러나 위에 적은 대로 확장자는 올린 사람이
정하는 값이고, 틀렸을 때 나오는 오류가 원인을 가립니다. 앞뒤 4바이트를 읽는 비용은
없는 것과 같습니다.

**CLI 로만 dmg 를 받는다** — CLI 가 로컬에서 풀어 zip 으로 올리면 서버도 워커도
그대로입니다. 그러나 브라우저로 올리는 사람에게는 아무 도움이 안 됩니다. 화면에서
올리는 것이 기본 경로입니다.

## 결과

**좋은 점**

- 빌드 도구가 뱉은 dmg 를 그대로 올립니다. 마운트해서 꺼내 다시 압축하지 않습니다
- 확장자가 틀려도 제대로 처리합니다. `.zip` 이라고 적힌 dmg 도, 그 반대도 됩니다
- 실패해도 마운트가 남지 않습니다. 성공 경로와 실패 경로 모두 확인했습니다

**나쁜 점**

- **dmg 는 자동 채우기가 안 됩니다.** 브라우저가 APFS·HFS+ 디스크 이미지를 열 방법이
  없습니다([ADR-0030](0030-read-bundle-info-in-browser.md)). zip 으로 올리면 다섯 칸이
  채워지고 dmg 면 직접 적어야 합니다. **같은 화면에서 고른 파일에 따라 동작이
  달라집니다.** 화면에 그렇게 적어뒀지만 어색한 것은 그대로입니다
- **워커가 신뢰할 수 없는 디스크 이미지를 마운트합니다.** 플래그로 좁혔지만
  `hdiutil` 이 파싱하는 형식 자체의 취약점까지 막지는 못합니다. zip 을 푸는 것보다
  넓은 공격면입니다
- **암호가 걸렸거나 사용권 동의(SLA)를 요구하는 dmg 는 받지 못합니다.** 사람이
  눌러줘야 붙는데 워커에는 눌러줄 사람이 없습니다. 실패 메시지로 zip 을 안내합니다
- 판정 코드가 두 곳에 생겼습니다. 워커의 `ArtifactFormat` 과 브라우저의
  `looksLikeDiskImage` 입니다. 쓰임이 달라서(하나는 푸는 방법을 정하고, 하나는 왜
  자동 채우기가 안 되는지 설명한다) 합치지 않았지만, `koly` 라는 같은 사실을 두 곳이
  알고 있습니다
