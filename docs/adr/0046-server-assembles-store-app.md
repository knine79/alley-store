# ADR-0046: 스토어 앱 번들은 서버가 조립하고 워커가 서명한다

- 상태: 수락됨
- 날짜: 2026-09-15

## 맥락

스토어 앱은 조직마다 이름과 번들 ID, URL 스킴, 아이콘이 다릅니다. 그 값들은
지금까지 운영 레포의 셸 환경변수에만 있었습니다
([ADR-0043](0043-product-and-operations-repositories.md)).

```bash
ALLEY_STORE_APP_BUNDLE_ID="com.example.alley.store"
ALLEY_STORE_APP_NAME="우리 앱 스토어"
```

이 구조에 세 가지가 걸립니다.

**하나. 바꾸려면 맥 앞에 앉아야 합니다.** 이름을 고치는 것은 설정 한 줄인데 절차는
"운영 레포를 고치고 → 서명 맥의 러너가 돌고 → 빌드·서명·공증" 입니다. 아이콘을 바꾸는
것도 같습니다.

**둘. 서버는 어느 앱이 스토어 앱인지 모릅니다.** 그래서 웹 콘솔에서 스토어 앱을 받을
길이 없었습니다(이슈 #17). 스토어 앱이 없는 사람은 스토어 앱을 받을 방법이 없는데,
그것이 바로 스토어 앱이 필요한 사람입니다.

**셋. 빌드 번호를 정하는 곳이 둘이었습니다.** 번들의 `CFBundleVersion` 은 셸이,
스토어의 빌드 번호는 CLI 가 각각 정했습니다. 그래서 두 번째 릴리스부터 설치된 앱이
자기를 최신이라고 말했습니다(이슈 #18).

한편 **바꿔야 할 것은 전부 파일 몇 개입니다.** 이름은 zip 항목의 경로이고,
`Info.plist` 는 새로 쓰면 되고, `.icns` 는 PNG 를 담는 그릇입니다
([ADR-0045](0045-branding-assets-in-storage.md)). 컴파일도 그림 변환도 필요 없습니다.

## 결정

**서버가 번들을 조립하고, 기존 서명 워커가 서명합니다.**

```
[CI] 브랜딩 없는 미서명 번들 zip
         ↓ (운영 CI 가 올린다. 관리자가 손으로 올릴 수도 있다)
관리 > 스토어 앱: 이름·번들 ID·스킴·아이콘
         ↓
서버: Info.plist 새로 쓰기 + AppIcon.icns 넣기 + 이름 갈아끼우기
         ↓
버전 하나로 등록 → 서명 잡
         ↓
기존 워커: codesign → notarize → staple
         ↓
ready → 관리자가 출시
```

- 압축을 풀지 않습니다. 손댈 파일은 `Info.plist` 와 아이콘뿐이고, 나머지는
  **압축된 바이트 그대로** 옮깁니다
- 임시 서명(`_CodeSignature`)은 버립니다. 맥이 끼워 넣는 `._*` 와 `__MACOSX/` 도 버립니다
- 빌드 번호는 서버가 정해 번들과 스토어 양쪽에 **같은 값**을 씁니다
- 붙을 스토어 주소는 서버가 자기 `PUBLIC_BASE_URL` 을 넣습니다
  ([ADR-0044](0044-store-app-knows-its-server.md) 가 운영 레포에 손으로 적게 하던 값입니다)
- 번들 ID 와 URL 스킴은 한 번이라도 내보낸 뒤에는 화면에서 잠급니다
- 스토어 앱의 앱 레코드는 첫 빌드 때 서버가 만듭니다. 그것이 곧 "어느 앱이 스토어
  앱인가" 의 답이고, 이슈 #17 의 받기 링크가 그것을 씁니다
- **운영 CI 도 같은 일을 할 수 있습니다.** 화면이 부르는 것과 같은 동작을
  `/api/v1/ops/store-app/{base-bundle,build}` 로도 부릅니다. 인증은 워커 릴리스가
  이미 쓰는 `ALLEY_OPERATOR_TOKEN` 이라 새 자격 증명이 없습니다. 같은 버전을 두 번
  빌드하지 않도록 `GET /api/v1/ops/store-app` 으로 먼저 확인합니다

### 왜 워커가 아니라 서버가 조립하나

워커는 macOS 라 `ditto` 로 풀고 다시 싸면 됩니다. 코드는 훨씬 적습니다.

그러나 **워커를 바꾸면 워커를 먼저 배포해야 합니다.** 워커 자동 업데이트
([ADR-0042](0042-worker-self-update.md))는 아직 배포 서버 상대로 돌려본 적이 없고,
새 기능이 그 미검증 경로에 의존하게 됩니다. 서버는 컨테이너 이미지라 굴리기만 하면
됩니다.

그리고 [ADR-0022](0022-worker-as-signed-app-bundle.md) 가 정한 "워커 맥에는 소스도
툴체인도 없다" 를 그대로 지킵니다. 워커는 이것이 스토어 앱인지 모르고, 알 필요도
없습니다.

### 왜 실행 파일 이름을 따로 만드나

**실행 파일 이름에 비ASCII 문자가 있으면 `codesign --verify --deep --strict` 가 그
번들을 거절합니다.** `.app` 폴더 이름은 한글이어도 괜찮고 실행 파일만 그렇습니다.

| 폴더 | 실행 파일 | `--verify --deep --strict` |
| --- | --- | --- |
| `Our Store.app` | `Our Store` | 통과 |
| `우리스토어.app` | `AlleyStore` | 통과 |
| `AlleyStore.app` | `우리스토어` | **실패** |

실패 문구는 `a sealed resource is missing or invalid` 한 줄이고, **서명이 끝난 뒤에야
나옵니다.** 이름이 원인이라는 것은 짐작할 수 없습니다. 설치 가이드가
`ALLEY_STORE_APP_NAME="우리 앱 스토어"` 를 예시로 들고 있어서 그 길을 그대로 밟는
조직이 나옵니다.

그래서 화면에 보이는 이름(`.app` 폴더, `CFBundleName`, `CFBundleDisplayName`)과 실행
파일 이름을 나눕니다. ASCII 이름은 그대로 두고, 비ASCII 가 섞였을 때만 ASCII 글자와
숫자만 남기며, 남는 것이 없으면 `AlleyStore` 를 씁니다. `Contents/MacOS/` 안을
들여다보는 사람은 없습니다.

조립 스크립트(`scripts/build-store-app.sh`)도 같은 규칙을 씁니다.

## 대안과 기각 사유

**워커가 소스부터 빌드한다** — 사람이 바이너리를 올릴 일이 없어 가장 자동입니다.
그러나 워커 맥에 Swift 툴체인과 소스가 필요해져 ADR-0022 를 뒤집습니다. 서명 키를 둔
머신에 빌드 환경까지 두는 것은 그 머신이 지켜야 할 것을 늘리는 일입니다.

**관리 화면은 설정만 보관하고 빌드는 사람이 맥에서 한다** — 새로 만들 코드가 제일
적습니다. 설정 파일과 명령 한 줄을 내려주고, 결과 zip 을 올리면 나머지는 자동입니다.
그러나 **아이콘을 바꿀 때마다 맥 앞에 앉아야 하는 것은 그대로**입니다. 이 변경이
없애려던 것이 정확히 그것입니다.

**서버가 zip 을 풀고 다시 압축한다** — 다루는 코드가 평범해집니다. 그러나 리눅스
컨테이너의 Swift 에서 deflate 를 쓰려면 zlib 바인딩을 들여야 하고, 수십 MB 짜리
실행 파일을 풀었다 다시 압축하는 비용을 매번 냅니다. 바꿀 것은 두 파일뿐입니다.

**조직 값을 서버 환경변수에 둔다 (이슈 #17 제안)** — ADR-0011 이 그은 경계와 일관되고,
재배포가 필요해서 실수로 바뀌지 않습니다. 그러나 서버가 번들을 빌드하게 되면 **서버가
원천이고 빌드가 그것을 따라가므로** "서버 혼자 바꾸면 이미 깔린 앱이 깨진다" 는 걱정이
성립하지 않습니다. 대신 다른 종류의 위험(번들 ID 를 바꾸면 별개 앱이 된다)이 생겨서
잠금과 확인으로 다룹니다.

**모든 앱에 웹 다운로드를 연다** — 규칙이 하나라 설명할 것이 없습니다. 그러나 스토어
앱이 하는 검증 중 "이미 깔린 같은 앱과 서명한 팀이 같은가" 는 로컬에 무엇이 깔렸는지
알아야만 판단할 수 있어서 브라우저에서는 재현할 수 없습니다. 웹 다운로드가 기본
경로가 되면 그 판단을 건너뛰는 문이 됩니다. 스토어 앱 자신과, 올릴 권한이 있는
사람에게만 엽니다.

## 결과

**좋은 점**

- 아이콘과 이름을 화면에서 바꾸고 버튼 하나로 내보냅니다
- 빌드 번호를 정하는 곳이 하나가 되어 이슈 #18 이 구조적으로 사라집니다
- 서버가 어느 앱이 스토어 앱인지 알게 되어 이슈 #17 의 받기 링크가 가능해집니다
- 붙을 주소를 사람이 두 번 적지 않습니다 (ADR-0044 의 나쁜 점이 버튼 하나가 됩니다)
- 워커는 손대지 않았습니다. 이미 배포된 워커가 그대로 처리합니다
- **스토어 앱 전용 배포 토큰이 필요 없어졌습니다.** 서버가 자기 데이터베이스에 직접
  버전을 만들므로 앱 배포 API 를 거치지 않습니다. 운영 레포의
  `ALLEY_STORE_APP_TOKEN` 을 뺐고, CI 가 쓰는 자격 증명은 워커 릴리스가 이미 갖고
  있던 `ALLEY_OPERATOR_TOKEN` 하나로 줄었습니다
- **자동 릴리스가 그대로입니다.** 운영 CI 가 도는 것만으로 스토어 앱이 새 코드로
  갱신됩니다. 사람은 출시 버튼만 누릅니다

**나쁜 점**

- **서버가 zip 을 쓰는 코드를 갖게 됐습니다.** 300줄 남짓의 바이트 다루기이고, 틀리면
  "번들이 깨져서 서명이 실패한다" 로 나타납니다. 진짜 `ditto` 가 싼 것을 다시 써서
  `unzip -t`·`plutil`·`iconutil`·`codesign` 으로 검사하는 시험을 두었지만, 그것이
  모든 형식을 덮지는 않습니다
- **zip64 를 다루지 않습니다.** 4GB 를 넘거나 항목이 65535개를 넘으면 읽기를 포기합니다.
  스토어 앱은 2MB 남짓이라 지금은 문제가 없습니다
- **`Info.plist` 를 만드는 코드가 두 벌입니다.** 조립 스크립트는 셸이라 서버 코드를
  부를 수 없습니다. 둘이 갈라지면 어느 경로로 빌드했느냐에 따라 번들이 달라지고,
  그 차이는 조용합니다
- 앱 아이콘 크기가 512·1024 로 좁습니다 ([ADR-0045](0045-branding-assets-in-storage.md))
- **운영 토큰이 하는 일이 늘었습니다.** 워커 릴리스만 다루던 자격 증명이 이제 스토어
  앱 번들을 올리고 빌드까지 시킵니다. 이 토큰이 새면 조직 구성원이 설치하는 앱에
  공격자가 고른 번들이 들어갑니다. 서명 워커가 Developer ID 로 서명하기 전에
  사람이 출시를 눌러야 한다는 것이 지금의 마지막 방어선입니다
- **CI 가 같은 버전을 다시 빌드하지 않도록 상태를 먼저 조회합니다.** 그 판정은 제품
  버전 문자열 비교라, 같은 버전 태그로 내용이 다른 번들을 내보내면 CI 가 건너뜁니다.
  그때는 관리 화면에서 손으로 올려야 합니다
- **베이스 번들이 낡아도 조용합니다.** CI 를 돌리지 않으면 옛 코드로 계속 빌드됩니다.
  화면에 그 번들의 제품 버전을 적어두는 것이 지금의 대비책입니다
