# ADR-0001: Swift 풀스택 모노레포로 간다

- 상태: 수락됨
- 날짜: 2026-08-12

## 맥락

서버, 서명 워커, 스토어 앱 세 계층을 만들어야 합니다. 워커는 `codesign`과
`notarytool`을 호출해야 하므로 macOS 전용이고, 스토어 앱은 SwiftUI입니다. 서버
언어만 열려 있는 상태였습니다.

세 계층은 같은 API를 주고받습니다. 각자 DTO를 따로 정의하면 필드 이름 하나만
어긋나도 런타임에 가서야 드러납니다.

## 결정

서버도 Swift로 씁니다. Vapor를 웹 프레임워크로 쓰고, 세 계층을 한 레포에 둡니다.
DTO와 API 경로는 `AlleyShared` 타겟에 모으고 서버·워커·앱이 모두 임포트합니다.

`AlleyShared`는 Vapor를 포함해 어떤 외부 프레임워크에도 의존하지 않습니다.
SwiftUI 앱이 그대로 임포트해야 하기 때문입니다. HTTP 직렬화 능력(`Content` 준수)은
서버 타겟에서 확장으로 덧붙입니다.

## 대안과 기각 사유

**TypeScript 서버 (NestJS 등)** — 웹 생태계가 풍부하고 프론트엔드·백엔드 개발자
기여를 받기 쉽습니다. 다만 DTO를 두 언어로 각각 정의해야 하고, 이 프로젝트를
주로 유지보수할 사람이 Apple 플랫폼 개발자라 컨텍스트 스위칭 비용이 생깁니다.

**Go 서버** — 단일 바이너리 배포가 가벼워 셀프호스팅에 잘 맞습니다. 다만 팀 내
경험치가 변수이고, DTO 이중 정의 문제는 TypeScript와 같습니다.

**레포 분리** — 서버/워커/앱을 각각 레포로 두면 배포 주기를 독립적으로 가져갈 수
있습니다. 그러나 DTO를 공유하려면 별도 패키지를 만들고 버전을 맞춰야 해서, 얻는
독립성보다 관리 비용이 큽니다. 규모가 커지면 그때 분리합니다.

## 결과

**좋은 점**
- API 스펙 불일치가 컴파일 단계에서 잡힙니다
- 한 팀이 전 계층을 유지보수할 수 있습니다
- 워커와 앱이 어차피 Swift라 언어가 하나로 통일됩니다

**나쁜 점**
- Vapor 생태계는 Node나 Go보다 작습니다. 없는 라이브러리는 직접 만들거나 REST를
  직접 호출해야 할 수 있습니다 (App Store Connect API가 그런 경우)
- 오픈소스 기여자 풀이 "서버를 아는 Swift 개발자"로 좁아집니다
- 서버 이미지 빌드가 느립니다. CI에서 `.build` 캐싱이 필수입니다

**후속**
- 웹 콘솔은 Vapor + Leaf 서버 렌더링으로 시작합니다. 화면이 복잡해지면 그때 SPA를
  검토합니다 (통계·피드백 대시보드 단계)
