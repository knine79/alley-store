# ADR-0008: 세션 토큰은 신원만 담고 권한은 매번 조회한다

- 상태: 수락됨
- 날짜: 2026-08-14

## 맥락

로그인이 끝나면 사용자에게 세션 토큰을 발급합니다. 이 토큰이 무엇을 담을지,
스토어 앱에는 어떻게 전달할지 정해야 했습니다.

앱과 웹 콘솔이 같은 인증 경로를 씁니다(ADR-0007 관련). 앱은
`ASWebAuthenticationSession`으로 서버의 로그인 주소를 열고, 인증이 끝나면
커스텀 URL 스킴으로 돌아옵니다.

## 결정

### 1. 토큰에 역할을 담지 않는다

세션 JWT는 사용자 ID(`sub`)와 만료(`exp`)만 담습니다. 역할(`admin`/`developer`/`user`)은
요청마다 데이터베이스에서 읽습니다.

### 2. 앱에는 일회용 코드를 주고 토큰은 따로 교환한다

콜백에서 커스텀 스킴으로 돌려보낼 때 세션 토큰을 URL에 싣지 않습니다. 대신 수명
2분짜리 일회용 코드를 싣고, 앱이 `POST /api/v1/auth/token`으로 교환합니다.
코드는 평문이 아니라 SHA-256 해시로 저장하고, 교환 시점에 소진 처리합니다.

### 3. ID 토큰은 서명까지 검증한다

Google의 공개키(JWKS)로 서명을 확인하고 `aud`가 우리 클라이언트인지 봅니다.
도메인 판단은 `email` + `hd` + `email_verified`를 함께 보고 서버에서만 합니다.

### 4. OAuth `state`는 서명된 단명 토큰으로 만든다

CSRF 방어와 "인증 후 어디로 돌아갈지"(웹/앱)를 한 값에 담아 서명합니다.
수명은 10분입니다.

## 대안과 기각 사유

**세션 토큰에 역할을 담는다** — 요청마다 조회가 없어 빠르고, 이것이 JWT를 쓰는
일반적인 이유입니다. 그러나 관리자에서 강등된 사용자가 **토큰 만료까지 관리자로
남습니다.** 세션 수명이 7일이라 무시할 수 없습니다. 조회 한 번은 인덱스가 걸린
기본키 조회이고, 이 규모에서 병목이 될 일이 없습니다. 정확성을 택했습니다.

**서버에 세션을 저장한다(stateless 포기)** — 로그아웃과 강제 만료가 즉시 됩니다.
그러나 세션 저장소를 운영해야 하고, 우리가 실제로 원한 것은 "권한 변경 즉시 반영"
뿐이었습니다. 그건 위 방식으로 이미 해결됩니다. 토큰 강제 무효화가 필요해지면
그때 도입합니다.

**세션 토큰을 커스텀 스킴 URL에 직접 싣는다** — 교환 단계가 없어 단순합니다.
그러나 URL은 시스템 로그, 브라우저 기록, 다른 앱의 URL 핸들러에 남을 수 있습니다.
7일짜리 토큰이 그런 곳에 남는 것과 2분짜리 일회용 코드가 남는 것은 다릅니다.

**ID 토큰 서명 검증을 생략한다** — 토큰을 Google 토큰 엔드포인트에서 TLS로 직접
받으므로 Google 문서도 생략을 허용합니다. 그러나 사용하는 라이브러리에 JWKS 검증이
들어 있어 비용이 사실상 없고, 나중에 토큰이 덜 신뢰되는 경로로 들어오게 바뀌어도
안전합니다.

**`state`를 데이터베이스에 저장한다** — 재사용을 확실히 막을 수 있습니다. 그러나
로그인 왕복마다 쓰기가 생기고, 만료된 행을 청소해야 합니다. 서명 + 짧은 수명으로
위조를 막는 것으로 충분하다고 봤습니다.

## 결과

**좋은 점**
- 권한 변경이 다음 요청부터 반영됩니다
- 앱 전달 경로에 장수명 토큰이 노출되지 않습니다
- 데이터베이스가 통째로 새도 교환 코드는 쓸 수 없습니다(해시 저장)
- 앱 바이너리에 Google 클라이언트 정보가 들어가지 않습니다

**나쁜 점**
- 인증된 요청마다 사용자 조회가 한 번 더 일어납니다
- 발급된 세션 토큰을 만료 전에 강제로 끊을 수 없습니다. 계정을 삭제하면
  조회가 실패해 사실상 차단되지만, "이 토큰만 무효화"는 안 됩니다
- `state`를 탈취당하면 만료 전까지 재사용할 수 있습니다. 수명 10분으로 창을 좁혔습니다
- 로그인 경로가 두 갈래(웹 쿠키 / 앱 코드 교환)라 테스트할 것이 늘어납니다

**후속**
- 만료된 `auth_codes` 행을 주기적으로 지우는 작업이 필요합니다. 지금은 쌓이기만 합니다
- 토큰 강제 무효화가 필요해지면 토큰에 발급 세대(generation)를 넣고 사용자 행과
  대조하는 방식으로 확장할 수 있습니다
