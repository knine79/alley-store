# ADR-0038: 컨테이너 자격증명 공급자를 직접 붙인다

- 상태: 수락됨
- 날짜: 2026-09-10

## 맥락

배포된 서버에서 dmg 를 올리자 앱은 만들어지고 업로드는 시작도 못 했습니다. 로그는
한 줄이었습니다.

```
[ WARNING ] 스토리지 자격증명을 찾지 못했습니다. S3_ACCESS_KEY_ID 와 ...
```

파드에는 액세스 키가 없습니다. 대신 이 둘이 주입돼 있습니다.

```
AWS_CONTAINER_CREDENTIALS_FULL_URI=http://169.254.170.23/v1/credentials
AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE=/var/run/secrets/.../eks-pod-identity-token
```

EKS Pod Identity 입니다. 그 주소에 토큰을 붙여 물어보면 15분짜리 임시 키가 나옵니다.
플랫폼 문서는 "AWS SDK 의 기본 credential chain 이 그대로 집어간다" 고 말하고,
Node·Python·Go·Java SDK 는 실제로 그렇습니다.

**Soto 는 아닙니다.** `soto-core` 7.14 의 컨테이너 자격증명 코드는
`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`(옛 ECS 방식) 하나만 봅니다. `FULL_URI` 는
문자열조차 없습니다. 그래서 기본 체인이 전부 헛돌고 `noProvider` 로 끝납니다.

플랫폼은 액세스 키를 발급하지 않습니다. 문서에 그렇게 적혀 있습니다 - "원시 AWS
액세스 키를 발급받는 경로는 없습니다."

## 결정

`PodIdentityCredentialProvider` 를 만들어 자격증명 체인 **앞**에 놓습니다.

```
.selector(.podIdentity, .default)
```

환경변수가 없거나 주소를 믿을 수 없으면 `podIdentity` 는 조용히 비켜서고 기본 체인이
이어받습니다. 로컬 개발은 지금처럼 `S3_ACCESS_KEY_ID` 로 돌아갑니다.

만료는 Soto 의 `RotatingCredentialProvider` 에 맡깁니다. 우리가 만든 것은 "한 번
받아오는 방법" 뿐이고, 언제 다시 받을지는 이미 있는 것이 정합니다.

### 주소를 가립니다

**이것이 이 결정에서 가장 조심한 부분입니다.**

토큰은 그 자체로 우리 IAM 역할을 빌릴 수 있는 열쇠입니다. 환경변수 하나만 바꾸면
그 토큰이 임의의 호스트로 나가고, 받은 쪽은 우리 이름으로 버킷에 접근합니다.

AWS SDK 들이 쓰는 규칙을 그대로 따릅니다. **루프백이거나, 자격증명 전용 링크로컬
주소이거나, `https` 여야 합니다.** 아니면 공급자를 아예 만들지 않습니다.

`169.254.169.254`(EC2 인스턴스 메타데이터)는 일부러 뺐습니다. 자격증명 엔드포인트가
아니고, 거기에 토큰을 보낼 이유가 없습니다.

### 토큰은 부를 때마다 다시 읽습니다

kubelet 이 그 파일을 갈아 끼웁니다. 한 번 읽어 들고 있으면 갱신 시점에 401 이 나고,
그때는 자격증명 만료와 겹쳐서 무엇이 원인인지 알기 어렵습니다. 파일 읽기 한 번이
훨씬 쌉니다.

## 대안과 기각 사유

**액세스 키를 발급받아 시크릿에 넣는다** — 코드가 한 줄도 안 늘고 이미 지원되는
경로입니다. 그러나 플랫폼이 발급하지 않습니다. 발급된다 해도 만료 없는 장기 키를
시크릿에 두는 것은 지금 구조보다 나쁩니다.

**Soto 에 고쳐 올린다** — 옳은 방향이고 다른 사용자도 같은 벽에 부딪힙니다.
그러나 머지되고 릴리스될 때까지 우리 서버는 파일을 하나도 못 올립니다. **이건
나중에 따로 할 일이고, 지금 막힌 것을 대신하지 못합니다.**

**AWS SDK for Swift 로 갈아탄다** — Pod Identity 를 지원합니다. 그러나 S3 클라이언트,
presigned URL 생성, 수명주기 관리가 전부 Soto 에 맞춰져 있습니다. 자격증명 하나
때문에 스토리지 계층을 통째로 바꾸는 것은 맞바꿈이 나쁩니다.

**서버가 바이너리를 대신 받아준다** — 자격증명 문제를 우회하는 것이 아니라 더
키웁니다. 어차피 S3 에 쓰려면 자격증명이 필요하고,
[ADR-0009](0009-presigned-artifact-transfer.md) 가 기각한 방식으로 돌아가는 일입니다.

## 결과

**좋은 점**

- 액세스 키 없이 배포된 채로 스토리지를 씁니다. 시크릿에 장기 키가 없습니다
- 만료·갱신은 Soto 가 하던 대로 합니다. 우리가 더한 것은 요청 하나입니다
- 없는 환경에서는 저절로 비켜섭니다. 로컬 개발과 다른 배포 형태가 그대로 돕니다
- 토큰이 나갈 수 있는 주소를 좁혔습니다

**나쁜 점**

- **AWS 자격증명 코드를 우리가 들고 있습니다.** SDK 가 할 일이고, 응답 형식이나
  엔드포인트 규약이 바뀌면 우리가 따라가야 합니다. 그 변경은 조용히 오고, 알게
  되는 시점은 파일이 안 올라갈 때입니다
- **실제 엔드포인트로는 검증하지 못했습니다.** 테스트는 가짜 HTTP 클라이언트로
  합니다. 링크로컬 주소는 파드 안에서만 존재해서, 진짜 확인은 배포해서 올려보는
  것뿐입니다
- Soto 가 나중에 이 방식을 지원하면 우리 코드가 중복이 됩니다. 그때 지워야 하는데,
  지울 이유를 아는 사람이 없으면 그대로 남습니다
- 자격증명 체인이 한 겹 길어졌습니다. 무엇으로 인증됐는지 알려면 로그를 봐야 합니다
- **기동할 때 한 번 고르고 그 선택을 계속 씁니다.** Soto 의 선택기가 원래 그렇습니다.
  하필 기동 순간에 엔드포인트가 응답하지 않으면 그 파드는 재시작 전까지 스토리지를
  못 씁니다. `.default` 도 같은 구조라 새로 생긴 위험은 아니지만, 이제 기동이
  링크로컬 주소 하나에 더 매달립니다
