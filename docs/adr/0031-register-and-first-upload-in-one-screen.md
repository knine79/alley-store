# ADR-0031: 앱 등록과 첫 버전 업로드를 한 화면에서 한다

- 상태: 수락됨
- 날짜: 2026-09-09

## 맥락

앱을 처음 올리는 사람은 화면 둘을 거쳤습니다.

```
새 앱 등록          새 버전
(파일 없음)   ──▶   (zip 여기서)
```

등록 화면에는 파일 칸이 없습니다. 번들 ID 와 이름을 손으로 적어 등록하고, 앱 상세로
간 뒤 "새 버전" 을 눌러 다시 파일을 고릅니다. 자동 채우기를 넣은 뒤로는 더 어색해졌습니다
([ADR-0030](0030-read-bundle-info-in-browser.md)). 등록 화면에서 값을 읽으려고 zip 을
고르는데 **그 파일은 올라가지 않고**, 다음 화면에서 같은 파일을 또 골라야 했습니다.

나눠둔 데는 이유가 있습니다. 앱은 오래 사는 신원이고 버전은 그 밑에서 일어나는
사건입니다. 권한도 다릅니다. 앱 등록은 역할(`canPublish`)로 정해지지만, 버전 업로드는
그 앱의 오너·멤버인지를 한 번 더 봅니다(`AppAccess.requireUploadAccess`). 등록이
먼저여야 "누가 이 앱에 올릴 수 있는가" 가 정해집니다.

그러나 **처음 등록하는 사람은 언제나 그 앱의 오너입니다.** 그 순간만큼은 두 권한이
같은 사람에게 있습니다. 나눠서 얻는 것이 없습니다.

## 결정

등록 화면에서 zip 을 고르면 **등록과 첫 버전 업로드를 이어서** 합니다.

```
1. POST /api/v1/apps                    앱을 만든다
2. POST /api/v1/apps/:id/versions       버전을 만들고 올릴 자리를 받는다
3. PUT  <presigned URL>                 스토리지에 직접 올린다
4. POST /api/v1/versions/:id/complete   다 올렸다고 알린다
```

2번부터는 버전 업로드 화면이 하던 것과 같습니다([ADR-0012](0012-browser-upload-script.md)).
앞에 1번이 붙었을 뿐입니다.

### 파일은 선택입니다

고르지 않으면 폼이 그대로 `POST` 되어 앱만 등록됩니다. 스크립트가 없을 때와 같은
동작입니다. 번들 ID 를 미리 잡아두거나, 빌드가 나오기 전에 멤버를 정해두는 경로가
그대로 남습니다.

"첫 버전" 칸은 파일을 골랐을 때만 나타납니다. 안 고른 사람에게 채울 수 없는 칸을
보여줄 이유가 없습니다.

### 앱을 먼저 만듭니다

순서를 뒤집지 않습니다. 앱 생성은 싸고, 번들 ID 중복과 프리픽스 검사가 거기서
걸립니다. 업로드가 먼저면 수백 MB 를 다 올린 뒤에 "그 번들 ID 는 이미 있습니다" 를
만납니다.

### 중간에 실패하면 앱은 남습니다

앱이 만들어지고 업로드가 실패하면 **되돌리지 않습니다.** 그 상태는 파일 없이 등록만
한 것과 같고, 앱 화면에서 버전을 다시 올리면 됩니다. 화면이 그렇게 안내합니다.

    스토리지에 연결하지 못했습니다. 네트워크를 확인하세요.

    앱은 등록됐습니다. 파일만 올라가지 않았으니 앱 화면에서 새 버전으로
    다시 올리세요: /apps/<id>

이 문장이 없으면 사용자는 처음부터 다시 하려다 자기가 방금 만든 앱의 번들 ID 중복에
막히고, 왜 막히는지 알 수 없습니다.

## 대안과 기각 사유

**서버가 한 요청으로 둘 다 처리한다** — 화면도 단순해지고 실패했을 때 되돌리기도
쉽습니다. 트랜잭션 하나로 묶을 수 있습니다. 그러나 바이너리가 서버를 거치게 됩니다.
그건 [ADR-0009](0009-presigned-artifact-transfer.md) 에서 이미 기각한 구조이고,
수백 MB 가 서버 메모리와 대역폭을 왕복합니다. 진행률도 사라집니다.

**실패하면 앱을 지운다** — "등록이 안 된 것처럼" 되돌리면 다시 시도하기 쉽습니다.
그러나 지우는 것도 실패할 수 있고, 그때는 "앱을 지웠다고 했는데 남아 있는" 상태가
됩니다. 되돌릴 수 없는 것을 되돌리려 드는 쪽이 더 나쁜 상태를 만듭니다. 게다가 앱이
남는 것은 사고가 아니라 **원래 있던 상태**(파일 없이 등록만 한 것)입니다.

**중복이면 이어서 올린다** — 앱 생성이 409 로 막혔을 때 그 앱의 오너가 나이고 버전이
하나도 없으면 업로드만 이어서 하는 방법입니다. 재시도가 매끄러워집니다. 그러나 조건이
셋이나 붙는 숨은 동작이고, 남의 앱이나 이미 버전이 있는 앱에서 어떻게 되는지를 매번
따져봐야 합니다. 지금은 실패 문구로 사람이 판단하게 둡니다.

**두 화면을 그대로 둔다** — 아무것도 안 만들면 됩니다. 그러나 자동 채우기를 넣은
뒤로 "올라가지도 않는 파일을 고른다" 는 어색함이 남았고, 그것을 설명으로 덮고
있었습니다.

## 결과

**좋은 점**

- 앱 하나를 처음 올리는 데 화면 하나면 됩니다. 같은 파일을 두 번 고르지 않습니다
- 자동 채우기가 다섯 칸으로 늘었습니다. 번들 ID·이름·버전·빌드 번호·최소 macOS 를
  번들이 말하는 그대로 넣습니다. 사람이 적는 것은 소개와 분류뿐입니다
- 파일을 안 고르는 경로가 그대로 남아, 번들 ID 를 미리 잡아두는 쓰임이 살아 있습니다
- 스크립트가 없어도 등록은 됩니다

**나쁜 점**

- **등록 화면이 스크립트 없이는 반쪽입니다.** 등록은 되지만 첫 버전은 못 올립니다.
  ADR-0030 에서 "없어도 되는 곳" 으로 분류한 화면인데, 이제 그 화면에서 할 수 있는
  일이 스크립트 유무에 따라 달라집니다. 경계가 흐려졌습니다
- **업로드 코드가 두 벌이 됐습니다.** `upload.js` 와 `app-new.js` 가 같은 세 단계와
  같은 진행률 처리를 각자 갖고 있습니다. 한쪽을 고치면 다른 쪽도 봐야 합니다.
  합치려면 공통 모듈이 필요한데, 빌드 스텝 없이 `<script>` 두 장으로 굴리는 지금
  구조에서는 전역 하나를 더 만드는 일이 됩니다. 세 번째 화면이 생기면 그때 합칩니다
- 등록 화면이 길어졌습니다. 파일을 고르면 칸이 다섯 개 더 나타납니다
- 실패했을 때 남는 앱을 사람이 치워야 합니다. 방치된 `draft` 청소
  ([ADR-0019](0019-abandoned-draft-cleanup.md))는 버전을 지우지 앱을 지우지 않습니다
