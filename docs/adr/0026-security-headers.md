# ADR-0026: 보안 헤더를 서버가 붙이고, CSP 는 화면이 실제로 쓰는 것만 연다

- 상태: 수락됨
- 날짜: 2026-09-08

## 맥락

ADR-0010 후속으로 `OriginCheckMiddleware` 를 만들어 CSRF 를 막았습니다. 그 미들웨어는
**다른 사이트가 보낸** 요청을 거절합니다.

막지 못하는 것이 있습니다. 다른 사이트가 우리 화면을 투명한 iframe 으로 덮어놓고
사용자 손으로 누르게 만드는 것(클릭재킹)입니다. 그때 브라우저가 보내는 `Origin` 은
우리 것이라 출처 검사를 그냥 통과합니다.

우리 콘솔에는 그렇게 눌리면 곤란한 POST 폼이 그대로 있습니다.

- `/apps/:id/versions/:id/release` - 검토 전 빌드를 전 구성원에게 출시
- `/admin/users/:id/role` - 아무나 관리자로 승격

둘 다 확인 절차 없는 버튼 하나입니다.

배포 대상 플랫폼은 앱 HTTP 경로에 어떤 인증도 걸지 않습니다. 주소를 아는 사내망
사용자 누구나 이 화면에 도달합니다. 이 문을 닫는 것은 `frame-ancestors` 뿐입니다.

## 결정

### 모든 응답에 붙이는 미들웨어를 하나 둔다

`SecurityHeadersMiddleware` 를 미들웨어 스택의 **가장 바깥**에 둡니다.
`ConsoleErrorMiddleware` 보다 바깥이어야 오류 처리가 만들어낸 응답(404 화면 등)에도
헤더가 붙습니다.

경로로 나누지 않고 전부 붙입니다. 붙일지 말지를 따지기 시작하면 새로 만든 경로에서
빠지는 날이 옵니다.

| 헤더 | 값 |
| --- | --- |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `same-origin` |
| `Content-Security-Policy` | 아래 |

### CSP 는 템플릿을 읽고 맞춘다

```
default-src 'none';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: https: {스토리지 출처};
connect-src 'self' {스토리지 출처};
form-action 'self';
frame-ancestors 'none';
base-uri 'none'
```

| 지시문 | 왜 이 값인가 |
| --- | --- |
| `default-src 'none'` | 열지 않은 종류의 자원은 전부 막습니다. 새 자원을 쓰기 시작하면 조용히 통과하는 대신 눈에 띄게 막힙니다 |
| `script-src 'self'` | 스크립트는 `Public/upload.js` 하나뿐이고 인라인 스크립트는 어느 템플릿에도 없습니다 (ADR-0012) |
| `style-src` 에 `'unsafe-inline'` | `layout.leaf` 가 강조색을 인라인 `<style>` 로 넣습니다 |
| `img-src` 에 `https:` | 스토어 로고가 관리자가 넣는 아무 주소입니다. 서버가 미리 알 수 없습니다 |
| `connect-src` 에 스토리지 출처 | 업로드가 presigned URL 로 스토리지에 직접 `PUT` 합니다 |
| `frame-ancestors 'none'` | 이 미들웨어를 만든 이유입니다 |

스토리지 출처는 **presigned URL 을 만드는 것과 같은 함수**(`ArtifactStorage.objectBase`)
로 계산합니다. 여기서 규칙을 다시 쓰면 언젠가 둘이 어긋나고, 어긋난 날 증상은
"업로드가 아무 오류 없이 안 됨" 입니다.

### HSTS 는 붙이지 않는다

TLS 를 끊는 자리(인그레스·리버스 프록시)의 몫입니다.

### `X-Frame-Options` 도 붙이지 않는다

`frame-ancestors` 가 대체합니다.

## 대안과 기각 사유

**`style-src` 에 nonce 를 쓴다** — `'unsafe-inline'` 없이 인라인 스타일을 허용하는
정석입니다. 강조색은 관리자가 설정 화면에서 정하는 값이라 미리 해시해둘 수 없으므로,
남는 방법은 nonce 뿐입니다. 그러나 요청마다 nonce 를 만들어 **모든 화면의 렌더 경로**에
값을 하나씩 실어 날라야 합니다. 화면 하나를 새로 만들면서 그 값을 빠뜨리면 그
화면만 스타일이 깨집니다. 얻는 것과 견주면 무겁습니다.

대신 그 값이 무엇이 될 수 있는지를 저장 시점에 `#RRGGBB` 로 좁혀둡니다
(`StoreSettingsValidation`). 스타일 주입으로 할 수 있는 일과 스크립트 실행으로 할 수
있는 일은 크기가 다르고, 여기서 막고 싶은 것은 뒤쪽입니다.

**HSTS 를 서버가 붙인다** — 한 자리에서 끝나고 프록시 설정을 잊을 일이 없습니다.
그러나 문제가 둘입니다. 첫째, TLS 를 끊는 자리가 이미 붙이는 경우가 흔해서
`max-age` 가 다른 헤더가 둘 나갑니다. 둘째, **이 서버는 자기가 https 로 서비스되는지
알지 못합니다.** http 로 뜬 서버가 HSTS 를 붙이면 그 호스트에 다시는 http 로 붙지
못하게 되고, 되돌리려면 브라우저마다 손으로 지워야 합니다. 로컬 개발에서 한 번
겪으면 원인을 찾기까지 오래 걸립니다.

**`X-Frame-Options: DENY` 를 함께 붙인다** — `frame-ancestors` 를 모르는 아주 오래된
브라우저까지 덮습니다. 그러나 이 콘솔을 여는 브라우저는 전부 `frame-ancestors` 를
압니다. 같은 뜻을 두 헤더로 적으면 한쪽만 고치는 날이 오고, 그때 어느 쪽이 이기는지
아는 사람이 없습니다.

**`Referrer-Policy: no-referrer`** — 가장 안전합니다. 그러나
`OriginCheckMiddleware` 가 `Origin` 이 없을 때 `Referer` 를 대신 봅니다. 다 떼면 그
대비책이 함께 죽습니다. `same-origin` 은 우리 화면 안에서는 `Referer` 를 남기고 밖으로
나갈 때만 뗍니다.

**보고 전용(`Content-Security-Policy-Report-Only`)으로 먼저 돌린다** — 화면이 깨지는
것을 미리 봅니다. 그러나 위반을 받아줄 자리가 없고, 화면이 몇 개 없어서 템플릿을
직접 읽는 편이 빠릅니다. 무엇보다 클릭재킹은 지금 열려 있는 문이라 보고만 받는
기간을 두고 싶지 않았습니다.

## 결과

**좋은 점**

- 출시·역할 변경 폼이 iframe 에 덮이지 않습니다
- 오류 화면과 정적 파일에도 헤더가 붙습니다
- CSP 가 화면이 쓰는 것에 맞춰져 있어서, 나중에 인라인 스크립트나 바깥 CDN 을
  들이면 그 자리에서 막힙니다. 조용히 늘어나지 않습니다
- 스토리지 출처를 presigned URL 과 같은 함수로 계산해서 둘이 어긋나지 않습니다

**나쁜 점**

- **`'unsafe-inline'` 이 스타일에 남아 있습니다.** 강조색 인라인 `<style>` 하나
  때문입니다. CSP 를 스타일 주입 방어로 읽으면 이 정책은 그 일을 하지 않습니다
- **`img-src` 에 `https:` 가 통째로 열려 있습니다.** 로고 주소를 서버가 미리 알 수
  없어서입니다. 이미지는 실행되지 않지만, 화면에 뜨는 이미지 하나로 바깥 호스트에
  방문 사실이 전해질 수 있습니다
- 로고를 `http://` 로 적으면 이제 막힙니다. 저장은 되는데 화면에 안 뜹니다.
  https 로 적어야 합니다
- CSP 위반은 화면에 아무 표시도 남기지 않습니다. 브라우저 콘솔에만 찍힙니다.
  템플릿을 고치면서 여기를 같이 보지 않으면, 어느 날 업로드가 이유 없이 안 됩니다
- 위반 보고를 받는 곳이 없습니다. 무엇이 막혔는지 서버는 모릅니다

**후속**

- 화면을 고칠 때 이 정책도 같이 봐야 합니다. `SecurityHeadersTests` 가 지시문을
  하나씩 확인하므로, 정책을 바꾸면 테스트가 먼저 걸립니다
- 위반 보고 수집(`report-to`)은 필요해지면 그때 붙입니다. 지금은 받을 자리가 없습니다
