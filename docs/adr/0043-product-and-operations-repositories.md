# ADR-0043: 제품 레포와 운영 레포를 나눈다

- 상태: 수락됨
- 날짜: 2026-09-11

## 맥락

이 레포는 어떤 조직도 모르게 만들기로 했습니다([ADR-0003](0003-organization-neutral-code.md)).
그런데 실제로 스토어를 세우려면 조직에 묶이는 것이 반드시 생깁니다.

- 서버 주소, 허용 이메일 도메인, 번들 ID 접두어
- Developer ID 인증서와 공증 자격증명
- 어느 맥이 워커인지, 어떤 이미지 태그가 떠 있는지

지금은 그것들이 **아무 데도 기록되지 않습니다.** 담당자의 기억과 각 맥의 상태가
전부입니다. 워커가 dmg 를 모르는 채로 한참 돌았던 것도, 그것이 언제 설치된 것인지
적힌 데가 없어서 한참 몰랐습니다.

동시에 **서명은 제품 레포에서 할 수 없습니다.** Developer ID 개인키는 조직 것이고,
공개 전제인 레포의 CI 에 둘 수 없습니다([ADR-0022](0022-worker-as-signed-app-bundle.md)).

## 결정

레포를 둘로 나눕니다.

| | 무엇을 담나 | 누가 보나 |
| --- | --- | --- |
| **제품 레포** (여기) | 코드, 문서, 서버 컨테이너 이미지 | 누구나 (공개 전제) |
| **운영 레포** | 조직 설정, 서명·배포 CI, 운영 이력 | 그 조직만 (비공개) |

### 운영 레포는 소스에서 빌드해 서명합니다

제품 레포가 서명되지 않은 번들을 릴리스에 넣고 조직이 그것에 서명하는 방법도
있었습니다. 조직 쪽에 Swift 툴체인이 필요 없어 훨씬 편합니다.

**그러나 서명은 "우리가 이 코드를 보증한다" 는 뜻입니다.** 남이 만든 바이너리에
우리 이름을 붙이는 일이고, 재현 가능한 빌드가 아닌 한 그 바이너리가 공개된 소스와
일치하는지 확인할 방법이 없습니다. 제품 레포를 남이 가져다 쓸 것을 전제하면 그
신뢰를 기본값으로 둘 수 없습니다.

그래서 **운영 레포가 제품 레포를 태그로 고정해 받아, 자기 손으로 빌드하고 서명합니다.**
서명하는 주체와 빌드하는 주체가 같습니다.

### 운영 레포는 제품 레포를 서브모듈로 품습니다

포크는 쓰지 않습니다. 업스트림을 머지할 때마다 충돌이 나고, 조직 설정이 제품 코드와
섞이고, 그 섞인 이력이 영구히 남습니다.

서브모듈은 **고정된 커밋을 가리킨다**는 성질이 이 용도에 맞습니다. 무엇을 빌드했는지가
운영 레포의 커밋 하나로 남고, 올리는 것은 서브모듈 포인터를 옮기는 일입니다.

### 서명은 조직의 맥에서 합니다 (self-hosted 러너)

GitHub 호스팅 러너에 인증서를 올리는 방법도 있었습니다. 편하지만 개인키가 GitHub
시크릿에 올라갑니다.

**개인키가 그 맥을 떠나지 않는 쪽을 고릅니다.** 이미 워커가 도는 맥에 러너를 얹습니다.
그 맥은 이미 조직 서명 권한을 가진 머신이라, 신뢰 경계가 새로 생기지 않습니다.

**대가가 분명합니다. GitHub 워크플로가 그 맥의 셸이 됩니다.** 그래서 가드를 둡니다.

- 러너는 **비공개 운영 레포에만** 등록합니다. 공개 제품 레포에는 등록하지 않습니다
- 포크에서 온 워크플로는 실행하지 않습니다 (비공개 레포이므로 기본으로 막힙니다)
- 러너 라벨(`self-hosted, macos, alley-signing`)을 지정한 잡만 그 맥에서 돕니다
- **키체인이 잠겨 있으면 서명이 조용히 실패합니다.** 그 맥은 자동 로그인을 켜서
  로그인 키체인이 열린 상태를 유지해야 합니다. 실제로 잠긴 키체인에서
  `notarytool store-credentials` 가 `User interaction is not allowed` 로 죽는 것을
  겪었습니다

### Developer ID 는 하나만 씁니다

서명 전용 인증서를 따로 발급해 CI 에만 두면 유출 시 revoke 범위가 좁아집니다.
그러나 키가 맥을 떠나지 않는 구조에서는 인증서를 둘로 나눠도 보관 장소가 같습니다.
관리할 것만 늘어납니다.

### CLI 도 서명합니다

`alley` CLI 는 CI 러너 안에서 쓰면 Gatekeeper 를 타지 않아 서명이 필요 없습니다.
그러나 사람이 자기 맥에 두고 쓰는 일이 실제로 생기고, 그때 "확인되지 않은 개발자"
경고를 만납니다. **서명 절차가 이미 도는 자리에 하나 더 얹는 비용이 작습니다.**

### 제품 레포가 운영 레포 템플릿을 동봉합니다

`templates/ops/` 에 둡니다. 새 조직은 그것을 복사해 값 몇 개를 채우면 시작할 수
있습니다. 별도 레포로 두면 제품이 바뀔 때 템플릿이 따라오지 않고, 그 사실을 아무도
모릅니다.

### 올리는 일은 버전 하나를 옮기는 것입니다

```
제품 레포 v0.3.0 태그
        ↓  운영 레포 CI 가 새 릴리스를 감지해 PR 을 만든다
사람이 PR 을 머지                        ← 유일한 사람 개입
        ↓
서브모듈 갱신 → 빌드 → 서명 → 공증 → 업로드 → 롤아웃
        ↓
워커가 스스로 갈아끼운다 (ADR-0042)
스토어 앱이 자기 설치 코드로 스스로 갈아끼운다 (Sparkle 이 아니다)
```

워커와 스토어 앱은 이미 자기 갱신 장치가 있습니다. 운영 CI 가 **업로드까지만** 하면
나머지는 퍼집니다. 각 맥에 갈 일이 없습니다.

## 대안과 기각 사유

**한 레포에 다 둔다** — 가장 단순하고 버전이 어긋날 일이 없습니다. 그러나 ADR-0003 을
버리는 것입니다. 조직 설정과 제품 코드가 한 이력에 섞이면 공개할 수 없습니다.

**제품 레포를 포크한다** — 익숙한 모양이고 도구가 잘 받쳐줍니다. 그러나 업스트림
머지마다 충돌하고, 운영 설정을 커밋한 이력이 포크에 영구히 남습니다.

**서명되지 않은 릴리스 산출물에 조직이 서명한다** — 운영 쪽에 툴체인이 필요 없어
가장 편합니다. 위에 적은 대로 **남이 만든 바이너리에 우리 이름을 붙이는** 일이라
기본값으로 두지 않았습니다. 조직이 제품 레포를 직접 관리하는 경우에는 이쪽이 합리적
이고, 그때는 이 결정을 뒤집는 ADR 을 새로 쓰면 됩니다.

**GitHub 호스팅 러너에 인증서를 올린다** — 러너 관리가 필요 없고 맥이 꺼져 있어도
돕니다. 그러나 개인키가 조직 밖(GitHub)에 놓입니다.

## 결과

**좋은 점**

- 제품 코드는 공개 전제를 지킵니다. 조직 값이 이력에 섞이지 않습니다
- **서명하는 주체와 빌드하는 주체가 같습니다.** 남의 바이너리에 이름을 붙이지 않습니다
- 개인키가 조직의 맥을 떠나지 않습니다
- 무엇을 배포했는지가 운영 레포의 커밋 하나로 남습니다
- 올리는 일이 PR 머지 하나로 줄어듭니다. 각 맥에 가지 않습니다
- 새 조직은 템플릿을 복사해 시작합니다

**나쁜 점**

- **레포가 둘이라 어디를 봐야 하는지 알아야 합니다.** 문제가 났을 때 제품 쪽인지
  운영 쪽인지 가리는 일이 늘어납니다
- **GitHub 워크플로가 서명 맥의 셸이 됩니다.** 가드를 두지만, 운영 레포에 쓰기
  권한을 가진 사람은 그 맥에서 코드를 돌릴 수 있습니다
- **그 맥이 단일 장애점입니다.** 꺼져 있으면 배포가 멈춥니다. 워커도 같은 맥이라
  서명과 배포가 함께 멈춥니다
- **자동 로그인이 필요합니다.** 키체인이 잠기면 서명이 조용히 실패합니다. 자동
  로그인은 그 자체로 물리적 접근에 대한 보호를 낮춥니다
- **서브모듈은 다루기 까다롭습니다.** 클론할 때 `--recursive` 를 빼먹으면 빈
  디렉터리를 보고, 갱신하는 명령이 따로 있습니다
- 운영 쪽에 Swift 툴체인과 Xcode 가 필요합니다. 서명만 하는 것보다 무겁습니다
