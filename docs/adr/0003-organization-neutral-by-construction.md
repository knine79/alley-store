# ADR-0003: 조직 고유값을 코드에서 완전히 몰아낸다

- 상태: 일부 대체됨(ADR-0044)
- 날짜: 2026-08-12

> [ADR-0044](0044-store-app-knows-its-server.md) 가 스토어 앱의 서버 주소만
> 무효로 만들었습니다. 이제 조직이 빌드할 때 주소를 `Info.plist` 에 넣을 수 있고,
> 받은 사람은 주소를 입력하지 않습니다.
>
> **나머지는 그대로입니다.** 소스에는 여전히 조직 값이 없고, 브랜딩과 허용 도메인은
> `/meta` 로 받아옵니다. 주소를 주지 않고 만든 빌드는 예전과 똑같이 굴러갑니다.
> 아래 "빌드 타임에 브랜딩을 주입한다" 기각 사유는 클라이언트를 조직마다 따로
> 빌드하지 않는다는 전제에 기대고 있었는데, 그 전제는
> [ADR-0043](0043-product-and-operations-repositories.md) 이 이미 바꿨습니다.

## 맥락

이 프로젝트는 특정 조직의 내부 도구로 시작하지만 오픈소스 공개를 전제로 합니다.

보통 이런 프로젝트는 조직 고유값을 코드에 박아두고 공개 직전에 걷어냅니다. 그러면
공개 시점에 히스토리 재작성이 필요하고, 어딘가 하나쯤 남아 있게 됩니다. 이미 공개된
커밋은 되돌릴 수 없습니다.

## 결정

처음부터 코드가 어떤 조직도 모르게 만듭니다.

- 애플리케이션 코드는 표준 인터페이스만 압니다: PostgreSQL URL, S3 호환 엔드포인트,
  SMTP, Slack Webhook URL. 전부 환경변수로 주입받습니다
- 스토어 이름·로고·색상·허용 로그인 도메인은 서버가 `GET /api/v1/meta`로 내려줍니다.
  클라이언트는 **서버 주소만 입력하면** 나머지를 받아옵니다. 클라이언트 바이너리에
  조직 고유값이 들어가지 않습니다
- 조직별 배포 매니페스트(플랫폼 설정, 시크릿, 도메인)는 이 레포 밖에 둡니다
- 비밀값과 조직 고유값에는 기본값을 두지 않습니다. 설정 누락은 기동 시점에 어떤
  키가 빠졌는지 명시하고 실패합니다
- `scripts/check-denylist.sh`가 CI에서 이 원칙을 강제합니다

deny list의 금칙어 목록 자체가 유출이므로 레포에 두지 않습니다. `DENYLIST_TERMS`
환경변수로 넘기고 CI에서는 저장소 시크릿으로 주입합니다. 조직과 무관한 구조적
패턴(내부 호스트, 실제 이메일 주소, 사설 IP, 서명 자격증명 파일)은 항상 검사합니다.

`docs/`도 검사 대상입니다. 설계 문서에 조직 고유값이 남는 것도 같은 유출입니다.
예시 값은 `example.com` 계열을 쓰면 통과합니다.

## 대안과 기각 사유

**조직 고유값을 박아두고 공개 직전에 걷어낸다** — 당장은 빠릅니다. 그러나 공개 시점에
히스토리 재작성이 필요하고, 검증 없이 사람 눈으로 걷어내면 반드시 빠뜨립니다.

**금칙어 목록을 레포에 커밋하고 스크립트가 읽는다** — 설정이 간단합니다. 그러나
금칙어 목록 자체가 조직 정보라 목록을 공개하는 셈이 됩니다.

**빌드 타임에 브랜딩을 주입한다** — 조직별로 클라이언트를 따로 빌드합니다. 그러나
바이너리가 조직에 묶여서 배포·검증이 복잡해지고, 화이트라벨의 이점이 사라집니다.

## 결과

**좋은 점**
- 공개 시점에 히스토리 청소가 필요 없습니다
- 같은 클라이언트 바이너리가 어느 조직 서버에도 붙습니다
- 셀프호스팅 사용자가 `docker compose up`만으로 자기 인스턴스를 띄웁니다
- 원칙이 CI로 강제되어 사람 기억에 의존하지 않습니다

**나쁜 점**
- 설정 항목이 많아집니다. `.env.example`을 꼼꼼히 유지해야 합니다
- 하드코딩 한 줄이면 될 것을 설정 경로로 빼야 해서 초기 작성이 조금 번거롭습니다
- deny list가 오탐을 낼 수 있습니다. 실제로 `.gitignore`의 `*.local.yml` 글롭 패턴을
  내부 호스트로 잡은 사례가 있어 정규식을 좁혔습니다

**후속**
- 공개 전(Phase 4)에 시크릿 스캔과 deny list 최종 점검을 한 번 더 돌립니다
