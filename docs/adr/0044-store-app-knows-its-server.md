# ADR-0044: 스토어 앱에 서버 주소를 빌드할 때 넣는다

- 상태: 수락됨
- 날짜: 2026-09-15

> 이 결정은 그대로입니다. 다만 **값을 누가 넣느냐가 달라졌습니다.**
> [ADR-0046](0046-server-assembles-store-app.md) 이후 서버가 번들을 조립하면서
> 자기 `PUBLIC_BASE_URL` 을 박습니다. 운영 레포의 `config/store.env` 에 손으로
> 적는 것은 조립 스크립트로 직접 빌드할 때만 필요합니다. 아래 "나쁜 점" 의 "주소를
> 옮기면 앱을 다시 빌드해 배포해야 합니다" 도 관리 화면의 버튼 하나가 됐습니다.

## 맥락

스토어 앱을 처음 열면 주소 입력 칸과 "조직에서 안내받은 주소입니다. 담당자에게
물어보면 알려줍니다" 라는 안내가 나옵니다([ADR-0003](0003-organization-neutral-by-construction.md)).

이 화면은 **앱을 받은 사람이 할 수 없는 일을 요구합니다.**

- 조직이 나눠준 앱입니다. 어느 스토어에 붙을지는 나눠준 쪽이 이미 알고 있습니다
- 주소를 모르는 사람은 물어볼 곳을 또 찾아야 합니다. 앱을 받은 자리(웹 콘솔,
  안내 메일)에서 주소를 복사해 와야 하는데, 그 자리를 떠난 뒤에 앱을 여는 일이
  대부분입니다
- 잘못 적으면 "서버에 연결하지 못했습니다" 만 보입니다. 오타인지 사내망 밖인지
  구분되지 않습니다

한편 [ADR-0043](0043-product-and-operations-repositories.md) 이후로 **조직마다
자기 손으로 빌드합니다.** 운영 레포가 제품 레포를 태그로 고정해 받아 서명합니다.
번들 ID 와 URL 스킴은 이미 그때 `Info.plist` 에 박힙니다. 주소만 사람에게 묻는
상태입니다.

## 결정

조립 스크립트가 `ALLEY_STORE_APP_SERVER_URL` 을 받으면 그 주소를 `Info.plist` 의
`AlleyServerURL` 에 넣습니다. 앱은 켜질 때 그것을 읽고 바로 붙습니다.

- **소스에는 주소가 없습니다.** 값은 운영 레포의 `config/store.env` 에 있고,
  빌드할 때 들어옵니다. 제품 레포는 여전히 어느 조직도 모릅니다
- **주소를 주지 않은 빌드는 지금과 같습니다.** 주소 입력 화면이 그대로 나오고
  아무 서버에나 붙습니다. 개발과 셀프호스팅 시연이 그 빌드를 씁니다
- 박힌 주소가 저장된 주소를 이깁니다. 조직이 주소를 옮기면 새 빌드가 퍼지며
  따라가야 하는데, 저장된 값을 먼저 보면 옛 주소에 계속 붙습니다
- 박힌 빌드에서는 "다른 서버에 연결" 이 사라집니다. 돌아갈 자리가 없는 화면으로
  보내는 버튼입니다
- 연결에 실패하면 주소를 보여주고 다시 시도하게 합니다. 입력 칸을 내주지 않습니다.
  그 주소는 사용자가 고칠 수 있는 값이 아닙니다

### 왜 코드가 아니라 `Info.plist` 인가

`Info.plist` 는 서명 대상 안에 있습니다. 받은 사람이 주소를 고쳐 다른 서버로
돌리려 하면 서명이 깨지고 Gatekeeper 가 막습니다.

소스에 상수로 두면 조직 값이 제품 레포 이력에 들어갑니다. 빌드 플래그로 컴파일
타임에 넣는 방법도 있지만, 값 하나 때문에 조직마다 다른 바이너리를 컴파일하게
됩니다. `Info.plist` 는 이미 조직 값이 들어가는 자리입니다.

## 대안과 기각 사유

**지금처럼 사람이 입력한다** — 바이너리 하나가 어느 조직에도 붙습니다. 화이트라벨의
이점이 가장 큽니다. 그러나 **그 이점은 앱을 배포하는 쪽의 것이고, 비용은 받는 쪽이
치릅니다.** 한 조직의 구성원이 서로 다른 스토어를 오갈 일은 없습니다.

**다운로드 파일 이름이나 zip 안에 주소를 넣는다** — 서버가 이미 자기 주소를 아니
내려줄 때 붙이면 됩니다. 그러나 **서명·공증이 끝난 번들을 건드리는 일입니다.**
번들 안을 고치면 서명이 깨지고, 파일 이름에 실으면 사용자가 이름을 바꾸는 순간
사라집니다.

**quarantine 속성(`kMDItemWhereFroms`)에서 받은 곳을 읽는다** — 번들을 건드리지
않고 첫 실행에 주소를 알아낼 수 있습니다. 실제로 쓰이는 기법입니다. 그러나 브라우저와
macOS 버전에 따라 값이 다르고, zip 을 풀어 옮기면 사라집니다. **조용히 실패하고,
실패했을 때 사용자에게 설명할 말이 없습니다.**

**서버가 스토어 앱을 조직별로 다시 서명해 내려준다** — 사용자 쪽은 완전히 자동입니다.
그러나 서명은 워커의 일이고([ADR-0022](0022-worker-as-signed-app-bundle.md)) 다운로드
시점마다 서명·공증을 돌릴 수는 없습니다. 공증만 수 분입니다.

## 결과

**좋은 점**

- 조직이 나눠준 앱은 열면 바로 로그인 화면입니다. 물어볼 것이 없습니다
- 주소 오타로 인한 문의가 없어집니다
- 소스는 그대로 조직 중립입니다. 값은 운영 레포에 있습니다
- 주소를 고치면 서명이 깨집니다. 받은 앱이 다른 서버를 보게 만들 수 없습니다

**나쁜 점**

- **주소를 옮기면 앱을 다시 빌드해 배포해야 합니다.** 기존 앱은 스스로 업데이트하니
  퍼지기는 하지만, 옛 주소가 죽은 뒤에는 그 업데이트도 받지 못합니다. **주소를 옮길
  때는 옛 주소를 새 주소로 넘겨주는 기간을 두어야 합니다**
- 빌드가 조직에 묶입니다. "이 zip 은 어느 스토어 것인가" 를 파일만 보고는 알 수
  없어서, 여러 조직에 배포하는 곳은 산출물을 구분해 두어야 합니다
- 조립 스크립트가 받는 값이 하나 더 늘어납니다
- 주소가 잘못 박히면 그 빌드는 아무 데도 붙지 못합니다. 서명·공증을 마친 뒤에 드러나면
  다시 만드는 데 공증 대기만큼이 더 듭니다. 그래서 스크립트가 빌드 전에 형식을 봅니다

**후속**

- 주소를 옮기는 절차(옛 주소에서 새 주소로 넘기기)는 아직 없습니다. 실제로 옮길 일이
  생기면 그때 정합니다
