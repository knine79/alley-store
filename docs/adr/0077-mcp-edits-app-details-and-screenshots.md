# ADR-0077: MCP 로 앱 상세의 글과 스크린샷을 고친다

- 상태: 수락됨
- 날짜: 2026-10-13

## 맥락

MCP 는 릴리스 한 번에 필요한 것만 냈습니다 (ADR-0060). 올리고, 서명을 확인하고, 출시하는
것까지입니다. 그 뒤로 앱 상세에 태그(#43), 분류(#44), 스크린샷(#40, ADR-0071)이 생겼고
콘솔에서 앱 정보를 고칠 수 있게 됐습니다.

새 기능을 내면 소개 글과 화면도 바뀌어야 합니다. 그런데 에이전트는 이것을 읽지도 고치지도
못합니다. "이번 기능을 소개에 반영하고 스크린샷도 새로 찍어 올려줘" 를 맡기면 에이전트가
할 수 있는 것은 사람에게 콘솔로 가라고 말하는 것뿐입니다 (이슈 #70).

막힌 곳은 두 겹입니다.

- 앱 수정 API(`PATCH /api/v1/apps/:id`)는 있지만 사람 토큰 허용 목록(`UserTokenScope`)에 없습니다
- 스크린샷 올리기와 지우기는 콘솔 폼(`/apps/:id/screenshots`, 쿠키)에만 있습니다

## 결정

**사람 토큰으로 앱 상세의 글을 고치고, 스크린샷을 받고, 올리고, 지울 수 있게 합니다.**

- 허용 목록에 네 줄을 더합니다. `PATCH /api/v1/apps/:id`, 스크린샷 `GET`·`POST`·`DELETE`
- 스크린샷 API 를 새로 엽니다. `POST /api/v1/apps/:id/screenshots` 는 본문에 그림 한 장을
  받고, `DELETE /api/v1/apps/:id/screenshots/:sid` 는 한 장을 지웁니다. 둘 다 앱을 돌려줍니다
- 콘솔 폼과 API 는 같은 규칙(형식, 5MB, 5장, 원자적 덧붙이기)을 한 함수로 지납니다
- 권한은 화면과 같습니다. 글은 소유자와 관리자만, 스크린샷은 공동 담당자까지 고칩니다
- MCP 도구는 다섯을 더합니다. `app_details`, `update_app`, `add_screenshots`,
  `remove_screenshot`, `save_screenshots`

**여전히 열지 않는 것**은 번들 ID, 아이콘 주소, 멤버, 배포·피드 토큰, 앱 삭제입니다. 번들
ID 는 수정 요청에 아예 없어 이 길로 바뀌지 않습니다.

**아이콘 주소(`iconURL`)는 같은 요청에 있지만 사람 토큰으로 오면 거절합니다.** 아이콘은
워커가 번들에서 뽑고(ADR-0067) 콘솔은 이 칸을 보내지 않습니다. 열어두면 새어 나간 토큰
하나로 모든 스토어 앱이 남의 호스트에서 아이콘을 받아가게 만들 수 있습니다. 경로 단위
허용 목록으로는 칸 하나를 막을 수 없어서 수정 처리에서 막습니다.

**빈 문자열은 "그대로 두라" 로 읽습니다.** 모델은 선택 인자를 빈 값으로 채워 보내기도
합니다. 그것을 "지우라" 로 읽으면 이름 하나 고치려다 설명이 사라집니다. 그래서 MCP 로는
소개나 설명을 비울 수 없습니다. 태그만 빈 배열로 모두 뗄 수 있습니다.

**스크린샷은 한 장씩 올립니다.** multipart 로 여러 장을 받으면 CLI 가 경계를 직접 만들어야
하고, 앱 아이콘 API 가 이미 본문 하나를 받는 모양입니다. 여러 장은 MCP 가 차례로 부르고,
중간에 막히면 어디까지 올라갔는지 돌려줍니다. 실패로 접으면 모델이 처음부터 다시 불러
앞의 것이 두 번 붙습니다.

## 대안과 기각 사유

### 읽기만 열고 고치기는 콘솔에 둔다

ADR-0060 의 "돌이킬 수 없는 일은 화면에서 사람이 한다" 에 가장 가깝습니다. 사람들이
스토어에서 보는 글을 모델이 바꾸는 일이 아예 생기지 않습니다. 에이전트가 지금 값을 읽고
바꿀 문안을 제안하는 데까지는 할 수 있습니다.

기각한 이유는 **고치는 것이 돌이킬 수 없는 일이 아니기** 때문입니다. 글은 다시 고치면
되고, 스크린샷은 `save_screenshots` 로 받아둔 것을 다시 올리면 됩니다. 앱 삭제나 토큰
발급과 무게가 다릅니다. 읽기만 열면 결국 사람이 문안을 복사해 콘솔에 붙이는 일이 남고,
스크린샷은 파일을 찾아 끌어다 놓는 일까지 남습니다. 이슈가 줄이려던 것이 그 왕복입니다.

### 스크린샷 API 를 콘솔 폼처럼 multipart 로 여러 장 받는다

서버 쪽은 이미 있는 처리를 그대로 쓰면 되고, 여러 장이 한 요청에 묶여 "하나라도 틀리면
아무것도 올리지 않는다" 를 서버가 보장해 줍니다.

기각한 이유는 부르는 쪽이 둘 다 프로그램이기 때문입니다. CLI 에 multipart 인코더를 새로
만들어야 하고, 실패했을 때 응답이 콘솔 화면(HTML)이라 그대로는 쓸 수 없습니다. 원자성은
MCP 가 올리기 전에 모든 파일을 읽어보는 것으로 대부분 얻습니다. 남는 것은 서버가 거절하는
경우인데, 그때는 어디까지 올라갔는지 알려주는 것으로 충분합니다.

### `AppDTO` 를 그대로 돌려준다

변환할 것이 없고, 서버에 칸이 늘면 MCP 결과에도 저절로 실립니다.

기각한 이유는 스크린샷 주소가 모델에게 쓸모없기 때문입니다. 토큰 없이는 열리지 않고
(ADR-0071), 지우거나 받을 때 필요한 것은 id 뿐입니다. 아이콘 주소와 소유자 id 도 매번
창을 차지합니다. `AppSummary` 를 따로 둔 것과 같은 이유입니다.

## 결과

**좋은 점**
- 에이전트가 릴리스와 함께 소개 글, 분류, 태그, 스크린샷까지 맞춰 바꿉니다
- 콘솔과 API 가 같은 규칙을 지나서 한쪽만 고쳐지는 일이 없습니다
- 스크린샷을 받을 수 있어 에이전트가 지금 무엇이 찍혀 있는지 보고 바꿀지 정합니다

**나쁜 점**
- 사람이 보지 않은 문구가 스토어에 올라갈 수 있습니다. 도구 설명에 "사람에게 먼저
  보여준다" 고 적었지만 강제하지는 못합니다
- 사람 토큰이 새면 그 사람이 맡은 앱들의 소개와 화면을 바꿀 수 있습니다. 전에는 읽고
  버전을 올리는 것까지였습니다
- `remove_screenshot` 으로 지운 그림은 서버에 남지 않습니다. 받아두지 않았으면 되살릴 수 없습니다
- MCP 로는 소개와 설명을 비울 수 없습니다. 비우려면 콘솔로 가야 합니다
- 사람 토큰의 경계가 경로 목록 하나로 끝나지 않게 됐습니다. `iconURL` 처럼 칸 단위로
  막는 곳이 수정 처리 안에 따로 있습니다
