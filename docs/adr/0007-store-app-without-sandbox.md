# ADR-0007: 스토어 앱에 App Sandbox를 쓰지 않는다

- 상태: 수락됨
- 날짜: 2026-08-13

## 맥락

스토어 앱은 임의의 바이너리를 내려받아 실행 가능한 위치에 씁니다. 보안 관점에서
샌드박싱을 검토할 만한 앱입니다.

동시에 이 앱이 하는 일 자체가 `/Applications`에 앱을 쓰고, 업데이트할 때 실행 중인
대상 앱에 종료를 요청하는 것입니다.

## 결정

App Sandbox를 쓰지 않습니다. Hardened Runtime만 켜서 배포합니다.

대신 다음으로 방어합니다.

- **Hardened Runtime** — 공증 요건이기도 합니다
- **설치 전 서명 검증** — 내려받은 앱을 `codesign --verify --deep --strict`로 확인하고
  Team ID가 기대값과 같은지 대조합니다
- **SHA-256 대조** — 서버가 알려준 해시와 내려받은 파일을 대조합니다
- **quarantine 속성 유지** — 첫 실행 시 macOS 표준 Gatekeeper 검증을 그대로 태웁니다

설치 위치는 `/Applications`가 기본이고, 쓰기 권한이 없으면 `~/Applications`로
폴백하며 그 사실을 사용자에게 알립니다.

## 대안과 기각 사유

**App Sandbox 적용** — 앱이 침해됐을 때 피해 범위가 줄어듭니다. 그러나 샌드박스는
파일시스템 쓰기와 다른 프로세스 제어를 막는데, 그 둘이 정확히 이 앱의 핵심 기능입니다.
우회하려면 사용자가 매번 설치 위치를 직접 고르거나 별도 권한 헬퍼를 두어야 하고,
보안은 늘지 않고 사용성만 나빠집니다.

Mac App Store에 올린다면 샌드박스가 필수지만 이 앱은 Developer ID로 배포하므로
해당하지 않습니다.

**설치 작업만 권한 분리된 헬퍼로 분리** — 이론적으로는 더 안전합니다. 그러나
`/Applications` 쓰기는 관리자 계정에서 특별한 권한 없이 되므로 헬퍼를 도입할 만큼의
이득이 없습니다. 오버엔지니어링입니다.

## 결과

**좋은 점**
- 설치 앱 탐지, 번들 교체, 대상 프로세스 종료 요청이 모두 자연스럽게 구현됩니다
- 서명 검증이 샌드박싱보다 실질적입니다. 서버가 침해되어 다른 바이너리를 내려줘도
  클라이언트에서 걸립니다

**나쁜 점**
- 스토어 앱이 침해되면 파일시스템 접근이 제한되지 않습니다. 스토어 앱 자체의 코드
  품질과 의존성 관리가 중요해집니다
- 조직 보안 정책이 모든 앱에 샌드박스를 요구한다면 이 결정을 다시 봐야 합니다

**후속**
- 스토어 앱의 의존성은 최소로 유지합니다. 샌드박스가 없는 만큼 공급망 위험이
  그대로 노출됩니다
