# ADR-0065: 스토어가 CLI 를 내준다

- 상태: 수락됨
- 날짜: 2026-09-29

## 맥락

`alley` 명령을 받을 데가 없습니다. 지금 얻는 유일한 길은 레포를 클론하고 Swift
툴체인으로 직접 빌드하는 것입니다.

```bash
swift build -c release --product alley
```

앱을 올리려는 사람과 코딩 에이전트를 붙이려는 사람에게 **"먼저 레포를 클론하세요"
는 말이 되지 않습니다.** MCP 를 붙이는 첫 단계가 `alley auth login`
([ADR-0064](0064-the-cli-gets-its-token-from-the-browser.md))인데, 그 명령을 얻는
방법이 문서에 없습니다.

`scripts/build-cli.sh` 는 이미 있고 서명·공증까지 합니다. 주석에 이유도 적혀
있습니다.

> 사람이 자기 맥에 두고 쓰는 일이 실제로 생기고, 그때 "확인되지 않은 개발자"
> 경고를 만난다.

**그런데 아무도 이 스크립트를 부르지 않습니다.** 제품 CI 도, 릴리스도, 운영 CI 도
부르지 않아서 산출물이 어디에도 없습니다.

## 결정

**운영 CI 가 빌드·서명해 스토어에 올리고, 스토어가 `/get/cli` 에서 내줍니다.**

```
운영 CI (조직 맥, 인증서 있음)
  ./scripts/build-cli.sh --sign
         ↓
  POST /api/v1/ops/cli-releases     (운영 토큰)
         ↓
서버: CLIRelease 한 줄 + 스토리지에 바이너리
         ↓
  GET /get/cli                      (로그인 없이)
```

### 제품 레포는 서명하지 않습니다

[ADR-0043](0043-product-and-operations-repositories.md) 이 정한 것을 그대로
따릅니다. 서명은 "우리가 이 코드를 보증한다" 는 뜻이고, 빌드하는 주체와 서명하는
주체가 같아야 합니다. 제품 CI 는 미서명 바이너리조차 내놓지 않습니다. 운영 레포가
태그로 고정한 소스에서 자기 손으로 빌드합니다.

워커 번들이 이미 같은 길로 갑니다.

### `WorkerRelease` 와 같은 모양입니다

[ADR-0042](0042-worker-self-update.md) 가 워커 번들을 올리고 고르는 자리를 이미
만들어뒀습니다. 버전, 스토리지 키, 크기, 해시, 그리고 **지금 배포할 것 하나를
가리키는 표시**입니다.

CLI 도 같은 것이 필요합니다. 특히 되돌릴 수 있어야 하는 것이 같습니다. "가장 높은
버전" 이 아니라 따로 표시를 두어, 새 CLI 에 문제가 있으면 옛것으로 돌립니다.

### 로그인 없이 내줍니다

스토어 앱을 받는 `/get` 과 같은 이유입니다
([ADR-0049](0049-public-store-app-download-page.md)). CLI 가 없는 사람에게 CLI 로
로그인하라고 할 수 없습니다. 받아가는 것은 서명·공증된 바이너리 하나이고, 그것만
으로는 이 스토어의 아무것도 볼 수 없습니다.

### 번들이 아니라 맨 실행 파일입니다

스토어 앱은 `.app` 이라 `Info.plist` 를 고쳐 조직 브랜딩을 입힙니다
([ADR-0046](0046-server-assembles-store-app.md)). CLI 는 고칠 것이 없습니다.
조직마다 다른 값은 `alley auth login --server` 로 사람이 주고, 그 뒤로는 저장된
것을 씁니다. 서버가 조립할 이유가 없어 **올라온 바이트를 그대로 내줍니다.**

## 대안과 기각 사유

### GitHub Release 에 붙이고 거기서 받게 한다

**서버에 만들 것이 없습니다.** 릴리스 워크플로에 파일 하나를 더하면 끝입니다.

기각한 이유는 서명 때문입니다. 제품 레포가 서명할 수 없으므로 붙일 수 있는 것은
미서명 바이너리뿐이고, 받은 사람은 Gatekeeper 에 막힙니다. 운영 레포의 릴리스에
붙이는 방법도 있지만, 그러면 **받는 자리가 스토어 밖으로 나갑니다.** 스토어 주소
하나만 알면 되던 것이 레포 접근 권한까지 필요해집니다.

### 서버 이미지에 실어 보낸다

**올리는 단계가 없습니다.** 이미지에 넣어두면 서버가 뜨는 순간 받을 수 있습니다.

기각한 이유는 서명입니다. 서버 이미지는 리눅스에서 만들어지고 거기에는 인증서가
없습니다. 미서명 바이너리를 실어봐야 받은 사람이 쓰지 못합니다.

### Homebrew tap 을 만든다

**맥 개발자에게 가장 익숙합니다.** `brew install` 한 줄이면 끝나고 업데이트도
따라옵니다.

기각한 이유는 tap 을 조직 밖에 두어야 하기 때문입니다. 사내 스토어의 CLI 주소가
공개 저장소에 적히고, 조직마다 다른 스토어 주소를 어떻게 다룰지도 정해야 합니다.
쓰는 사람이 늘면 그때 얹을 수 있고, 그때도 이 자리가 원본으로 남습니다.

## 나쁜 점

**올리는 것을 잊으면 옛 CLI 가 계속 나갑니다.** 서버는 올라온 것을 내줄 뿐이고,
제품 버전과 맞는지 보지 않습니다. 운영 CI 가 제품 반영과 같은 자리에서 올리므로
대개 함께 가지만, 손으로 반영하면 어긋날 수 있습니다.

**받은 사람이 스스로 갱신하지 않습니다.** 워커는 자기를 갈아끼우지만
(ADR-0042) CLI 는 그렇지 않습니다. 사람이 다시 받아야 합니다. `alley` 가 서버에
붙을 때마다 버전을 견주어 알려줄 수는 있지만, 지금은 그것도 없습니다.

**universal 바이너리라 큽니다.** arm64 와 x86_64 를 함께 담아 2MB 가 조금 넘습니다.
맥마다 맞는 것을 고르게 하면 절반이 되지만, 받는 사람이 자기 칩을 알아야 합니다.
