# ADR-0005: 번들 ID는 고유하게, 포털 App ID는 와일드카드로 묶는다

- 상태: 수락됨
- 날짜: 2026-08-12

## 맥락

앱이 늘어나면 개발자 포털에 App ID 엔트리가 쌓입니다. "번들 ID를 하나 만들어
공유하면 되지 않나"라는 제안에서 출발했습니다.

여기에는 두 개념이 섞여 있습니다. **번들 ID(bundle identifier)**는 앱의 런타임
정체성이고, **포털의 App ID**는 개발자 계정에 등록하는 엔트리입니다. 둘은 다르게
다뤄야 합니다.

## 결정

**번들 ID는 앱마다 고유해야 합니다. 공유하지 않습니다.**

macOS가 번들 ID를 기준으로 LaunchServices 앱 등록, `UserDefaults` 도메인,
Application Support 경로, 키체인 접근 그룹, TCC 권한(카메라·마이크·화면 녹화) 승인
단위를 결정하기 때문입니다. 같은 번들 ID를 쓰는 두 앱은 서로를 덮어씁니다.

**포털의 App ID는 3단 정책으로 최소화합니다.**

| 앱 유형 | 포털 등록 |
| --- | --- |
| 대부분의 내부 앱 | 등록 없음. 서명 + 공증만으로 배포 |
| 프로필은 필요하나 특수 capability 없음 | 와일드카드 App ID 1개 공유 (`<prefix>.*`) |
| Push / iCloud / App Groups / Sign in with Apple / Associated Domains 사용 | explicit App ID 개별 등록 |

첫 행이 핵심입니다. Developer ID 배포는 대부분의 앱에서 프로비저닝 프로필도 App ID
등록도 필요 없습니다. Gatekeeper가 보는 것은 인증서 서명과 공증 티켓입니다
(ADR-0002 참조).

**ID 관리 책임은 스토어가 가져갑니다.** 번들 ID 프리픽스를 서버 설정값
`BUNDLE_ID_PREFIX`로 두고, 앱 등록 시 프리픽스 준수와 중복 여부를 검증합니다.
등록된 번들 ID 목록을 웹 콘솔에서 조회할 수 있게 해서 실질적인 ID 대장으로 씁니다.

## 대안과 기각 사유

**번들 ID 하나를 여러 앱이 공유** — 애초에 불가능합니다. macOS가 번들 ID로 앱을
식별하므로 앱들이 서로 충돌합니다.

**모든 앱을 explicit App ID로 등록** — 관리가 명시적입니다. 그러나 대부분의 앱에는
필요 없는 엔트리이고, 정확히 이 제안이 피하려던 난립을 만듭니다.

**프리픽스를 코드에 하드코딩** — 검증이 단순해집니다. 그러나 ADR-0003의 조직 중립
원칙에 어긋납니다. 설정값으로 두고 강제 여부도 선택할 수 있게 합니다.

## 결과

**좋은 점**
- 포털 엔트리가 와일드카드 1개 + 특수 capability 앱 몇 개로 유지됩니다
- 번들 ID 중복이 등록 시점에 걸립니다
- 어떤 번들 ID가 쓰이고 있는지 한곳에서 보입니다

**나쁜 점**
- 와일드카드 App ID는 Push, iCloud, App Groups, Sign in with Apple, Associated
  Domains를 커버하지 못합니다. 이런 앱은 여전히 개별 등록이 필요합니다
- 프리픽스 강제는 기존 앱을 스토어에 올릴 때 마찰이 될 수 있습니다.
  `ENFORCE_BUNDLE_ID_PREFIX`로 끌 수 있게 했습니다

**후속**
- 프리픽스 비교는 경계를 확인합니다. `com.example`을 요구할 때
  `com.exampleevil.tool`이 통과하면 안 되므로 끝점을 붙여 비교합니다
  (`BundleIdentifier.validate`)
