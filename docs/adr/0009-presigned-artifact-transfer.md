# ADR-0009: 바이너리는 서버를 거치지 않고 presigned URL로 주고받는다

- 상태: 수락됨
- 날짜: 2026-08-14

## 맥락

앱 하나가 수십에서 수백 MB입니다. 개발자가 빌드를 올리고, 서명 워커가 그것을
받아 서명본을 올리고, 사용자가 그것을 받아갑니다. 하나의 버전이 스토리지와
최소 네 번 오갑니다.

서버는 Docker 컨테이너 하나로 도는 것을 전제합니다(ADR-0004). 오브젝트
스토리지는 MinIO일 수도 AWS S3일 수도 있어야 합니다.

## 결정

서버는 바이너리를 자기 프로세스로 통과시키지 않습니다. 만료 있는 서명된 URL을
발급하고, 클라이언트가 스토리지와 직접 주고받습니다.

- 버전을 만들면 `UploadTicket`(업로드용 PUT URL + 만료 시각)을 내줍니다
- 클라이언트가 올린 뒤 `POST /versions/:id/complete`로 알립니다
- 서버는 그 통지를 받고 **스토리지에 `HEAD`를 던져 실제 크기를 확인한 뒤**에만
  상태를 `uploaded`로 넘깁니다
- 다운로드도 같은 방식이고, URL을 내주기 **전에** 다운로드 이력을 남깁니다

오브젝트 키는 `apps/{앱ID}/versions/{버전ID}/{unsigned|signed}.zip`입니다.
서명본과 미서명본이 다른 자리에 놓여서, 서명이 실패해도 원본이 남습니다.

무결성 확인용 SHA-256은 올린 쪽이 신고합니다. 크기는 신고를 믿지 않고
스토리지가 알려준 값을 씁니다.

## 대안과 기각 사유

**서버가 업로드를 받아 스토리지로 중계한다** — 구현이 단순하고, 서버가 바이트를
직접 보므로 SHA-256을 서버가 계산해서 신고를 믿지 않아도 됩니다. 접근 제어도
한곳에서 끝납니다. 그러나 200MB 업로드가 진행되는 동안 서버 커넥션 하나가
묶이고, 메모리나 임시 디스크를 씁니다. 재시도할 때마다 그 비용을 다시 냅니다.
컨테이너 하나로 도는 전제에서 개발자 몇 명이 동시에 올리면 그것만으로 서버가
막힙니다. 무엇보다 이 경로는 사용자 다운로드에도 그대로 적용돼서, 배포일에
수십 명이 동시에 받으면 서버가 병목이 됩니다.

**멀티파트 업로드를 처음부터 넣는다** — 큰 파일에서 실패했을 때 처음부터 다시
올리지 않아도 되고, 5GB 단일 PUT 제한도 넘습니다. 그러나 파트별 URL 발급,
파트 목록 추적, 완료 통지, 미완료 업로드 청소까지 붙습니다. 사내망에서 수백 MB를
올리는 상황이라 단순 재시도로 충분하다고 봤습니다. 실패가 잦아지면 그때
도입합니다(구현 계획의 열려 있는 결정에 남겨뒀습니다).

**클라이언트에게 스토리지 자격증명을 직접 준다** — URL 발급 왕복이 사라집니다.
그러나 자격증명이 클라이언트에 남고, 범위를 앱·버전 단위로 좁히려면 STS 같은
것이 필요합니다. MinIO와 S3 양쪽에서 같게 동작하게 만들기도 어렵습니다.

**SHA-256을 서버가 계산한다** — 신고를 믿지 않아도 됩니다. 그러나 그러려면
서버가 파일 전체를 읽어야 하고, 그건 중계와 같은 비용입니다. 올린 사람이 거짓을
적을 수는 있지만 그건 자기 바이너리에 대한 거짓이고, 받는 쪽의 진짜 방어선은
설치 직전의 서명·Team ID 검증입니다(ADR-0007).

## 결과

**좋은 점**

- 서버 사양이 앱 크기나 동시 다운로드 수와 무관해집니다
- 스토리지가 MinIO든 S3든 같은 코드로 동작합니다
- URL에 만료가 있어서 유출돼도 창이 좁습니다
- 서명 워커도 같은 방식을 씁니다. 워커에게 스토리지 자격증명을 주지 않아도 됩니다

**나쁜 점**

- 업로드가 두 단계(PUT → complete)라 클라이언트가 복잡해집니다. `complete`를
  안 부르면 버전이 `draft`로 남고, 스토리지에는 파일이 있는데 아무도 모릅니다
- 발급된 URL은 만료 전까지 인증 없이 유효합니다. 다운로드 이력은 티켓 발급
  시점에 남으므로, 티켓을 남에게 넘기면 실제로 받은 사람과 기록이 어긋납니다
- 스토리지가 서버와 다른 주소로 노출돼야 합니다. 사용자 브라우저나 스토어 앱이
  스토리지에 직접 닿을 수 있어야 하고, 이건 배포 구성의 제약이 됩니다
- 큰 파일 업로드가 중간에 끊기면 처음부터 다시 올립니다
- presigned URL의 기준 주소를 서버가 직접 조립합니다. path style과 가상 호스트
  방식을 각각 다뤄야 하고, 여기가 틀리면 서명은 맞는데 엉뚱한 곳을 가리키는
  URL이 나갑니다

**후속**

- `draft`로 남아 방치된 버전과 그 오브젝트를 청소하는 작업이 필요합니다
- 다운로드 URL에 `response-content-disposition`을 붙여 파일 이름을 앱 이름으로
  내려주면 사용자 경험이 나아집니다
- 재개 가능 업로드가 필요해지면 멀티파트로 확장합니다
