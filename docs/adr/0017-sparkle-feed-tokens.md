# ADR-0017: Sparkle 피드는 앱별 읽기 전용 토큰을 주소에 실어 인증한다

- 상태: 수락됨
- 날짜: 2026-09-01

## 맥락

ADR-0006 에서 앱 업데이트 경로를 둘로 두기로 했습니다. 스토어 앱으로 받는 경로와,
앱이 Sparkle 로 스스로 받는 경로입니다. 후자를 실제로 만들면서 두 가지를 정해야
했습니다.

**인증.** 다른 모든 API 는 로그인을 요구하는데 Sparkle 은 우리가 만든 클라이언트가
아닙니다. `SUFeedURL` 하나를 주면 그 주소를 GET 할 뿐이고, `Authorization` 헤더를
붙일 방법이 없습니다. ADR-0006 은 "앱별 피드 토큰"이라고만 적었고 전달 방식은
비워두었습니다.

**서명.** Sparkle 2 는 내려받은 파일에 EdDSA(Ed25519) 서명이 붙어 있어야 설치합니다.
코드 서명·공증과 별개의 검사입니다. 서명을 만들려면 개인키가 필요한데, 그 키를
어디에 둘 것인지가 ADR-0002(서명 키는 워커 머신에만)와 맞닿습니다.

## 결정

### 피드 토큰은 앱별 읽기 전용, 주소의 질의 항목으로 받는다

- `feed_tokens` 표를 따로 둡니다. 배포 토큰(ADR-0015)과 표를 나눕니다
- 접두사는 `alleyf_`. 값만 보고 무엇인지 알 수 있습니다
- 할 수 있는 것은 **그 앱의 출시본 목록을 보고 받는 것**뿐입니다
- `?token=...` 으로 받습니다. Sparkle 이 헤더를 붙일 수 없어서입니다
- 토큰이 틀리면 403 이 아니라 **404** 를 줍니다. 앱 ID 를 바꿔가며 무엇이 있는지
  훑는 것을 막습니다
- 발급하면 `SUFeedURL` 에 그대로 넣을 완성된 주소를 줍니다. 사람이 물음표와 등호를
  손으로 붙이면 실수가 납니다

### Sparkle 서명은 워커가 만든다

- 서명 워커가 결과물 zip 에 Ed25519 서명을 만들어 서버에 함께 보고합니다
- 개인키는 `ALLEY_SPARKLE_PRIVATE_KEY` 로 워커 머신에만 둡니다. 서버는 서명 문자열만
  받아 appcast 에 싣습니다
- Sparkle 의 `sign_update` 도구를 쓰지 않고 직접 서명합니다. 그 도구가 하는 일이
  Ed25519 서명과 base64 인코딩뿐이라, 워커 머신에 도구를 하나 더 깔게 할 값이
  없습니다
- 키가 설정되지 않으면 서명 없이 진행합니다. appcast 를 쓰지 않는 조직에는 필요
  없는 값입니다

## 대안과 기각 사유

**피드 주소를 로그인 뒤에만 열어둔다 (쿠키 인증)** — 다른 경로와 규칙이 같아집니다.
그러나 Sparkle 은 브라우저가 아니라 쿠키를 들고 있지 않습니다. 앱이 직접 로그인
플로우를 밟아 세션을 얻고 Sparkle 에 넘기는 방법은, Sparkle 의 요청에 헤더를 얹는
델리게이트를 앱마다 구현해야 한다는 뜻입니다. 사내 앱 하나하나에 그 코드를 넣게
하려고 이 기능을 만드는 것이 아닙니다.

**토큰을 `Authorization` 헤더로 받고 앱이 Sparkle 을 감싸게 한다** — 주소에 비밀이
실리지 않아 로그 유출 위험이 사라집니다. Sparkle 은 `SPUUpdaterDelegate` 로 요청을
손볼 여지를 주기도 합니다. 그러나 앱마다 그 델리게이트를 구현해야 하고, 그것을
빠뜨린 앱은 조용히 업데이트가 멈춥니다. "URL 하나만 넣으면 된다"가 이 경로의 가치인데
그걸 잃습니다.

**토큰 없이 열어둔다** — 사내망 안이라면 그럴 수도 있습니다. 그러나 스토어 서버는
VPN 밖에서도 닿게 두는 구성이 흔하고(ADR-0004), 그러면 앱 ID 만 알면 누구나 사내
빌드를 받게 됩니다.

**서버가 Sparkle 서명키를 갖는다** — 워커에 설정을 하나 덜 넣어도 되고, 이미 있는
버전에 나중에 서명을 채울 수도 있습니다. 그러나 ADR-0002 에서 "서명에 쓰는 키는
워커 머신에만"이라고 정한 것과 어긋납니다. 코드 서명 키와 Sparkle 서명 키는 종류가
다르지만, 둘 다 "이것이 우리가 만든 것"이라고 말하는 키입니다. 서버가 뚫렸을 때
공격자가 자기 빌드에 서명해 배포할 수 있게 되는 것은 같습니다.

**서명 없이 appcast 를 낸다** — Sparkle 1 은 서명 없이도 돌지만 Sparkle 2 는
거부합니다. 그리고 거부의 방식이 조용합니다. 사용자는 "업데이트 없음"만 봅니다.

## 결과

**좋은 점**

- 앱에 `SUFeedURL` 한 줄만 넣으면 됩니다. 델리게이트도 추가 코드도 없습니다
- 토큰이 새도 그 앱의 출시본을 받을 수 있을 뿐입니다. 쓰기는 아무것도 못 합니다
- 폐기가 즉시 반영되고, 마지막 사용 시각이 남아 안 쓰는 피드를 정리할 수 있습니다
- 서명 키가 코드 서명 인증서와 같은 자리에 있습니다. 워커 머신 하나만 지키면 됩니다

**나쁜 점**

- **토큰이 URL 에 들어갑니다.** 프록시 로그, 브라우저 기록, 오류 보고에 그대로
  남습니다. 헤더로 받는 것보다 분명히 약합니다. 대신 그 토큰으로 할 수 있는 일을
  읽기 하나로 좁혔습니다
- **사용자별 다운로드 이력이 남지 않습니다.** 토큰이 앱 단위라 누가 받았는지 알 수
  없습니다. ADR-0006 이 이미 인정한 한계이고, 이력이 중요한 앱은 스토어 앱 경로를
  씁니다
- 서명 키를 잃어버리면 이미 배포된 앱들이 업데이트를 못 받습니다. 앱에 박힌
  `SUPublicEDKey` 를 바꾸려면 새 빌드를 다른 경로로 배포해야 합니다
- 워커가 서명할 때 파일을 통째로 메모리에 올립니다. Ed25519 는 스트리밍 서명이
  아닙니다. 수백 MB 짜리 앱에서 그 순간 메모리를 그만큼 씁니다
- 신원이 넷이 됐습니다(사람·워커·배포·피드). 새 경로마다 어느 것을 받을지 판단해야
  합니다

**후속**

- 피드 토큰에 만료를 둘지는 실제 운영을 보고 정합니다. 만료가 있으면 앱이 조용히
  업데이트를 멈추는 날이 오고, 알림이 없으면 만료가 오히려 나쁩니다

  아무 데도 적혀 있지 않습니다~~ → [셀프호스팅 가이드](../self-hosting.md)에 썼습니다.

  Sparkle 은 Ed25519 서명과 Apple 코드 서명 중 **하나만** 맞아도 업데이트를 받아들여서,

  같이 바뀐 경우입니다
