# ADR-0060: MCP 는 사람으로 붙고, 배포 토큰은 CI 에 남긴다

- 상태: 수락됨
- 날짜: 2026-09-22

## 맥락

개발자가 릴리스 한 번을 내는 동안 자리를 여러 번 옮깁니다. CLI 로 올리고, 콘솔을
새로고침하며 서명이 끝나기를 기다리고, 실패하면 화면의 안내를 읽어 손으로 고치고,
Sparkle 을 쓰는 앱이면 `SUPublicEDKey` 를 화면에서 복사해 `Info.plist` 에 붙입니다.

그 자리를 에이전트가 대신 밟게 하려고 MCP 서버를 답니다. 그러려면 에이전트가 무엇으로
인증하느냐를 먼저 정해야 합니다.

**여기서 정하는 것은 MCP 가 쥘 자격증명뿐입니다.** CI 가 쓰는 배포 토큰을 어떻게 할
것인가가 아닙니다. 그쪽은 앱마다 따로 두는 지금이 맞고, 이 결정으로 바뀌지 않습니다.

**지금 개발자가 쥘 수 있는 자격증명은 앱별 배포 토큰(`alleyd_`) 하나입니다.** 그런데
그 토큰을 받는 경로는 `VersionController` 와 배포 토큰 화면뿐입니다. 곧 **업로드
전용**입니다. MCP 가 할 일로 꼽은 다섯 중 업로드를 뺀 넷(서명 상태, 버전 목록,
Sparkle 피드와 상태, 피드백)은 사람 세션으로만 읽힙니다.

토큰의 종류는 이미 넷입니다. 워커(`alleyw_`), 배포(`alleyd_`), 운영(`alleyo_`),
피드(`alleyf_`). 하나를 더 들일지, 있는 것을 넓힐지의 문제입니다.

## 결정

**MCP 는 사람 토큰으로 붙습니다.** 사람에게 발급하고, 무엇을 만질 수 있는지는 그
사람의 앱 멤버십에서 나옵니다. 발급과 폐기는 "내 설정" 에서 하고, 90일이면 만료됩니다.
접두사는 `alleyu_` 로 두어 나머지 넷과 갈립니다.

**권한을 scope 로 나누지 않습니다.** 그 사람이 화면에서 할 수 있는 것은 대체로 이
토큰으로도 됩니다. 도구마다 권한을 적어두는 표를 만들면 도구를 하나 더할 때마다 그
표를 손봐야 하고, 빠뜨린 것은 조용합니다.

**대신 지우는 것은 막습니다.** 두 자리에서 한 번씩입니다.

- `/api/v1` 밖에서는 인증하지 않습니다. 화면 경로에는 API 에 없는 동작이 있고, 앱
  삭제가 그렇습니다. 사람이 브라우저에서 한 번 더 생각하고 누르는 자리를 토큰으로
  열어둘 이유가 없습니다
- 그 안에서도 `DELETE` 는 거절합니다. 멤버를 떼거나 토큰을 폐기하거나 출시를 되돌리는
  것들입니다

도구로 내주지 않는 것과 토큰으로 못 하는 것은 다릅니다. 도구 목록은 늘어나지만 이
규칙은 한 자리에 있습니다.

**배포 토큰은 지금 그대로 둡니다.** 앱 하나에 묶인 CI 자격증명이고 업로드만 합니다.
MCP 를 위해 권한을 넓히지 않습니다.

둘은 경쟁하는 선택지가 아닙니다. 하나는 기계의 신원이고 하나는 사람의 신원입니다.
GitHub 도 Actions 시크릿과 개인 토큰을 따로 둡니다.

| | 배포 토큰 | 사람 토큰 |
| --- | --- | --- |
| 누구 | CI 러너 | 개발자 본인 |
| 범위 | 앱 하나 | 그 사람이 속한 앱들 |
| 할 수 있는 것 | 업로드 | 그 사람이 화면에서 할 수 있는 것 |
| 새면 | 그 앱만 | 그 사람의 앱 전부 |

## 대안과 기각 사유

### 앱별 배포 토큰을 그대로 쓴다

**통상적인 모양입니다.** CI 자격증명은 좁게 잡는 것이 맞고, 앱마다 나누면 새어도
반경이 그 앱에서 끝납니다. 사람이 새로 배울 것도 없습니다. 이미 발급해 쓰고 있는
것을 MCP 설정에 한 번 더 넣으면 됩니다.

기각한 이유는 **그 토큰으로는 MCP 가 할 일의 대부분이 되지 않기** 때문입니다. 되게
하려면 배포 토큰에 읽기 권한을 붙여야 하는데, 그 토큰은 CI 시크릿에 박혀 있습니다.
러너를 건드릴 수 있는 사람이 피드백과 통계까지 보게 됩니다. 좁게 잡아둔 것을 넓히는
쪽이 오히려 통상에서 벗어납니다.

앱이 늘 때마다 MCP 설정을 고쳐야 하는 것도 실사용에서 걸립니다. 에이전트에게 "내
앱들" 을 물어볼 수 없고, 사람이 목록을 먼저 알려줘야 합니다.

### OIDC 로그인 흐름을 MCP 가 그대로 탄다

새 자격증명이 아예 없다는 점이 가장 좋습니다. 세션 수명과 탈퇴가 그대로 걸리고,
따로 관리할 것이 생기지 않습니다.

기각한 이유는 브라우저입니다. 로그인 창을 띄워야 하고, 헤드리스나 원격 셸에서는
쓸 수 없습니다. 세션 쿠키를 에이전트가 들고 있는 것도 수명 관리가 어렵습니다.
스토어 앱은 이 문제를 `/api/v1/auth/token` 으로 한 번 풀었지만, 그것은 앱 클라이언트
전용 교환이라 그대로 가져다 쓸 수 없습니다.

### 운영 토큰(`alleyo_`)을 쓴다

이미 있고, 읽기도 쓰기도 됩니다. 기각한 이유는 그것이 스토어 전체를 만지는
자격증명이라서입니다. 워커를 폐기하고 스토어 앱을 갈아끼울 수 있는 값을 앱 하나
만드는 사람에게 줄 수 없습니다.

## 나쁜 점

**자격증명 종류가 다섯으로 늘어납니다.** 각각 발급 화면과 폐기 화면이 필요하고,
"이 토큰이 무엇이었더라" 를 사람이 가려야 할 자리가 하나 더 생깁니다. 접두사로
갈리게 해뒀지만 그것은 기계를 위한 장치입니다.

**새면 반경이 배포 토큰보다 넓습니다.** 그 사람이 속한 앱 전부입니다. 그래서 만료를
두고(90일), 마지막 사용 시각을 남기고, 내 설정에서 언제든 끊을 수 있게 합니다. 그래도
도난당한 토큰이 90일까지 살아 있을 수 있다는 사실은 남습니다.

**할 수 있는 일이 도구보다 넓습니다.** 지우는 것은 막았지만 만드는 것과 고치는 것은
그대로 됩니다. 앱 설정을 바꾸거나 버전을 출시하는 것이 토큰만으로 됩니다. 에이전트가
그 값을 쥐고 90일을 사는 셈이라, scope 로 좁힌 쪽보다는 여지가 큽니다. 실제로 사고가
나면 그때 좁히는 ADR 을 새로 씁니다.

**`DELETE` 로 거르는 것은 모양에 기댄 규칙입니다.** 지금은 지우는 동작이 전부
`DELETE` 이거나 화면 경로에 있지만, 누군가 `POST .../purge` 를 만들면 그 규칙을
빠져나갑니다. 그런 경로를 더할 때 이 자리를 함께 봐야 합니다.

**사람이 떠날 때 함께 죽어야 합니다.** 그래서 사용자 비활성화를 이 작업보다 먼저
넣고, 비활성화에 토큰 끊기를 묶습니다. 손으로 끊는 방식으로 먼저 내는 안도 있었지만,
손으로 하는 일은 빠집니다. 나간 사람의 토큰이 90일 살아 있는 것은 위 항목과 겹쳐서
특히 나쁩니다.

**MCP 가 할 수 있는 일이 화면과 어긋날 수 있습니다.** 권한을 멤버십에서 끌어오기로
했으니 화면과 같은 판단을 써야 하는데, 지금 그 판단은 웹 컨트롤러 안에 흩어져
있습니다. 어긋나면 화면에서 막힌 것이 MCP 로는 되는 상태가 생깁니다.

## 결과

- 사용자 비활성화가 선행 조건이 됩니다. 그것부터 넣고 토큰 끊기를 묶습니다
- 사용자 토큰 모델과 인증 미들웨어가 하나 늘어납니다. 기존 넷과 같은 모양(원문은
  저장하지 않고 SHA-256 해시만, 발급 직후 한 번만 노출)을 따릅니다
- 권한 판단을 한 곳으로 모아야 합니다. `AppAccess` 가 그 자리입니다. 화면과 토큰이
  같은 답을 내야 하는데 지금 그 판단은 웹 컨트롤러에 흩어져 있습니다
- MCP 서버는 이 토큰 하나만 설정으로 받습니다. 앱 목록은 서버에 물어봅니다
- 배포 토큰은 아무것도 바뀌지 않습니다. CI 는 지금 쓰던 것을 그대로 씁니다
