# ADR-0016: 피드백 스크린샷은 서버가 직접 받는다

- 상태: 수락됨
- 날짜: 2026-09-01

## 맥락

ADR-0009 에서 바이너리는 서버를 거치지 않기로 했습니다. 클라이언트가 presigned URL
로 스토리지와 직접 주고받고, 서버는 "무엇이 어디 있는가"만 관리합니다. 수백 MB 짜리
앱이 서버 메모리와 대역폭을 왕복하면 서버가 병목이 되기 때문입니다.

Phase 3 의 피드백에는 스크린샷 첨부가 있습니다. 같은 규칙을 그대로 적용하면 화면과
앱 양쪽에 "자리를 받아서 → 올리고 → 알린다"는 세 단계가 또 생깁니다. 웹에서는 그
세 단계를 밟으려고 스크립트가 필요하고, 그건 ADR-0012 에서 업로드 화면 하나로
한정하기로 한 것을 넓히는 일입니다.

그런데 스크린샷은 앱 바이너리와 크기가 두 자릿수 다릅니다. 화면 하나를 찍으면 보통
수백 KB, 레티나 전체 화면이라도 수 MB 입니다.

## 결정

**8MB 이하의 이미지는 서버가 직접 받아 스토리지에 넣습니다.**

- 라우트 하나에만 본문 상한을 겁니다. 서버 전체 기본값(`1mb`)은 그대로 둡니다
- `Content-Type` 이 `image/*` 인 것만 받습니다
- 저장 자리는 아티팩트와 같은 버킷의 다른 경로(`feedback/<id>/screenshot`)입니다
- 내려줄 때는 아티팩트와 같게 만료 있는 URL 을 씁니다

**앱 바이너리에는 이 경로를 쓰지 않습니다.** ADR-0009 는 그대로입니다.

## 대안과 기각 사유

**모든 업로드에 presigned URL 을 쓴다 (ADR-0009 를 예외 없이 적용)** — 규칙이 하나라
설명할 것이 없고, 나중에 큰 첨부가 생겨도 그대로 갑니다. 그러나 웹 콘솔의 피드백
폼에 스크립트가 들어갑니다. 지금 그 화면은 폼 하나로 끝나는데, 이미지 하나 때문에
"자리 받기 → PUT → 통지" 를 자바스크립트로 붙이면 ADR-0012 에서 그은 선이 무너집니다.
서버 부담도 실제로는 다릅니다. 8MB 는 앱 바이너리의 1/50 이하입니다.

**첨부를 아예 넣지 않는다** — 가장 단순합니다. 그러나 "메모가 사라진다"는 신고에
화면 하나가 붙는 것과 아닌 것은 고치는 쪽에서 차이가 큽니다. 계획에 넣은 이유가
그것입니다.

**스토어 앱에서만 첨부를 지원한다** — 앱에서는 presigned 세 단계를 밟아도 스크립트
문제가 없습니다. 그러나 같은 기능이 화면마다 있고 없으면 사용자가 어디서 무엇을 할
수 있는지 외워야 합니다.

## 결과

**좋은 점**

- 웹 콘솔의 피드백 폼이 폼 하나로 끝납니다. 스크립트가 늘지 않습니다
- 서버가 파일을 직접 보므로 형식과 크기를 그 자리에서 검사합니다. presigned 로 올린
  것은 다 올라온 뒤에야 확인할 수 있습니다
- 스크린샷을 지울 때 스토리지에서도 함께 지웁니다. 피드백을 지우면 이미지가 남지
  않습니다

**나쁜 점**

- **전송 경로가 둘이 됐습니다.** "이 파일은 어느 쪽으로 올리는가"를 판단해야 하고,
  그 경계가 이 문서와 코드 주석에만 있습니다
- 8MB 는 임의의 숫자입니다. 레티나 전체 화면 PNG 를 담을 만한 크기로 골랐지만,
  누군가 큰 이미지를 올리려다 막히면 이유가 바로 보이지 않습니다
- 이미지가 서버 메모리를 지납니다. 동시에 여러 명이 올리면 그만큼 쌓입니다.
  사내 규모에서는 문제가 되지 않지만 공짜는 아닙니다
- `Content-Type` 을 믿습니다. 이미지가 아닌 것을 이미지라고 말하며 올릴 수 있습니다.
  받는 쪽이 브라우저의 `img` 태그라 실행 위험은 낮지만, 내용을 확인하지는 않습니다

**후속**

- 첨부가 늘어나면(로그 파일, 진단 정보) 그때는 presigned 로 옮기는 것을 검토합니다.
  경계가 "이미지 하나"에서 넓어지는 순간 이 결정의 근거가 약해집니다
- 이미지 내용 검사(매직 넘버 확인)를 붙일지는 실제로 문제가 생기면 정합니다
