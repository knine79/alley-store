# ADR-0011: 스토어 설정을 데이터베이스로 옮기고 환경변수는 씨앗으로만 쓴다

- 상태: 수락됨
- 날짜: 2026-08-18

## 맥락

ADR-0003에서 조직 고유값을 코드 밖으로 몰아내면서 전부 환경변수로 받았습니다.
스토어 이름, 로고, 강조색, 허용 로그인 도메인, 번들 ID 프리픽스까지 모두요.

그런데 설계 문서에는 `store_settings` 테이블이 있었습니다. 코드와 설계가 어긋난
채로 여기까지 왔고, 웹 콘솔에 "스토어 설정" 화면을 만들려는 시점에 드러났습니다.
환경변수는 화면에서 바꿀 수 없습니다. 바꾸려면 `.env`를 고치고 서버를 다시
띄워야 하고, 그건 배포 권한이 있는 사람만 할 수 있습니다.

스토어 이름을 바꾸려고 배포를 하는 것은 과합니다.

## 결정

설정을 두 갈래로 나눕니다.

### 데이터베이스로 옮기는 것

`store_settings` 테이블(행 하나)에 두고 관리자가 화면에서 바꿉니다.

- 스토어 이름, 로고 URL, 강조색
- 로그인 허용 이메일 도메인
- 번들 ID 프리픽스와 강제 여부

### 환경변수에 남기는 것

각각 화면에 둘 수 **없는** 이유가 있습니다.

| 설정 | 남기는 이유 |
| --- | --- |
| `DATABASE_URL` | 데이터베이스 주소를 데이터베이스에서 읽을 수 없습니다 |
| `S3_*`, `JWT_SECRET`, `GOOGLE_CLIENT_SECRET` | 비밀값입니다. 관리자 화면에 띄울 이유가 없습니다 |
| `GOOGLE_CLIENT_ID`, `OAUTH_REDIRECT_URI` | 공급자 쪽에 등록된 값이라 우리 서버 혼자 바꿔봐야 소용없습니다 |
| `PUBLIC_BASE_URL` | 부팅에 필요합니다 |
| `INITIAL_ADMIN_EMAILS` | 관리자가 0명일 때 첫 관리자를 만드는 값입니다. 관리자만 바꿀 수 있는 곳에 두면 닭과 달걀입니다 |
| `STORE_APP_URL_SCHEME` | 스토어 앱 `Info.plist`에 박히는 값입니다. 서버 혼자 바꾸면 이미 깔린 앱의 로그인 콜백이 깨집니다. 앱과 서버가 함께 바뀌어야 하는 값입니다 |

### 씨앗 규칙

행이 없으면 환경변수 값으로 **한 번** 만듭니다. 그 뒤로는 데이터베이스가 진실이고
환경변수는 무시합니다.

씨앗을 마이그레이션이 아니라 최초 접근 시점에 심습니다. 마이그레이션은
`alley-server migrate`라는 별도 명령으로 도는데, 그 시점의 환경변수가 서버 프로세스와
같다는 보장이 없기 때문입니다.

### 위험한 항목에는 확인을 요구한다

허용 도메인을 비우면 조직 밖 계정도 전부 로그인합니다. 예전에는 서버를 다시
배포해야 바꿀 수 있어서 그 자체가 장벽이었는데, 화면에서 바꾸게 되면서 사라졌습니다.

목록을 비우는 요청은 `confirmOpenToAnyDomain`을 함께 보내야 통과합니다. 그리고
설정을 바꾼 사람을 행에 남기고 로그에 적습니다.

## 대안과 기각 사유

**환경변수를 그대로 둔다** — 설정이 한 곳에만 있어서 "어느 쪽이 진짜인가"를 물을
일이 없습니다. 배포 파이프라인에 설정이 코드처럼 남는다는 장점도 있습니다.
그러나 스토어 이름을 고치려고 배포를 해야 하고, 그 권한이 없는 관리자는 아무것도
못 합니다. 셀프호스팅으로 배포하는 제품에서 이건 실질적인 제약입니다.

**환경변수가 데이터베이스를 덮어쓴다(환경변수 우선)** — 배포 시점에 설정을 확실히
고정할 수 있습니다. 그러나 관리자가 화면에서 바꾼 값이 재시작할 때마다 조용히
되돌아갑니다. 화면에 저장 버튼이 있는데 저장이 안 되는 것처럼 보이는 것이 가장
나쁜 조합입니다.

**전부 데이터베이스로 옮긴다** — 규칙이 하나뿐이라 설명하기 쉽습니다. 그러나
데이터베이스 주소는 논리적으로 불가능하고, 비밀값을 평문으로 넣으면 데이터베이스
백업이 곧 자격증명 유출입니다. `INITIAL_ADMIN_EMAILS`는 관리자가 없을 때 쓰는
값이라 관리자만 바꿀 수 있는 곳에 둘 수 없습니다.

**씨앗을 마이그레이션에서 심는다** — 스키마와 초기 데이터가 한 곳에 모입니다.
그러나 마이그레이션은 서버와 다른 프로세스로 도는 별도 명령입니다. 그 시점의
환경변수가 서버와 같다고 가정하면, CI에서 마이그레이션만 돌릴 때 엉뚱한 값이
심깁니다.

**설정을 메모리에 캐시한다** — 요청마다 조회가 사라집니다. 그러나 서버가 여러
대일 때 한 대에서 바꾼 값이 다른 대의 캐시에 반영되지 않습니다. 조용히 낡은
설정으로 도는 것보다 기본키 조회 한 번이 낫다고 봤습니다. 로그인 허용 도메인처럼
보안에 걸린 값이라 더 그렇습니다.

## 결과

**좋은 점**

- 관리자가 배포 없이 브랜딩과 정책을 바꿉니다
- 설계 문서의 `store_settings`와 코드가 처음으로 일치합니다
- 바뀐 값이 다음 요청부터 즉시 반영됩니다. 재시작이 필요 없습니다
- `.env`만 채우면 일단 뜨는 셀프호스팅 경험은 그대로입니다

**나쁜 점**

- **`/api/v1/meta`가 데이터베이스에 의존하게 됐습니다.** 데이터베이스가 죽으면
  스토어 앱이 부트스트랩조차 못 합니다. 예전에는 프로세스만 살아 있으면 됐습니다
- 요청마다 설정 조회가 한 번씩 늘어납니다. 기본키 조회라 지금 규모에서는 무시할
  수 있지만 공짜는 아닙니다
- **로그인 허용 도메인을 바꾸는 장벽이 낮아졌습니다.** 확인 절차와 기록으로
  보완했지만, 배포 권한이 필요하던 것이 관리자 권한으로 내려온 것은 사실입니다
- 설정이 두 곳에 있습니다. "이 값은 어디서 바꾸나"를 매번 판단해야 하고, 그
  경계가 이 문서에만 적혀 있습니다
- 씨앗 규칙이 직관적이지 않습니다. `.env`를 고쳤는데 아무 일도 안 일어나는 상황을
  처음 겪으면 당황합니다

**후속**

- 설정 변경 이력을 별도 표로 남기는 것이 필요할 수 있습니다. 지금은 마지막으로
  바꾼 사람만 남고, 무엇을 무엇으로 바꿨는지는 로그에만 있습니다
- 데이터베이스가 죽었을 때 `/api/v1/meta`가 마지막으로 읽은 값으로라도 응답하게
  할지 판단이 필요합니다. 그건 위에서 기각한 캐시를 다른 이유로 다시 꺼내는 일입니다
