# ADR-0004: Docker 셀프호스팅을 기본 배포 단위로 삼는다

- 상태: 수락됨
- 날짜: 2026-08-12

## 맥락

서버를 어디에 어떻게 띄울지 정해야 합니다. 조직 내부 운영은 그 조직의 컨테이너
플랫폼에 올릴 예정이지만, 오픈소스 사용자는 각자 다른 환경을 씁니다.

특정 플랫폼에 맞춘 배포 산출물을 만들면 그 플랫폼을 안 쓰는 사람은 처음부터
막힙니다.

## 결정

산출물은 표준 Docker 이미지와 `docker-compose.yml`입니다. 어떤 호스팅 환경도
전제하지 않습니다.

- `docker compose up` 한 번으로 서버 + PostgreSQL + S3 호환 스토리지(MinIO)가 뜹니다
- 스토리지는 S3 호환 API로 추상화합니다. 로컬과 셀프호스팅은 MinIO를 쓰고, AWS S3를
  쓰려면 엔드포인트만 비웁니다
- 이미지는 멀티스테이지로 만들고 비루트 사용자로 돌립니다
- 조직별 배포 매니페스트는 이 레포 밖에 둡니다 (ADR-0003)

업로드·다운로드는 presigned URL로 스토리지에 직접 오갑니다. 서버가 큰 바디를 받을
일이 없어 바디 상한을 낮게 잡습니다.

## 대안과 기각 사유

**Firebase (Auth + Firestore + Storage)** — 구축이 가장 빠릅니다. 그러나 오픈소스
사용자도 각자 Firebase 프로젝트를 만들어야 해서 셀프호스팅 진입장벽이 생기고,
데이터가 특정 벤더에 묶입니다.

**특정 컨테이너 플랫폼 전용 매니페스트를 산출물로** — 조직 내부 운영은 편해집니다.
그러나 그 플랫폼을 안 쓰는 사람은 배포할 수 없고, ADR-0003의 조직 중립 원칙에
어긋납니다.

**파일시스템에 아티팩트 저장** — 스토리지 의존성이 사라져 구성이 단순해집니다.
그러나 컨테이너를 여러 개 띄우면 공유 볼륨이 필요하고, presigned URL로 클라이언트가
직접 주고받는 구조를 못 씁니다. 큰 바이너리가 전부 서버를 통과하게 됩니다.

## 결과

**좋은 점**
- 조직 내부 운영은 이 이미지를 컨테이너 플랫폼에 올리기만 하면 됩니다
- 오픈소스 사용자는 추가 계정 없이 로컬에서 전체 스택을 띄웁니다
- 대용량 전송이 서버를 통과하지 않습니다

**나쁜 점**
- MinIO와 PostgreSQL을 함께 운영해야 해서 구성요소가 늘어납니다
- Swift 서버 이미지 빌드가 느립니다. CI 캐싱이 필수입니다
- presigned URL 만료 시간을 잘못 잡으면 대용량 업로드가 중간에 실패합니다

**후속**
- 대용량 업로드는 S3 multipart를 씁니다. MVP는 단순 재시도로 가고 재개 가능
  업로드는 후속으로 미룹니다
