# ADR-0024: 스토리지 설정을 프리픽스·공개 주소·선택 자격증명으로 나눈다

- 상태: 수락됨
- 날짜: 2026-09-03

## 맥락

지금까지 스토리지 설정은 셀프호스팅 MinIO 하나만 상정했습니다
([ADR-0004](0004-docker-selfhosting-s3-abstraction.md)). 그 전제가 관리형 쿠버네티스
샌드박스에 처음 올리면서 세 군데에서 깨졌습니다. 셋 다 배포를 막는 문제입니다.

**1. 버킷 루트에 씁니다.** `ArtifactStorage.objectKey` 가 `apps/...` 로 시작하는 키를
만들어 버킷 루트에 바로 놓습니다. 배포 대상은 버킷 하나를 여러 프로젝트가 나눠 쓰고
각 프로젝트가 그 안의 프리픽스 하나만 소유하는 구조입니다. 루트에 쓰면 권한에서
막힙니다.

**2. 액세스 키를 필수로 요구합니다.** `S3_ACCESS_KEY_ID` 와 `S3_SECRET_ACCESS_KEY` 가
`required` 였습니다. 인스턴스에 붙은 역할로 인증하는 환경(IRSA 계열)은 액세스 키를
아예 발급하지 않습니다. 서버가 뜨지도 못합니다.

**3. `S3_ENDPOINT` 하나가 두 가지 일을 합니다.** 같은 값이 (a) 서버가 스토리지에 붙는
주소이면서 (b) 브라우저와 스토어 앱에 내주는 presigned URL 의 기반 주소입니다
(`ArtifactStorage.objectBase`). compose 는 이것을 `http://minio:9000` 으로 덮어쓰는데,
그 이름은 컨테이너 안에서만 풀립니다. 로컬 개발에서 안 걸린 이유는
`http://localhost:9000` 이 양쪽 모두에서 통했기 때문입니다.

## 결정

환경변수 셋을 더하고, 액세스 키를 선택으로 바꿉니다.

### `S3_KEY_PREFIX`

버킷 안에서 이 서버가 쓰는 자리. 없으면 지금 동작 그대로입니다.

- `foo`, `foo/`, `/foo/` 를 모두 같은 값으로 봅니다. 앞뒤 슬래시와 공백을 떼어
  정규화합니다. 그대로 이어붙이면 `//` 가 생기는데, S3 는 그것을 빈 이름의 디렉터리로
  받아들여 **틀린 채로 조용히 동작합니다**
- 아티팩트(`apps/...`)와 피드백 스크린샷(`feedback/...`,
  [ADR-0016](0016-server-handles-small-uploads.md)) 양쪽에 같은 프리픽스가 붙습니다.
  둘은 같은 버킷을 쓰고, 프리픽스는 "버킷 안에서 우리가 소유한 자리"를 뜻하므로 한쪽만
  나갈 이유가 없습니다
- **프리픽스는 새로 만드는 키에만 붙습니다.** `artifacts.storage_key` 와
  `feedbacks.screenshot_key` 에 이미 저장된 값이 곧 전체 키입니다. 읽을 때는 저장된
  값을 그대로 씁니다. 마이그레이션으로 기존 값을 건드리지 않습니다. 프리픽스를 나중에
  켜도 이미 올라간 오브젝트는 원래 자리에서 계속 읽힙니다

프리픽스를 붙이는 자리는 `ArtifactStoring.newKey(_:)` 한 곳입니다. 이름이 "새 키"라고
말하고 있어서, 저장된 키에 이걸 쓰면 안 된다는 것이 호출부에서 보입니다.

### `S3_PUBLIC_ENDPOINT`

클라이언트에게 내주는 주소. 안 주면 `S3_ENDPOINT` 를 그대로 씁니다(지금 동작).

이름은 이미 있는 `PUBLIC_BASE_URL` 을 따랐습니다. 이 레포에서 "public" 은 일관되게
"밖에서 닿는 주소"를 뜻합니다.

**presigned URL 의 서명은 호스트를 포함해서 계산됩니다.** 한 호스트로 서명하고 다른
호스트로 내주면 스토리지가 거절합니다. 그래서 `objectBase` 는 공개 주소가 있으면 그것으로
만들고, S3 클라이언트의 엔드포인트(서버가 붙는 곳)와 갈라집니다. Soto 의
`signURL(url:...)` 은 넘긴 URL 을 그대로 서명하므로, presign 전용 클라이언트를 따로 둘
필요는 없습니다. 서비스 설정에서 가져다 쓰는 것은 리전과 자격증명뿐입니다.

MinIO 로 확인했습니다. `127.0.0.1:9000` 을 내부, `localhost:9000` 을 공개로 두고 서명한
URL 은 `PUT`·`GET` 이 모두 200 이고, 같은 URL 의 호스트만 `127.0.0.1` 로 바꾸면 403 입니다.

### 액세스 키는 선택

`S3_ACCESS_KEY_ID` 와 `S3_SECRET_ACCESS_KEY` 를 둘 다 비우면 SDK 기본 자격증명 체인을
씁니다. Soto 7 의 `CredentialProviderFactory.default` 는 리눅스에서
`환경변수 → ECS → EC2 → ~/.aws → SSO → login` 순입니다. 첫 단계인 "환경변수" 가
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` 를 먼저 보고, 없으면 `AWS_ROLE_ARN`,
`AWS_ROLE_SESSION_NAME`, `AWS_WEB_IDENTITY_TOKEN_FILE` 로 STS `AssumeRoleWithWebIdentity`
를 부릅니다. IRSA 계열이 여기로 들어옵니다.

**하나만 주면 기동을 막습니다.** 그대로 뜨면 기본 체인으로 조용히 넘어가서, 방금 넣은
키가 왜 안 먹는지 아무도 모르게 됩니다.

### presigned URL 의 수명

`S3_PRESIGNED_URL_TTL` 은 **상한일 뿐입니다.** 임시 자격증명(STS)으로 서명한 URL 은
그 세션 토큰이 죽으면 함께 죽습니다. 실제 수명은
`min(TTL, 서명에 쓴 세션 토큰의 남은 수명)` 입니다.

Soto 는 `AssumeRoleWithWebIdentity` 에 `DurationSeconds` 를 주지 않으므로 AWS 기본값
1시간이 적용되고, 역할의 최대 세션 길이로 다시 잘립니다. Soto 는 남은 수명이 165초
아래로 내려가면 자격증명을 갱신하지만, **이미 내준 URL 은 갱신 대상이 아닙니다.**
그러니까 최악의 경우 기본값 3600초로 발급한 업로드 URL 이 3분 만에 죽을 수 있습니다.

이 계산은 Soto 소스로 확인했고, **실제 STS 환경에서는 아직 확인하지 못했습니다.**
로컬에 세울 수 있는 것이 MinIO 뿐이고 MinIO 는 정적 키를 씁니다. 배포 환경에서 실제로
겪는 수명은 첫 배포 때 재봐야 합니다. 증상은 [운영 가이드](../operations.md)에 적었습니다.

## 대안과 기각 사유

**프리픽스 대신 버킷 이름으로 나눈다** — 설정이 늘지 않고, 이미 있는 `S3_BUCKET` 만
바꾸면 됩니다. 권한 경계도 버킷 단위가 프리픽스 단위보다 다루기 쉽고, 수명 정책이나
버저닝도 버킷에 붙습니다. 그러나 배포 대상이 버킷을 프로젝트마다 만들어주지 않습니다.
버킷 하나를 공유하고 프리픽스 하나를 주는 것이 그쪽의 모델이라, 우리가 고를 수 있는
선택지가 아니었습니다. 버킷을 따로 받을 수 있는 환경이라면 `S3_KEY_PREFIX` 를 비우고
`S3_BUCKET` 만 쓰면 됩니다. 그 길을 막지는 않습니다.

**스토리지를 프로젝트마다 따로 둔다 (MinIO 를 우리가 함께 배포)** — 프리픽스도 공개
주소 분리도 필요 없어집니다. 지금 compose 가 하는 그대로를 쿠버네티스로 옮기면 되고,
자격증명도 우리가 만든 정적 키라 수명 문제가 없습니다. 그러나 상태를 가진 것을 하나 더
운영하게 됩니다. 볼륨, 백업, 용량, 업그레이드가 전부 우리 몫이 됩니다. 샌드박스가
관리형 스토리지를 이미 주는데 그 옆에 우리 것을 세우는 것은, 첫 배포에서 확인하려는
것(전체 루프가 도는가)과 상관없는 일을 늘립니다.

**공개 주소를 리버스 프록시로 맞춘다** — 서버가 붙는 주소와 브라우저가 붙는 주소를
프록시가 같은 이름으로 보이게 하면 코드를 안 고쳐도 됩니다. 실제로 클러스터 안에서
외부 도메인이 그대로 풀리게 하는 구성(split-horizon DNS)이면 오늘도 동작합니다. 그러나
그것을 이 레포가 요구하면, 셀프호스팅하는 사람이 스토리지 앞에 프록시를 세우고 DNS 를
맞춰야 서버가 뜹니다. 설정 한 줄로 끝날 일에 인프라 전제를 얹는 것은
[ADR-0003](0003-organization-neutral-by-construction.md) 과 어긋납니다. 게다가 프록시가
헤더나 경로를 조금이라도 손대면 서명이 깨지는데, 그 실패는 403 이라 프록시를 의심하기까지
오래 걸립니다.

**액세스 키를 계속 필수로 두고, 역할 인증이 필요하면 키를 만들어 넣는다** — 코드가
그대로고, 자격증명이 하나뿐이라 무엇으로 인증되는지 헷갈릴 일이 없습니다. presigned URL
수명도 TTL 그대로입니다. 그러나 배포 대상이 액세스 키를 발급하지 않습니다. 만들 수
있더라도, 장기 키를 시크릿으로 심는 것은 역할 인증을 쓰는 이유(키가 새어도 만료된다)를
버리는 일입니다.

## 결과

**좋은 점**
- 버킷을 공유하는 환경에 그대로 올라갑니다. 프리픽스를 안 주면 예전과 같습니다
- 액세스 키 없이 뜹니다. 인스턴스에 붙은 역할로 인증하는 환경을 지원합니다
- 서버가 붙는 주소와 클라이언트가 붙는 주소가 달라도 됩니다. 첫 배포를 막던 문제입니다
- 기존 데이터를 건드리지 않습니다. 마이그레이션이 없습니다

**나쁜 점**
- **설정이 세 개 늘었습니다.** 틀릴 자리가 셋 늘었다는 뜻이기도 합니다. 특히
  `S3_ENDPOINT` 와 `S3_PUBLIC_ENDPOINT` 는 이름이 비슷해서 바꿔 넣기 쉽습니다
- **내부 주소와 공개 주소가 어긋나면 증상이 403 입니다.** 서명이 호스트에 묶여 있어서,
  주소를 틀리면 "못 찾음" 이 아니라 "권한 없음" 이 나옵니다. 키를 잘못 넣었을 때와
  구분되지 않아 원인을 찾기 어렵습니다. 서버 로그에는 아무것도 남지 않습니다. 서명은
  서버가 하고 거절은 스토리지가 하기 때문입니다
- **presigned URL 수명이 자격증명 종류에 따라 달라집니다.** 정적 키면 TTL 대로, 임시
  자격증명이면 그보다 짧습니다. 얼마나 짧은지는 URL 을 언제 받았느냐에 달려 있어서
  재현이 안 됩니다. "어제는 됐는데 오늘은 안 된다" 로 보고될 종류의 문제입니다
- **프리픽스를 바꾸는 시점에 진행 중이던 것은 깨집니다.** 업로드 URL 을 받아두고 아직
  안 올린 `draft`, 워커가 물고 있는 서명 잡이 그렇습니다. 서버가 새 프리픽스로 키를
  다시 만들기 때문입니다. 다시 올리면 됩니다. 프리픽스는 배포할 때 정하고 그 뒤로
  건드리지 않는 값으로 다루세요
- 기본 자격증명 체인은 **아무것도 못 찾아도 기동을 막지 않습니다.** Soto 가 체인
  끝에서 "언제나 실패하는" 제공자를 놓기 때문입니다. 실패는 스토리지를 처음 쓰는
  순간에 나옵니다. 기동 시점에 자격증명을 한 번 받아보게 할 수도 있었지만, 그러면
  메타데이터 응답이 느린 순간에 서버가 아예 안 뜹니다. 대신 그 실패를 알아볼 수 있는
  말로 바꿔서 던집니다(`ArtifactStorage.StorageError.noCredentials`)

**후속**
- 실제 STS 환경에서 presigned URL 이 얼마나 사는지 재기. 그 결과에 따라
  `S3_PRESIGNED_URL_TTL` 기본값을 낮추거나, 자격증명 만료 시각을 보고 TTL 을 스스로
  줄이는 것을 검토합니다
- `DRAFT_RETENTION_HOURS` 는 여전히 `S3_PRESIGNED_URL_TTL` 을 기준으로 잡혀 있습니다
  ([ADR-0019](0019-abandoned-draft-cleanup.md)). URL 이 실제로는 더 짧게 산다면 그
  여유는 더 넉넉해질 뿐이라 지금은 문제가 없습니다
