# ADR-0030: 번들 속성은 브라우저가 zip 을 열어 읽는다

- 상태: 수락됨
- 날짜: 2026-09-08

## 맥락

올리는 사람이 손으로 옮겨 적는 값이 여섯 개입니다.

| 화면 | 사람이 적는 것 | 번들이 이미 아는 것 |
| --- | --- | --- |
| 새 앱 등록 | 번들 ID, 이름, 한 줄 소개, 설명, 분류 | 번들 ID, 이름 |
| 버전 업로드 | 버전, 빌드 번호, 최소 macOS, 릴리즈 노트 | 앞의 셋 |

번들 ID 는 서명 전에 대조하므로(ADR-0029) 틀리면 막힙니다. **막히는 것을 올린
다음에 아는 것이 문제입니다.** 등록하고, 빌드를 올리고, 워커가 집어가고, 그때서야
"번들 ID 가 다릅니다" 를 봅니다. 그 사이 시간과 전송은 이미 썼습니다.

버전·빌드·최소 macOS 는 아예 아무도 검사하지 않습니다. 잘못 적으면 스토어에 잘못된
버전으로 표시되고, 그것을 고치는 방법은 버전을 다시 올리는 것뿐입니다.

[ADR-0012](0012-browser-upload-script.md) 는 **업로드 화면만** 자바스크립트를 쓴다고
정했습니다. 그 화면은 스크립트가 없으면 동작하지 않습니다. 브라우저가 스토리지로
직접 올리면서 진행률을 보여줘야 하기 때문입니다. 새 앱 등록 화면은 다릅니다. 폼을
`POST` 하면 그대로 됩니다. 그 화면에 스크립트를 넣는 것은 경계를 넓히는 일입니다.

## 결정

**브라우저가 고른 zip 을 열어 `Info.plist` 를 읽고 입력칸을 채웁니다.**

`Public/bundle-info.js` 가 그 일을 합니다. zip 의 중앙 디렉터리만 읽어 최상위
`<무엇>.app/Contents/Info.plist` 항목 하나를 꺼내 압축을 풉니다. 파일을 통째로
메모리에 올리지 않습니다. 29MB Electron 앱으로 확인했습니다.

### 스크립트 경계를 두 갈래로 나눕니다

ADR-0012 의 결정은 뒤집지 않습니다. 대신 기준을 다시 씁니다.

- **없으면 안 되는 곳**: 업로드 화면. 스크립트가 없으면 `<noscript>` 로 CLI 를
  안내합니다
- **없어도 되는 곳**: 그 밖에. 스크립트는 타이핑을 덜어주기만 하고, 없으면 화면이
  예전처럼 동작해야 합니다

두 번째 갈래에는 규칙이 하나 붙습니다. **스크립트가 없을 때 아무 일도 하지 않는
컨트롤은 감춥니다.** 새 앱 등록 화면의 파일 칸은 HTML 에서 `hidden` 이고
`app-new.js` 가 벗깁니다. 눌러도 아무 일이 없는 칸을 보여주면 고장으로 읽힙니다.

### XML 과 바이너리 plist 를 모두 읽습니다

이 머신의 `/Applications` 를 세어보니 50개 중 10개가 바이너리였습니다. Xcode 로
만든 앱이 그렇고 Electron 앱은 XML 입니다. 한쪽만 읽으면 자동 채우기가 앱의 종류에
따라 되기도 하고 안 되기도 합니다. 그건 기능이 없는 것보다 나쁩니다.

### 사람이 적은 값은 덮지 않습니다

번들의 값이 칸과 다르면 덮는 대신 무엇이 다른지 알립니다. 일부러 다르게 적는
경우가 있고(핫픽스 빌드 번호), 조용히 되돌리면 적은 사람은 사라진 것을 모릅니다.

**서버가 제안한 값은 사람이 적은 값이 아닙니다.** 빌드 번호 칸에는 서버가 다음
번호를 미리 넣어둡니다. 그것까지 지키면 그 칸은 영영 안 채워집니다. `data-suggested`
로 표시해 구별합니다. 이건 실제로 브라우저로 돌려보고서야 나온 버그입니다.

### 실패는 업로드를 막지 않습니다

읽지 못하면 그 칸 아래 설명으로 알리고 직접 적으라고 합니다. 빨간 배너를 띄우면
올리지 말라는 뜻으로 읽힙니다. 자동 채우기가 실패하는 것은 업로드가 실패하는 것이
아닙니다.

## 대안과 기각 사유

**서버가 읽는다** — 브라우저에 파서를 넣지 않아도 되고, 값을 신뢰할 수 있게 되며
자동 채우기가 아니라 검증으로 쓸 수도 있습니다. 가장 그럴듯한 대안이었습니다.

기각한 이유는 [ADR-0029](0029-verify-bundle-identifier-before-signing.md) 와 같습니다.
지금 서버는 아티팩트를 한 번도 열지 않습니다. 신뢰할 수 없는 zip 을 서버 프로세스
안에서 풀기 시작하면 zip bomb 과 경로 탈출을 스스로 감당해야 하고, 앱 하나 크기의
디스크와 전송이 컨테이너에 필요해집니다. 게다가 **등록 화면에서는 아직 올릴 파일도
없습니다.** 값을 채우자고 파일을 먼저 서버에 보내는 것은 순서가 뒤집힌 일입니다.

**CLI 에만 넣는다** — 브라우저 코드를 늘리지 않고 ADR-0012 경계를 그대로 둡니다.
그러나 브라우저로 올리는 사람에게는 아무 도움이 안 됩니다. 화면에서 등록하는 것이
기본 경로인데 그 경로만 손으로 적게 남깁니다. CLI 쪽에도 나중에 넣을 만하고, 그때는
같은 값을 읽는 코드가 Swift 에 한 벌 더 생깁니다. 그 중복은 감당할 수 있습니다.
읽는 대상이 Apple 이 정한 고정 형식이라 두 구현이 어긋날 여지가 작습니다.

**zip 라이브러리를 쓴다** — 직접 쓴 파서보다 안전합니다. 그러나 CSP 가
`script-src 'self'` 라 CDN 에서 받을 수 없습니다(ADR-0026). 레포에 번들해 넣으면
빌드 스텝 없이 굴러가는 지금 구조에 최소화되지 않은 수백 KB 가 들어옵니다. 우리가
필요한 것은 "항목 하나 꺼내기" 하나뿐입니다.

**만들지 않는다** — 여섯 칸을 계속 손으로 적습니다. 번들 ID 는 이제 서명 전에
막히니 큰 사고는 안 납니다. 그러나 막힌 것을 아는 시점이 너무 늦고, 버전·빌드는
여전히 아무도 안 봅니다.

## 결과

**좋은 점**

- 번들 ID 오타를 등록하는 자리에서 잡습니다. 워커까지 갔다 오지 않습니다
- 버전·빌드·최소 macOS 를 번들이 말하는 그대로 넣습니다. 세 칸이 한 번에 채워집니다
- 값이 다를 때 무엇이 다른지 알려줍니다. 조용히 덮지 않습니다
- 스크립트가 없어도 두 화면 모두 예전처럼 동작합니다

**나쁜 점**

- **손으로 쓴 zip 파서와 바이너리 plist 파서가 레포에 생겼습니다.** 둘 다 형식을
  일부만 구현합니다. 이 레포에서 가장 "직접 만든 것" 에 가까운 코드이고, 앞으로
  이상한 zip 을 만나면 여기를 봐야 합니다
- **이 레포에는 자바스크립트 테스트 하네스가 없습니다.** 실제 Chrome 을 DevTools
  프로토콜로 붙여 확인했지만 그 절차는 CI 에 없습니다. 다음에 고치는 사람은 같은
  절차를 손으로 다시 만들어야 합니다. 하네스를 만드는 편이 낫지만 이 변경에
  끼워 넣지는 않았습니다
- **zip64 는 읽지 못합니다.** 4GB 를 넘거나 항목이 65535 개를 넘으면 사람에게
  직접 입력하라고 합니다
- `DecompressionStream` 이 필요합니다. Safari 16.4 (2023년 3월) 이상입니다. 그보다
  낮은 브라우저에서는 자동 채우기만 동작하지 않습니다
- 최상위 `.app` **하나만** 봅니다. zip 안에 앱이 여러 개면 첫 번째를 집습니다.
  워커는 그 경우를 실패로 다루므로(`bundle_layout_invalid`) 결국 막히지만, 화면은
  그 전에 엉뚱한 값을 채워둘 수 있습니다
- 버전 업로드 화면의 칸 순서를 바꿨습니다. 파일이 맨 위로 올라갔습니다. 자동
  채우기가 그래야 의미가 있는데, 그 화면에 익숙한 사람은 한 번 헤맵니다
