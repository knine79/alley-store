# ADR-0034: dmg 는 번들 ID 를 묻지 않고 워커가 정한다

- 상태: 수락됨
- 날짜: 2026-09-10

## 맥락

[ADR-0033](0033-drop-file-first-then-confirm.md) 에서 dmg 를 올릴 때 번들 ID 한 칸을
받았습니다. 브라우저가 디스크 이미지를 열 수 없어 미리 알 수 없고, 앱을 만들려면
`apps.bundle_id` 가 있어야 하기 때문이었습니다.

**그 한 칸이 실제로는 위험합니다.** 사람이 손으로 적으니 실제 번들과 어긋날 수
있고, 어긋나면 서명 직전에 막힙니다([ADR-0029](0029-verify-bundle-identifier-before-signing.md)).
수백 MB 를 다 보낸 뒤에 "번들 ID 가 다릅니다" 를 만나는데, 정작 올린 사람은 자기가
무엇을 잘못 적었는지 모릅니다. **번들 안에 이미 정답이 적혀 있는데 사람에게 옮겨
적으라고 한 셈입니다.**

`apps.id` 는 이미 임의의 UUID 이고 `bundle_id` 는 별도 UNIQUE 제약입니다. 막고 있던
것은 기본 키가 아니라 `NOT NULL` 하나였습니다.

## 결정

**dmg 를 놓으면 아무것도 묻지 않습니다.** 임시 번들 ID 로 앱을 만들고, 워커가 번들에서
읽은 값으로 확정합니다.

```
드롭 → (확인 창) → 업로드 → 워커가 번들을 열어 ID 를 읽음
                          → 정책에 맞나? ─ 아니오 → 서명 안 하고 실패
                                        └ 예   → 서버가 확정 → 서명·공증
```

### `bundle_id` 를 nullable 로 바꾸지 않습니다

그 칼럼은 앱의 정체성이고 UNIQUE 이며 수많은 조회가 매달려 있습니다. NULL 을
허용하면 그 조회마다 "없을 수도 있다" 를 다뤄야 합니다. 대신 `alley-pending.<uuid>`
를 넣고 **확정 전이라는 사실을 `bundle_id_pending` 에 따로 적습니다.**

### 정책 검사가 대조의 자리를 대신합니다

**이것이 이 결정의 핵심이자 유일한 문턱입니다.**

지금까지 두 검사가 있었습니다.

| 언제 | 무엇을 보나 |
| --- | --- |
| 등록할 때 | 적은 번들 ID 가 조직 접두어에 맞는가 |
| 서명 직전 | 올린 번들이 등록된 그 앱인가 (ADR-0029) |

번들 ID 를 안 받으면 첫 번째가 사라지고, 두 번째는 **대조할 등록값이 없어서** 함께
무력해집니다. 그대로 두면 아무 앱이나 올려서 조직 Developer ID 로 서명받을 수
있습니다. `com.apple.Safari` 를 올려도 막을 것이 없습니다.

그래서 접두어 검사를 **서명 직전으로 옮깁니다.** 잡 지시서에 조직 정책
(`requiredBundleIDPrefix`, `enforceBundleIDPrefix`)을 실어 보내고, 워커가 번들에서
읽은 ID 가 거기 맞는지 봅니다. 맞지 않으면 서명하지 않고 멈춥니다.

서버도 확정할 때 같은 검사를 한 번 더 합니다. 워커는 우리가 준 설정으로 판단하고
서버는 지금 설정으로 판단합니다. 그 사이 관리자가 정책을 바꿨을 수 있고, 정책의
주인은 서버입니다.

### 접두어 정책을 없애자는 제안은 받지 않았습니다

번들 ID 를 안 받으면 정책 검사도 필요 없어 보이지만 반대입니다. 사람이 아무 값도
적지 않게 되면서 **번들이 말하는 것을 그대로 받아들이게 되므로**, "우리 조직 것인가"
를 묻는 자리가 더 중요해집니다.

### 올리기 전에 한 번 확인받습니다

번들 ID 를 모른 채로 몇백 MB 를 보내는 일입니다. 규칙에 맞지 않으면 다 올린 뒤에
실패한다는 것을 그 전에 알려야 합니다. 브라우저 `confirm` 을 씁니다. 투박하지만
되돌리기 어려운 일 앞에서 멈춰 세우는 것이 목적이고, 직접 만들면 초점 가두기와 Esc
처리를 새로 만들어야 하는데 이 콘솔에 그런 장치가 없습니다.

### 임시값은 화면에 보이지 않습니다

앱 목록·상세·통계·확인 화면 모두 "확인 중" 으로 바꿔 그립니다. `alley-pending.<uuid>`
는 자리를 채우려고 넣은 값이지 그 앱의 정체성이 아닙니다.

**API 에는 진짜 값이 그대로 나갑니다.** `bundleIDPending` 이 함께 붙습니다. 가려서
내보내면 API 를 쓰는 쪽에 거짓말이 됩니다.

## 대안과 기각 사유

**`bundle_id` 를 nullable 로 바꾼다** — 임시값이라는 개념 자체가 없어져서 가장
깔끔합니다. 확정 여부를 따로 적을 필요도 없습니다(`NULL` 이면 확정 전). 그러나 그
칼럼을 읽는 모든 자리가 옵셔널을 다뤄야 합니다. 스토어 앱의 설치 대조, Sparkle 피드,
번들 ID 대장, 워커 지시서가 전부 그렇습니다. 임시값 하나를 없애자고 **확정된 앱을
다루는 코드 전부에 "없을 수도 있다" 를 퍼뜨리는** 맞바꿈입니다.

**dmg 도 지금처럼 번들 ID 를 받는다** — 스키마를 안 건드리고, 위반과 중복을 올리기
전에 잡습니다. 그러나 번들 안에 이미 있는 값을 사람이 옮겨 적는 일이고, 틀리면
업로드가 통째로 헛일이 됩니다.

**접수(intake) 테이블을 새로 만든다** — 앱도 버전도 아닌 상태를 제대로 표현합니다.
그러나 새 상태 흐름과 그것을 청소하는 장치가 따라옵니다. 임시 번들 ID 는 기존
테이블 안에서 같은 일을 합니다.

**접두어 정책을 없앤다** — 번들 ID 를 안 받는 것과 잘 맞아 보입니다. 그러나 위에
적은 대로 조직 Developer ID 로 무엇을 서명할지 가리는 문턱이 사라집니다.

## 결과

**좋은 점**

- dmg 를 놓으면 **입력칸이 하나도 없습니다.** 사람이 옮겨 적다 틀릴 일이 없습니다
- 번들 ID 가 번들에서 옵니다. 등록값과 실제가 어긋나는 상태가 애초에 생기지 않습니다
- 정책 문턱은 그대로입니다. 자리만 서명 직전으로 옮겼습니다
- `bundle_id` 를 읽는 기존 코드는 하나도 바뀌지 않았습니다

**나쁜 점**

- **정책 위반을 업로드 뒤에 압니다.** 몇백 MB 를 보낸 뒤 실패합니다. 확인 창으로
  미리 알리지만 그건 경고일 뿐입니다
- **확정에 실패하면 어중간한 앱이 남습니다.** 서명은 끝났는데 번들 ID 가 임시값인
  상태입니다. 그 버전은 배포 준비됨으로 넘기지 않아서 아무도 못 받고, 치우는 것은
  사람 몫입니다. 방치된 `draft` 청소([ADR-0019](0019-abandoned-draft-cleanup.md))는
  이것을 지우지 않습니다
- **임시값이 DB 에 실제로 존재합니다.** 화면에서 가리지만 DB 를 직접 보는 사람은
  만납니다. `alley-pending.` 접두어로 알아볼 수 있게 해뒀습니다
- **정책 검사가 두 곳에 있습니다.** 워커와 서버가 각자 봅니다. 판단 기준이 갈릴 수
  있고(설정이 그 사이 바뀌면) 그때는 서버가 이깁니다. 한 곳으로 모으려면 워커가
  서명 도중에 서버에 물어야 하는데, 잡 하나에 왕복을 더하는 편이 더 나쁩니다
- 워커가 이 필드를 모르는 옛 버전이면 임시값과 실제 값이 달라 실패합니다. **그쪽이
  안전한 방향이라 그대로 둡니다**
