# ADR-0012: 콘솔에서 스크립트를 쓰는 화면은 업로드 하나로 한정한다

- 상태: 수락됨
- 날짜: 2026-08-26

## 맥락

웹 콘솔은 빌드 스텝 없이 서버가 HTML을 그려주는 화면입니다. 지금까지 자바스크립트가
한 줄도 없었고, 그것이 이 콘솔의 성격이었습니다. 폼을 서버가 받고 리다이렉트로
돌려보내면 대부분의 화면은 그것으로 충분합니다.

버전 업로드만 다릅니다. ADR-0009에서 바이너리는 서버를 거치지 않기로 했습니다.
브라우저가 presigned URL로 스토리지에 직접 `PUT`을 보내고, 다 올린 뒤 서버에
따로 통지해야 합니다. HTML 폼 하나로는 이 세 단계를 밟을 수 없습니다.

진행률도 필요합니다. 사내 앱은 보통 수십에서 수백 MB입니다. 그 시간 동안 화면에
아무 표시가 없으면 멈춘 것과 구분되지 않아서, 사용자는 새로 고침을 누르고 업로드를
끊습니다.

## 결정

**`/apps/:id/versions/new` 화면 하나만** 스크립트를 씁니다. `Public/upload.js`
한 장이고, 번들러도 프레임워크도 없습니다. 브라우저가 그대로 읽습니다.

세 단계를 브라우저가 밟습니다.

1. `POST /api/v1/apps/:id/versions` — 버전을 만들고 업로드 URL을 받는다
2. 그 URL로 파일을 `PUT` 한다 (`XMLHttpRequest`, 진행률 이벤트)
3. `POST /api/v1/versions/:id/complete` — 다 올렸다고 알린다

`fetch`가 아니라 `XMLHttpRequest`를 쓰는 자리는 2번뿐입니다. `fetch`로는 업로드
진행률을 알 수 없습니다.

**나머지 화면은 지금처럼 스크립트가 없습니다.** 출시, 철회, 역할 변경, 스토어 설정은
전부 폼 `POST` 뒤 리다이렉트입니다. 버튼 하나짜리 폼을 스크립트로 바꿀 이유가 없습니다.

**콘솔에서 올린 파일은 SHA-256을 신고하지 않습니다.** `CompleteUploadRequest.sha256`을
비워 보냅니다. 이유는 아래 결과에 적었습니다.

## 대안과 기각 사유

**서버가 업로드를 중계한다** — 폼 하나로 끝나고 스크립트가 필요 없습니다. 진행률도
`Content-Length`로 서버가 알 수 있고, 파일을 서버가 직접 보므로 SHA-256을 계산해서
신고를 믿지 않아도 됩니다. 그러나 이건 ADR-0009에서 이미 기각한 구조입니다. 수백 MB가
서버 메모리와 대역폭을 왕복하고, 재시도할 때마다 그 비용을 다시 냅니다. 게다가 화면에
보이는 진행률은 브라우저에서 서버까지의 구간이라, 서버가 스토리지로 올리는 시간만큼
실제보다 빨리 끝난 것처럼 보입니다.

**S3 POST policy로 폼에서 직접 올린다** — 서명한 정책을 숨은 필드에 넣으면 HTML 폼
제출만으로 브라우저가 스토리지에 직접 올릴 수 있습니다. 스크립트가 정말 한 줄도
필요 없고, `success_action_redirect`로 우리 화면에 돌아오게 할 수도 있습니다.
진지하게 검토할 만한 대안이었습니다. 그러나 진행률을 보여줄 방법이 없어서 원래
문제가 그대로 남습니다. 그리고 지금은 업로드와 다운로드가 모두 presigned `PUT`/`GET`
하나로 통일돼 있는데, 여기에 서명 방식이 다른 세 번째 경로가 생깁니다. MinIO와
S3에서 정책 서명이 똑같이 동작하는지도 따로 검증해야 합니다. 스크립트 한 장을
피하려고 서명 경로를 이원화하는 것은 맞바꿈이 나쁩니다.

**프론트엔드 프레임워크를 도입한다** — 업로드 화면 정도는 훨씬 편하게 만들 수 있고,
나중에 통계 대시보드처럼 복잡한 화면이 오면 어차피 필요해집니다. 그러나 Swift 레포에
Node 툴체인과 빌드 파이프라인이 따라옵니다. 화면 하나 때문에 셀프호스팅하는 사람의
빌드 절차가 늘어납니다. 복잡한 화면이 실제로 필요해지면 같은 API에 붙는 별도
프론트엔드를 다른 레포에서 만드는 편이 낫습니다.

**업로드는 CLI로만 한다** — Phase 2에 `alley-cli`가 있으니 콘솔에서는 목록과 출시만
하게 하는 선택지입니다. 그러나 CLI가 나오기 전까지는 누구도 화면에서 앱을 올릴 수
없고, CLI는 CI에서 쓰는 도구라 사람이 한 번 올리려고 설치하게 만드는 것은 과합니다.

## 결과

**좋은 점**

- 바이너리가 서버를 거치지 않는다는 원칙이 웹에서도 그대로 지켜집니다
- 올리는 동안 진행률이 보입니다. 큰 파일에서 이건 있고 없고의 차이가 큽니다
- 스크립트가 한 화면에만 있어서, 나머지 화면은 스크립트를 꺼도 전부 동작합니다
- 빌드 스텝이 없습니다. 셀프호스팅 절차는 그대로입니다

**나쁜 점**

- **콘솔에 스크립트가 생겼습니다.** "여기도 조금만"이 쌓이면 결국 프레임워크를
  손으로 다시 만들게 됩니다. 그 경계가 이 문서에만 적혀 있습니다
- 자바스크립트가 꺼져 있으면 업로드가 불가능합니다. 화면에 안내를 띄우지만
  안내일 뿐입니다
- **콘솔로 올린 파일에는 해시가 없습니다.** 브라우저에는 파일을 통째로 메모리에
  올리지 않고 SHA-256을 계산할 방법이 없습니다. `crypto.subtle`은 스트리밍
  해시를 제공하지 않고, 순수 자바스크립트로 직접 구현하는 것은 조용히 틀릴 위험이
  해시가 없는 것보다 나쁩니다
- 창을 닫거나 업로드가 끊기면 `draft` 버전과 올리다 만 오브젝트가 남습니다.
  이어올리기도 없습니다 (ADR-0009의 열려 있는 결정)
- 테스트가 서버 응답까지만 닿습니다. 세 단계를 잇는 코드는 브라우저에서 도는데,
  거기에 대한 자동 검증이 없습니다

**후속**

- 해시 구멍은 절반만 열려 있습니다. 미서명으로 올리면 서명 워커가 서명본을 만들면서
  해시를 남기므로(`SigningJobDTO.resultSHA256`), 실제로 비는 것은 **이미 서명·공증을
  마친 완성본을 웹으로 올릴 때**뿐입니다. 이 경로는 CLI를 권하는 것으로 시작하고,
  그래도 문제가 되면 그때 다른 방법을 찾습니다
- 브라우저 코드가 더 늘어나면 검증 방법을 정해야 합니다. 지금 한 장 수준에서
  브라우저 테스트 러너를 들이는 것은 과합니다
