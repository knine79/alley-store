# ADR-0051: 웹 콘솔 목록은 손댈 수 있는 앱만 보여준다

- 상태: 수락됨
- 날짜: 2026-09-17

## 맥락

`/apps` 는 두 가지를 겸하고 있었습니다.

| | 보는 사람 | 하는 일 |
| --- | --- | --- |
| 스토어 카탈로그 | 조직 구성원 전체 | 어떤 앱이 있나 둘러보기 |
| 퍼블리셔 콘솔 | 앱 올리는 사람 | 등록·업로드·토큰·통계 |

[ADR-0041](0041-remove-any-app-with-a-real-guard.md) 이후 출시된 앱은 모두에게
보였습니다. 스토어니까 당연하다고 봤습니다.

**그런데 웹에서는 남의 앱을 받지도 못합니다.** 웹 다운로드는 스토어 앱에만 열려
있습니다(이슈 #17, [ADR-0049](0049-public-store-app-download-page.md)). 카탈로그
노릇을 못 하면서 줄만 차지하고, 그 줄에는 남의 팀 앱 이름·번들 ID·설명·별점이
실립니다.

받는 사람에게는 이미 다른 자리가 생겼습니다. 스토어 앱이 카탈로그를 그리고, 스토어
앱이 없는 사람은 `/get` 에서 받습니다(ADR-0049). 웹 콘솔이 카탈로그를 겸할 이유가
남아 있지 않습니다.

**수정 권한과는 별개의 문제입니다.** 남의 앱을 열어도 고칠 수 없습니다.
`canManage` 가 오너와 관리자만 통과시키고, 화면에도 버튼이 그려지지 않습니다. 이
결정이 막는 것은 권한이 아니라 **보이는 범위**입니다.

## 결정

웹 콘솔 목록(`/apps`)은 **손댈 수 있는 앱만** 보여줍니다. 오너, 앱 멤버, 관리자입니다.
출시 여부와 무관합니다.

`canUpload` 와 같은 기준입니다. 새 개념을 만들지 않았고, "보이는데 못 만지는" 상태가
생기지 않습니다.

**API 목록(`/api/v1/apps`)은 그대로 둡니다.** 출시된 앱을 모두에게 줍니다. 그것이
스토어 앱이 그리는 카탈로그이고, 여기까지 좁히면 받을 앱 목록이 빕니다.

**상세 화면(`/apps/{id}`)도 그대로 둡니다.** 출시된 앱이면 누구나 볼 수 있습니다.
목록은 "내가 맡은 것" 이고 상세는 "주소를 알고 찾아온 자리" 입니다. 별점과 피드백을
읽는 길이고, 손대는 것은 어차피 막혀 있습니다.

### 웹과 API 의 규칙이 갈라지는 것에 대하여

[c337e94](https://github.com/knine79/alley-store/commit/c337e94) 는 둘을 일부러
맞췄습니다. 그 커밋의 말은 이랬습니다.

> 웹 목록과 API 목록이 같은 규칙을 씁니다. 웹만 막고 API 를 열어두면 목록은
> 깨끗한데 값은 그대로 나갑니다.

그 말은 **출시 전인 앱**에 대한 것이었고, 지금도 유효합니다. 출시 전인 앱은 양쪽
모두 손댈 수 있는 사람에게만 보입니다.

달라지는 것은 **출시된 앱**입니다. 여기서는 보는 사람이 다르므로 규칙도 갈리는 것이
맞습니다. 웹은 올리는 사람의 화면이고 API 는 받는 사람의 카탈로그입니다. 같은 값을
같은 규칙으로 내주는 것이 원칙이 아니라, **그 자리가 무엇을 하는 곳인지**가 원칙입니다.

숨기는 것이 보안 장치는 아닙니다. 출시된 앱의 이름과 번들 ID 는 로그인한 사람이면
API 로 그대로 받습니다. 이 결정이 얻는 것은 **화면이 무엇을 하는 곳인지가 흐려지지
않는 것**입니다.

## 대안과 기각 사유

**오너인 것만 보여준다** — 더 좁고 규칙이 더 단순합니다.

기각한 이유는 **올릴 권한을 받은 사람이 그 앱을 목록에서 못 찾기 때문입니다.** 앱
멤버는 버전을 올리라고 넣은 사람인데, 올릴 자리를 목록에서 찾지 못하면 주소를 따로
받아야 합니다. `canUpload` 와 어긋나는 순간 "보이는데 못 만지는" 의 반대인 "만질 수
있는데 안 보이는" 이 생깁니다.

**관리자도 자기 것만 보여준다** — 목록이 가장 깨끗해집니다.

기각한 이유는 **관리자가 찾아갈 길이 필요하기 때문입니다.** 워커가 실패했거나 어떤
앱이 문제를 일으켰을 때 관리자가 들어가야 합니다. 관리자는 어차피 모든 앱을 수정할
권한이 있어서, 감추는 것이 보호가 되지도 않습니다.

**상세 화면도 같이 조인다** — 목록과 규칙이 같아져 설명할 것이 하나로 줄어듭니다.

기각한 이유는 **피드백과 별점을 읽는 길이 없어지기 때문입니다.** 웹 콘솔은 앱에
달린 피드백을 보여주는 유일한 자리입니다. 실제로 그 동작을 지키는 시험이 넷
있었습니다. 목록에서 빼는 것과 주소로 찾아온 사람을 막는 것은 다른 결정이고, 후자는
지금 치를 이유가 없습니다.

**웹 목록에 "내 앱 / 전체" 탭을 둔다** — 둘 다 할 수 있습니다.

기각한 이유는 **전체 탭이 카탈로그가 아니기 때문입니다.** 거기 선 앱들은 웹에서
받을 수 없습니다. 누를 수 있는데 아무 일도 일어나지 않는 줄을 탭 하나 뒤에 감추는
것뿐입니다.

## 결과

**좋은 점**

- 콘솔이 무엇을 하는 곳인지 분명해집니다. 목록에 선 앱은 전부 그 사람이 손댈 수
  있는 것입니다
- 다른 팀이 준비 중인 것도, 출시한 것도 이름과 번들 ID 가 목록에 실리지 않습니다
- 규칙이 `canUpload` 하나입니다. 출시 여부를 따지지 않아 조건이 단순해졌습니다

**나쁜 점**

- **웹에서 조직의 앱을 둘러볼 길이 없어집니다.** 스토어 앱이 없는 사람은 무엇이
  있는지 볼 수 없습니다. `/get` 에서 스토어 앱을 받는 것이 먼저입니다
- **같은 사람이 웹과 스토어 앱에서 다른 목록을 봅니다.** 그것이 의도지만, 처음 보는
  사람에게는 한쪽이 고장 난 것처럼 보일 수 있습니다
- **목록과 상세의 규칙이 다릅니다.** 목록에 없는 앱을 주소로는 열 수 있습니다.
  설명할 것이 하나 늘었습니다
- 관리자 화면은 여전히 전부 보입니다. 관리자 계정으로 확인하면 이 결정이 도는지
  알 수 없고, 그래서 시험으로 지킵니다
