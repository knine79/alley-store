[ADR](adr/README.md)을 보세요.

- 현재 상태: Phase 1·3·4 완료, Phase 2 는 프로필 발급만 남음. **실제 자격증명이 필요한 검증(서명·공증·로그인·설치)은 아직 하지 못했습니다**

## 지금 무엇을 먼저 하나

코드는 대부분 있고, **실제로 굴려본 적이 없는 것**이 남았습니다. 순서는 그 기준으로
정했습니다.

| | 무엇 | 왜 지금 |
| --- | --- | --- |
| 1 | [1-6. 첫 배포](#1-6-첫-배포) | 여기서 나오는 것이 나머지 순서를 바꿉니다. `S3_ENDPOINT` 를 나누는 일이 여기 걸려 있습니다 |
| 2 | [워커 자동 업데이트](#다음-워커-자동-업데이트---시작-전) | 워커 버그는 그 워커가 서명한 모든 앱에 영향을 줍니다. 지금은 고쳐도 퍼뜨릴 방법이 없습니다 |
| 3 | 워커 회귀 시험 (아래) | 2번의 승인 지점을 의미 있게 만듭니다 |
| 4 | Developer ID 프로필 발급 ([Phase 2](#phase-2-발급-자동화--cli-1-2주---대부분-완료)) | 실제로 프로필이 필요한 앱이 나올 때 |

**1번을 맨 위에 둔 이유**는 실제로 돌려봐야만 나오는 것들이 있기 때문입니다. 실제
인증서로 서명을 돌려보다 프레임워크 안의 dylib 여섯 개가 서명에서 빠지는 것을
찾았고, 빈 디렉터리에서 서버를 띄워보다 설치 문서에 마이그레이션 단계가 통째로 빠진
것을 찾았습니다. 둘 다 코드와 테스트로는 나오지 않았습니다.

### 워커 회귀 시험

워커 자동 업데이트에는 사람이 확인하는 지점이 필요한데, **승인 버튼만으로는 값이
거의 없습니다.** 위의 서명 버그가 그 증거입니다. `codesign --verify --deep --strict`
가 통과했는데 여섯 개가 미서명이었습니다. 화면에서 "승인" 을 눌러도 그것은 못 잡습니다.

기계가 검사하고 사람은 그 결과를 봐야 합니다.

- [ ] 중첩 프레임워크와 헬퍼가 있는 시험용 번들을 픽스처로 만든다
- [ ] 새 워커에게 그것을 서명시키고 결과를 서버가 검사한다 (서명 대상 수, 남은
      ad-hoc Mach-O 0개, 공증 통과, entitlements 가 `.app` 에만)
- [ ] 그 검사를 통과해야 승인할 수 있게 한다

실행 파일 하나짜리 번들로는 의미가 없습니다. 위의 버그를 잡으려면 프레임워크 안에
따로 서명해야 하는 코드가 들어 있어야 합니다.

### 1-2. 앱/버전/아티팩트 (1주) - 완료

- [x] 앱 등록 시 번들 ID 검증 (프리픽스 준수 + 중복 차단), 번들 ID 대장 조회
- [x] S3 presigned 업로드/다운로드 ([ADR-0009](adr/0009-presigned-artifact-transfer.md))
- [x] 버전 상태 머신 서버 연동
- [x] 다운로드 이력 기록
- [x] 방치된 `draft` 청소 ([ADR-0019](adr/0019-abandoned-draft-cleanup.md))

업로드를 시작했다가 완료 통지 없이 버려진 버전은 서버가 지웁니다. 보관 기간은
`DRAFT_RETENTION_HOURS` 로 정하고 기본값은 72시간입니다. 오브젝트가 올라와 있으면
그것도 함께 지웁니다. **이 값을 `S3_PRESIGNED_URL_TTL` 보다 짧게 두면 올리는 중인
파일의 자리를 지우게 됩니다.**

멀티파트 업로드는 넣지 않았습니다. 사내망에서 수백 MB를 올리는 상황이라 단순
재시도로 충분하다고 봤습니다. 근거와 대안은 ADR-0009에 있습니다.

### 1-3. 서명 워커 (1주) - 코드 완료, E2E 미검증

- [x] signing_jobs 큐 + 워커 API (long-poll, 클레임, 하트비트)
- [x] 워커 토큰 발급·폐기 (API + 관리자 화면, [ADR-0013](adr/0013-worker-token-authentication.md))
- [x] codesign → notarytool → staple 파이프라인
- [x] entitlements 검사 (restricted 항목이 있는데 프로필이 없으면 서명 전 실패)
- [x] 업로더가 entitlements 를 함께 올린다 (API·CLI·콘솔, `.app` 에만 적용,
      Electron JIT 검사, [ADR-0020](adr/0020-uploader-provides-entitlements.md))
- [x] launchd 설치 스크립트 (`scripts/install-worker.sh`)
- [x] 워커 번들 조립·서명 (`scripts/build-worker-app.sh`, 스토어 앱과 공통 절차를 쓰는
      `scripts/lib/bundle.sh`, [ADR-0022](adr/0022-worker-as-signed-app-bundle.md))
- [x] 번들 설치 경로 (`install-worker.sh --bundle <zip>`, 워커 맥에 소스·Swift 불필요)
- [x] 실패 로그 수집/재시도
- [x] 멈춘 잡 회수: 하트비트가 끊긴 `running` 잡을 큐로 되돌리고, 시도 상한을 넘기면
      실패로 확정 ([ADR-0018](adr/0018-stalled-signing-job-recovery.md))
- [ ] **실제 인증서로 E2E 검증**

**선행 조건**: 서명 워커를 돌릴 macOS 머신, Developer ID Application 인증서,
`notarytool store-credentials`로 저장한 공증 자격증명.

마지막 항목은 위 선행 조건이 갖춰져야 할 수 있습니다. 그 전까지는 `codesign` 과
`notarytool` 을 실제로 부르는 구간이 검증되지 않은 상태입니다. 파이프라인이 조립하는
명령과 순서는 단위 테스트로 확인했지만, 그 명령이 실제 인증서에서 어떻게 반응하는지는
돌려봐야 압니다.

워커를 설치하려면 관리 > 서명 워커에서 토큰을 발급하고, 인증서가 있는 맥에서
`./scripts/build-worker-app.sh --sign` 으로 만든 zip 을 워커 맥으로 옮겨
`./install-worker.sh --bundle <zip>` 을 실행합니다. 워커 맥에는 소스도 Swift 툴체인도
필요 없습니다. 절차는 [설치 가이드](setup.md#4-서명-워커-설치)에 있습니다.

워커가 잡을 가져간 채로 죽으면 서버가 5분마다 훑어서 그 잡을 큐로 되돌립니다. 세 번
내보내고도 끝나지 않으면 실패로 확정합니다. 되돌린 사실은 관리 > 서명 워커의
"최근 서명 잡" 표에 시도 횟수로 나타납니다.

실제 Electron 앱으로 돌려보다 미서명 업로드에는 붙일 entitlements 가 없다는 것을
찾았습니다. 재서명이면 기존 서명에서 읽으면 되지만 미서명에는 읽을 것이 없어서, 권한이
빈 채로 Hardened Runtime 만 켜져서 서명됐습니다. 이제 업로더가 plist 를 함께 올립니다
([ADR-0020](adr/0020-uploader-provides-entitlements.md)). **빼먹으면 여전히 조용히
잘못된 앱이 나갑니다.** Electron 만 서명 전에 걸러냅니다.

### 1-4. 웹 콘솔 (0.5-1주, 1-2와 병행 가능) - 완료

- [x] 스토어 설정을 데이터베이스로 이전 ([ADR-0011](adr/0011-store-settings-in-database.md))
- [x] 관리자 API: 스토어 설정 조회/수정, 사용자 역할 변경
- [x] 렌더링 기반 (레이아웃, 정적 파일, 오류 페이지)
- [x] CSRF `Origin` 검사 + 로그인/로그아웃 화면
- [x] 앱 목록/상세/등록 화면
- [x] 버전 업로드 화면 (진행률), 릴리즈/철회 ([ADR-0012](adr/0012-browser-upload-script.md))
- [x] 관리자 화면: 역할 관리, 스토어 설정

콘솔은 빌드 스텝 없는 중립 CSS 한 장으로 만듭니다. 강조색과 로고는 스토어 설정에서
와서, 다른 조직이 띄우면 그 조직 것으로 보입니다. 사내용 고급 화면이 필요해지면
같은 API 에 붙는 별도 프론트엔드를 다른 레포에서 만듭니다.

브라우저에서 MinIO 로 직접 업로드하는 경로는 CORS 를 확인했습니다. MinIO 가
preflight 와 실제 `PUT` 양쪽에 헤더를 붙여줘서 [ADR-0009](adr/0009-presigned-artifact-transfer.md)
의 방식을 웹에서도 그대로 씁니다. 허용 출처는 `PUBLIC_BASE_URL` 로 좁혔습니다.

업로드 화면만 자바스크립트를 씁니다. 브라우저가 스토리지로 직접 올리면서 진행률을
보여주려면 폼 제출만으로는 안 됩니다. 나머지 화면은 스크립트 없이 폼 `POST` 와
리다이렉트로 동작합니다. 경계와 대가는 [ADR-0012](adr/0012-browser-upload-script.md)
에 있습니다.

**워커 등록 화면은 1-3 이후로 미룹니다.** `workers` 테이블이 아직 없습니다.
앱 멤버 추가·제거 화면과 콘솔에서의 다운로드도 아직 없습니다. 멤버는 API 로,
다운로드는 스토어 앱으로 합니다.

아직 눈으로 보지 않았습니다.** 로그인은 Google OAuth 클라이언트가 있어야 하고,
설치는 실제 서명·공증된 앱이 있어야 합니다. 둘 다 1-6 에서 함께 확인합니다.

### 1-6. 첫 배포

- [x] 서버 이미지를 ghcr 에 발행, compose 를 이미지 기준으로 전환
      ([ADR-0021](adr/0021-publish-server-container-image.md))
- [ ] **`S3_ENDPOINT` 를 서버용과 브라우저용으로 나눈다** (아래)
- [ ] 배포 환경 구성 (시크릿·도메인, 이 레포 밖)
- [ ] Google OAuth 클라이언트 발급 (운영용 리다이렉트 URI 추가)
- [ ] 워커 설치, 파일럿 앱 1개로 전체 루프 검증

운영은 `docker-compose.yml` 과 `.env` 두 파일만 가져갑니다. 소스 없이 뜨는 것과
컨테이너 안에서 마이그레이션이 도는 것까지 로컬에서 확인했습니다. **레지스트리에서
실제로 받아본 것은 아직 아닙니다.** CI 를 한 번 돌려야 확인됩니다.

**`S3_ENDPOINT` 하나로는 운영에서 업로드가 안 됩니다.** 지금 이 값이 두 곳에 쓰입니다.
서버가 스토리지에 붙는 주소이면서, 브라우저와 스토어 앱에 내주는 presigned URL 의
기반 주소이기도 합니다 (`ArtifactStorage.objectBase`). compose 는 이것을
`http://minio:9000` 으로 덮어쓰는데, 그 이름은 컨테이너 안에서만 풀립니다. 브라우저는
닿을 수 없습니다.

로컬 개발에서 안 걸린 이유는 `S3_ENDPOINT=http://localhost:9000` 이 양쪽에서 다
통했기 때문입니다. 운영 도메인에서는 통하지 않습니다.

**값을 둘로 나눠야 합니다.** 서버가 쓰는 내부 주소와, 클라이언트에게 내주는 공개
주소입니다. 스토리지도 그 공개 주소로 밖에서 닿을 수 있어야 합니다. 첫 배포를 막는
문제라 여기 둡니다.

```bash
export ALLEY_SERVER_URL=https://store.example.com
export ALLEY_TOKEN=alleyd_...        # 앱 상세 화면에서 발급
alley upload build/MyApp.zip --version 1.2.0
```

빌드 번호를 안 주면 서버의 마지막 번호에 1을 더합니다. 종료 코드는 설정·인자 실수가
2, 서버·전송 실패가 1입니다. 전자는 재시도해봐야 소용없습니다.

**프로필 발급은 남겼습니다.** API 호출 자체보다 "발급한 프로필을 누구에게 어떻게
전달하는가"가 문제입니다. 프로필은 서명 **이전에** 번들 안에 들어가야 하므로
(설계 문서 §3) 워커가 아니라 앱을 빌드하는 개발자에게 가야 합니다. 그 흐름을 정하는
것이 API 연동보다 큰 일이라 실제로 필요한 앱이 나올 때 정합니다.

**App Store Connect 연동은 실제 키로 확인하지 못했습니다.** JWT 조립과 응답 해석,
만료 판단은 테스트로 확인했지만, Apple 이 그 토큰을 받아주는지는 키가 있어야 압니다.

## Phase 3. 별점 + 피드백 + 알림 (1-2주) - 완료

- [x] 별점(1점부터 5점까지, 버전별), 피드백(텍스트 + 스크린샷 첨부, [ADR-0016](adr/0016-server-handles-small-uploads.md))
- [x] 스토어 앱/웹에 별점·리뷰 UI
- [x] 알림 채널 추상화 + Slack Incoming Webhook, 앱별 알림 대상 설정
- [x] 신규 피드백·별점 등록 시 앱 오너에게 발송
- [x] 워커 하트비트 끊김 알림

**SMTP 는 넣지 않았습니다.** Swift 에 표준 클라이언트가 없어 의존성을 하나 더 지거나
직접 구현해야 하는데, 사내에서 Slack 을 쓰면 값을 하지 못합니다. 채널은 타입으로
추상화해두었으므로 필요해지면 `NotificationChannel` 을 따르는 타입 하나가 늡니다.

피드백은 **받아본 버전에만** 남길 수 있습니다. 다운로드 이력을 조건으로 씁니다.
익명은 화면에서만 익명이고 서버는 누가 남겼는지 계속 압니다. 본인이 고치고 지울 수
있어야 하고, 악용이 생기면 추적할 수 있어야 하기 때문입니다.

**익명 허용 여부는 관리자 화면에서 켜고 끕니다.** 조직마다 답이 다릅니다. 끄면
이름을 감춘 요청이 거절되고 화면에서 체크박스가 사라집니다. 조용히 실명으로 바꾸지
않습니다. 익명인 줄 알고 쓴 글에 이름이 붙는 것이 이 기능에서 가장 나쁜 실패입니다.
**이미 익명으로 남긴 글은 설정을 꺼도 익명으로 남습니다.** 남길 때의 약속을 나중에
뒤집으면 그 사람이 쓴 것이 다른 뜻이 됩니다.

스토어 앱은 지금 깔려 있는 버전이 최신 출시본과 같을 때만 폼을 띄웁니다. 앱이 아는
것이 "설치된 버전"뿐이라서입니다. 예전 버전에 남기려면 웹 콘솔을 씁니다.

      ([ADR-0017](adr/0017-sparkle-feed-tokens.md))

- [x] 다운로드 통계 대시보드
- [x] 공개 준비: LICENSE(MIT), 셀프호스팅 가이드, 시크릿 스캔, deny list

**스토어 앱에는 Sparkle 을 넣지 않았습니다.** 다른 앱들이 쓸 appcast 는 서버가
그대로 내주지만, 스토어 앱 자신은 이미 앱을 받아 검증하고 설치하는 코드를 갖고
있어서 프레임워크를 하나 더 얹을 이유가 없습니다. 실행 중인 자기를 갈아끼우는 것은
셸 스크립트 하나로 처리합니다.

**통계는 "설치"가 아니라 "다운로드"입니다.** 서버가 아는 것은 누군가 파일을
받아갔다는 사실까지입니다. 설치 완료를 알려면 스토어 앱이 따로 보고해야 하는데,
그 값이 크지 않다고 봤습니다.

- [x] 잡 로그를 덮어쓰지 않고 쌓는다 (상한 16KB, 넘으면 앞을 버린다)
- [x] 관리 > 서명 워커와 앱 상세에 안내 문구와 코드를 함께 보여준다

([ADR-0023](adr/0023-signing-failure-codes.md))

**동작이 하나 바뀝니다.** 지금까지 워커가 보고한 실패는 무조건 버전을 `failed` 로
확정했습니다. 이제 네트워크·스토리지·공증 서비스·타임아웃은 잡을 큐로 되돌립니다.
그 외에는 시도 횟수를 쓰지 않고 곧장 실패로 확정합니다.

**분류하지 못한 실패는 다시 시도하지 않습니다.** 잘못된 재시도가 같은 버전을 공증에
두 번 올리기 때문이고, 자동으로 넘어가면 갈래를 늘려야 한다는 신호가 묻히기
때문입니다. `unknown` 이 자주 들어온다면 갈래를 하나 더 만들 때입니다.

## 다음. 워커 자동 업데이트 - 시작 전

- [ ] 워커가 새 번들이 나왔는지 확인하고 받아온다
- [ ] 잡을 잡고 있지 않을 때만 자기를 갈아끼운다
- [ ] 갈아끼운 뒤 정해진 시간 안에 하트비트가 없으면 스스로 이전 번들로 되돌린다
- [ ] 번들 버전(`CFBundleShortVersionString`)과 코드 안의 `workerVersion` 을 한 곳에서
      관리한다
- [ ] 워커 릴리스를 누가 만들어 어디에 올리는지 정한다

워커를 고쳐도 사람이 각 맥에 가서 다시 설치해야 합니다. 워커 버그는 그 워커가 서명한
모든 앱의 배포 품질을 망치는데 고친 것을 퍼뜨릴 길이 없습니다
([ADR-0022](adr/0022-worker-as-signed-app-bundle.md)의 후속 과제).

**유휴일 때만 갈아끼웁니다.** 서명이나 공증 도중에 프로세스가 바뀌면 그 잡은 중간에
끊깁니다. 공증은 Apple 응답을 기다리는 구간이 길어서 그럴 확률이 낮지 않습니다.

**뜬 뒤 일정 시간 안에 하트비트를 못 보내면 스스로 이전 버전으로 되돌립니다.**
갈아끼운 워커가 뜨지 못하면 되돌릴 사람이 그 맥에 직접 가야 하는데, 그 맥은 원래
사람이 잘 가지 않는 머신입니다. 되돌릴 자리는 이미 있습니다. 설치 경로가 고정된
번들이라 이전 것을 옆에 두면 됩니다.

**사람이 확인하는 지점이 필요합니다.** 새 워커 번들을 서명하는 것이 지금 돌고 있는
워커입니다. 워커가 자기 다음 버전을 서명하고 그것으로 자기를 갈아끼우는 순환이
생깁니다. 잘못된 빌드가 나가면 그것을 되돌릴 워커도 그 빌드입니다. 승인을 어디에 둘지는
릴리스를 누가 만드는지와 함께 정합니다.

## MVP 수용 기준

Phase 1을 완료로 판정하는 조건 일곱 가지입니다. 그중 **3, 4, 7 은 실제 인증서와 OAuth
클라이언트가 갖춰진 뒤에야 확인할 수 있습니다.** 나머지는 코드와 테스트로
확인했습니다.

1. `docker compose up`만으로 로컬에서 서버·DB·스토리지가 뜨고 브라우저에서
   로그인까지 동작한다
2. 허용 도메인 밖의 계정은 로그인이 서버 단에서 거부된다
3. developer가 미서명 빌드를 올리면 워커가 자동으로 서명·공증·스테이플을 수행하고
   상태가 `ready`가 된다
4. released 버전을 스토어 앱에서 로그인 후 다운로드하면 Gatekeeper 경고 없이
   실행된다
5. 다운로드 이력에 사용자·버전·시각이 기록된다
6. 코드에 조직 고유 명사가 검색되지 않는다 (CI deny list 통과)
7. 스토어 앱은 서버 주소만 입력하면 다른 조직 서버에도 그대로 붙는다

## 검증 방법

- **단위 테스트**: 상태 머신 전이, 번들 ID 검증, 설정 로딩, 권한 미들웨어,
  OAuth 도메인 검증
- **통합 테스트**: docker-compose 기반 API 시나리오
  (등록 → 업로드 → 잡 생성 → 상태 전이)
- **E2E**: 파일럿 앱 1개로 실제 서명·공증·다운로드·Gatekeeper 통과 확인
- **보안 점검**: 워커 토큰 없는 잡 API 접근 거부, 비로그인 다운로드 거부,
  presigned URL 만료 확인, 메타 응답에 비밀값 미포함
