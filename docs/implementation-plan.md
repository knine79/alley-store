무엇을 언제 만드는지에 대한 문서입니다. 진행에 따라 계속 갱신됩니다.

무엇을 왜 이렇게 만드는지는 [설계 문서](design.md)를, 개별 결정의 배경은
[ADR](adr/README.md)을 보세요.

- 최종 갱신: 2026-09-18
- 현재 상태: Phase 1·3·4 완료, Phase 2 는 프로필 발급만 남음. 배포 서버 상대로 서명·공증·스테이플·출시까지 돌았고(2026-09-17), 받은 결과물이 `source=Notarized Developer ID` 인 것까지 확인했습니다. dmg 는 옛 워커가 잡을 가져가서 안 만들어진 것이었고, 워커가 자기를 갈아끼운 뒤 빌드 19 에서 만들어진 것을 확인했습니다. **남은 것은 0.8.0 을 반영해 스토어 앱을 다시 빌드하고, 받아서 실제로 열어보는 것입니다** - 지금 나가 있는 빌드는 열리지 않습니다

## 지금 무엇을 먼저 하나

코드는 대부분 있고, **실제로 굴려본 적이 없는 것**이 남았습니다. 순서는 그 기준으로
정했습니다.

| | 무엇 | 왜 지금 |
| --- | --- | --- |
| 1 | 고친 서버로 스토어 앱을 다시 빌드 ([1-6](#1-6-첫-배포)) | 지금 출시된 빌드는 열리지 않습니다. 받은 사람이 "손상되었거나 완전하지 않다" 를 봅니다 |
| 2 | Developer ID 프로필 발급 ([Phase 2](#phase-2-발급-자동화--cli-12주---대부분-완료)) | 실제로 프로필이 필요한 앱이 나올 때. 지금 올라온 앱 중에는 없습니다 |
| 3 | [워커 회귀 시험](#워커-회귀-시험---대부분-이미-있습니다) 의 남은 한 줄 | 급하지 않습니다. 고르기 로직은 테스트 14개가 덮고 있고, 남은 것은 실제 `codesign` 을 돌려야 나오는 한 경우입니다 |

**실제로 돌려봐야만 나오는 것들이 있습니다.** 실제 인증서로 서명을 돌려보다
프레임워크 안의 dylib 여섯 개가 서명에서 빠지는 것을 찾았고, 빈 디렉터리에서 서버를
띄워보다 설치 문서에 마이그레이션 단계가 통째로 빠진 것을 찾았습니다. 300KB 를
올리는 `curl` 에서 워커가 영구히 멈추는 것도 그렇게 나왔습니다. 셋 다 코드와
테스트로는 나오지 않았습니다. 그래서 아직 굴려보지 않은 조합이 맨 위에 옵니다.

### 워커 회귀 시험 - 대부분 이미 있습니다

**이 절은 dylib 여섯 개가 서명에서 빠진 직후에 적혔습니다.** 그 뒤에 테스트가
생겼는데 여기를 지우지 않아서, 문서만 보면 아직 아무것도 없는 것처럼 읽힙니다.

지금 `BundleLayoutTests` 에 서명 대상을 고르는 테스트가 14개 있습니다. 그 버그를
직접 막는 것들입니다.

- `프레임워크 안의 dylib 과 헬퍼는 따로 서명한다`
- `프레임워크 안쪽을 프레임워크보다 먼저 서명한다`
- `프레임워크의 주 실행 파일은 따로 서명하지 않는다`
- `모든 Mach-O 를 세는 쪽은 주 실행 파일도 포함한다`

macOS CI 가 PR 마다 돌립니다(`swift test --filter 'AlleyStoreTests|AlleyWorkerTests'`).
픽스처를 코드로 짓는 헬퍼도 그 파일에 있습니다.

**남은 것은 하나입니다.** 지금 테스트는 "무엇을 서명 대상으로 고르는가" 까지만 봅니다.
고르기는 맞는데 서명 순서가 틀려 바깥 번들의 봉인이 깨지는 경우는 실제로 `codesign`
을 돌려야 드러납니다. ad-hoc 서명(`codesign -s -`)이면 Developer ID 없이 CI 에서도
됩니다.

- [ ] 진짜 Mach-O 로 지은 픽스처를 ad-hoc 으로 서명하고, 남은 미서명 Mach-O 가
      0개인지 본다

**지금은 하지 않습니다.** 픽스처의 Mach-O 가 매직 넘버만 쓴 가짜라 `codesign` 이
거부하므로 실행 파일과 dylib 을 컴파일해야 하고, 서명 단계가 `private` 이라 접근
수준도 손봐야 합니다. 한두 시간짜리인데 막아주는 것은 위의 한 경우뿐입니다. 워커는
한 대고 잘못 배포해도 이전 릴리스로 되돌립니다.

**서버가 결과를 검사하고 그것을 통과해야 배포할 수 있게** 하는 계획은 접었습니다.
서버는 리눅스라 `codesign` 이 없어 zip 안의 Mach-O 를 직접 파싱해야 하고, 실제 서명과
공증이 필요해 CI 에서 돌릴 수도 없습니다. CI 가 막으면 릴리스가 나가지 않으므로
배포 게이트는 그 위에 얹는 장치입니다.

## Phase 1. MVP: 코어 배포 루프 (3\~4주)

목표: 로그인 → 앱 등록/업로드 → 자동 서명·공증 → 스토어 앱에서 다운로드·설치가
끝까지 동작한다.

프로젝트 `alley-store`, 동의 화면 Internal, 웹 애플리케이션 클라이언트.

### 1-2. 앱/버전/아티팩트 (1주) - 완료

- [x] apps/versions/artifacts CRUD + 권한 (developer만 등록, app_members만 업로드)
- [x] 앱 등록 시 번들 ID 검증 (프리픽스 준수 + 중복 차단), 번들 ID 대장 조회
- [x] 올린 번들의 `CFBundleIdentifier` 를 서명 전에 대조
      ([ADR-0029](adr/0029-verify-bundle-identifier-before-signing.md))
- [x] S3 presigned 업로드/다운로드 ([ADR-0009](adr/0009-presigned-artifact-transfer.md))
- [x] 버전 상태 머신 서버 연동
- [x] 다운로드 이력 기록
- [x] 방치된 `draft` 청소 ([ADR-0019](adr/0019-abandoned-draft-cleanup.md))

업로드를 시작했다가 완료 통지 없이 버려진 버전은 서버가 지웁니다. 보관 기간은
`DRAFT_RETENTION_HOURS` 로 정하고 기본값은 72시간입니다. 오브젝트가 올라와 있으면
그것도 함께 지웁니다. **이 값을 `S3_PRESIGNED_URL_TTL` 보다 짧게 두면 올리는 중인
파일의 자리를 지우게 됩니다.**

멀티파트 업로드는 넣지 않았습니다. 사내망에서 수백 MB를 올리는 상황이라 단순
재시도로 충분하다고 봤습니다. 근거와 대안은 ADR-0009에 있습니다.

**선행 조건**: 서명 워커를 돌릴 macOS 머신, Developer ID Application 인증서,
`notarytool store-credentials`로 저장한 공증 자격증명.

실제 Developer ID 로 미서명 앱을 끝까지 통과시켰습니다. 업로드 → 클레임 → 서명 →
공증(48초) → 티켓 첨부 → 결과 업로드 → `ready` 까지 갔고, 다시 내려받아
`source=Notarized Developer ID` 를 확인했습니다. 94개를 서명해야 하는 Electron 앱도
entitlements 세 개를 그대로 유지한 채 통과했습니다.

**상대는 로컬 서버였습니다.** 배포 서버에 붙였을 때만 드러나는 것 - presigned URL
수명, 잡 폴링의 네트워크 지연, 결과 업로드 경로 - 이 남아 있습니다.

실제로 돌려보고 잡은 것이 이 구간에서 셋 나왔습니다. 프레임워크 안의 dylib 여섯 개가
서명 대상에서 빠지던 것, `codesign --verify --deep --strict` 가 그 여섯 개를 통과시키던
것, 그리고 결과를 올리는 `curl` 에서 워커가 영구히 멈추던 것입니다. 마지막 것은
`Process.waitUntilExit()` 의 경합이었고, 워커가 잡 하나를 물고 멈춰서 그 뒤로 아무
잡도 받지 못했습니다. 셋 다 단위 테스트로는 나오지 않았습니다.

워커를 설치하려면 관리 > 서명 워커에서 토큰을 발급하고, 인증서가 있는 맥에서
`./scripts/build-worker-app.sh --sign` 으로 만든 **설치 키트**를 워커 맥으로 옮겨
`./install-worker.sh --config <설정 파일>` 을 실행합니다. 키트에는 번들과 설치
스크립트가 함께 들어 있고, 설정 파일 하나를 채우면 인증서 등록·공증 프로필 저장·
설치·환경 점검을 한 번에 합니다. 워커 맥에는 소스도 Swift 툴체인도 필요 없습니다.
절차와 빌드에 넘길 환경변수는 [설치 가이드](setup.md#4-서명-워커-설치)에 있습니다.

워커가 잡을 가져간 채로 죽으면 서버가 5분마다 훑어서 그 잡을 큐로 되돌립니다. 세 번
내보내고도 끝나지 않으면 실패로 확정합니다. 되돌린 사실은 관리 > 서명 워커의
"최근 서명 잡" 표에 시도 횟수로 나타납니다.

실제 Electron 앱으로 돌려보다 미서명 업로드에는 붙일 entitlements 가 없다는 것을
찾았습니다. 재서명이면 기존 서명에서 읽으면 되지만 미서명에는 읽을 것이 없어서, 권한이
빈 채로 Hardened Runtime 만 켜져서 서명됐습니다. 이제 업로더가 plist 를 함께 올립니다
([ADR-0020](adr/0020-uploader-provides-entitlements.md)). **빼먹으면 여전히 조용히
잘못된 앱이 나갑니다.** Electron 만 서명 전에 걸러냅니다.

있는 일이 스크립트 유무에 따라 달라지는 것은 ADR-0030 이 그은 경계가 흐려진
자리이고, ADR-0031 에 대가로 적어뒀습니다.

나머지 화면은 스크립트 없이 폼 `POST` 와 리다이렉트로 동작합니다.

**워커 등록 화면은 1-3 이후로 미룹니다.** `workers` 테이블이 아직 없습니다.

운영은 `docker-compose.yml` 과 `.env` 두 파일만 가져갑니다. 소스 없이 뜨는 것과
컨테이너 안에서 마이그레이션이 도는 것까지 로컬에서 확인했습니다. **레지스트리에서
실제로 받아본 것은 아직 아닙니다.** CI 를 한 번 돌려야 확인됩니다.

**스토리지 설정이 세 군데에서 배포 환경과 맞지 않았습니다.** 셋 다 첫 배포를 막는
문제였고, 환경변수 셋으로 풀었습니다. 배경과 대가는
[ADR-0024](adr/0024-storage-prefix-endpoints-credentials.md) 에 있습니다.

| 무엇이 문제였나 | 무엇을 더했나 |
| --- | --- |
| 버킷 루트에 쓴다. 프리픽스 하나만 소유하는 배포에서 막힌다 | `S3_KEY_PREFIX` |
| `S3_ENDPOINT` 가 서버가 붙는 주소이자 클라이언트에게 내주는 주소였다 | `S3_PUBLIC_ENDPOINT` |
| 액세스 키를 필수로 받는다. 역할로 인증하는 배포는 뜨지도 못한다 | 액세스 키를 선택으로 |

MinIO 로 확인했습니다. 프리픽스를 준 업로드가 `<프리픽스>/apps/...` 에 놓이는 것,
안 주면 예전 자리 그대로인 것, 내부·공개 주소를 다르게 준 presigned URL 이 실제로
통하는 것, 호스트만 어긋내면 403 이 나는 것, 액세스 키 없이 서버가 뜨는 것까지
직접 돌려봤습니다.

**presigned URL 수명은 아직 확인하지 못했습니다.** 임시 자격증명으로 서명하면
`S3_PRESIGNED_URL_TTL` 이 상한일 뿐이라는 것은 SDK 소스로 확인했지만, 실제 STS 환경에서
얼마나 사는지는 배포해봐야 압니다.

**배포까지는 됐습니다.** Kubernetes 샌드박스에 이미지를 올려 서버가 떴고
(`MIGRATE_ON_BOOT` + advisory lock 으로 스키마가 잡혔습니다), Google 로그인으로
첫 관리자가 만들어지고 허용 도메인 밖 계정이 거부되는 것까지 확인했습니다. 역할로
인증하는 스토리지(Pod Identity)에서 presigned URL 이 실제로 통하는 것도 확인했습니다.

**워커까지 배포 서버 상대로 돌았습니다** (2026-09-17). 서버가 조립한 스토어 앱이
워커에서 서명·공증·스테이플을 거쳐 출시까지 여덟 번 지나갔습니다. 출시본을 받아
검사해 `accepted / source=Notarized Developer ID`, 스테이플 티켓 유효, Hardened
Runtime, Apple 타임스탬프까지 확인했습니다. 걱정하던 것 - presigned URL 수명, 잡
폴링의 네트워크 지연, 결과 업로드 경로 - 은 전부 지나갔습니다.

CLI 는 배포 토큰으로 인증합니다. 토큰이 앱 하나에 묶여 있어서 앱 ID 를 넘길 필요가

**프로필 발급은 남겼습니다.** API 호출 자체보다 "발급한 프로필을 누구에게 어떻게
전달하는가"가 문제입니다. 프로필은 서명 **이전에** 번들 안에 들어가야 하므로
(설계 문서 §3) 워커가 아니라 앱을 빌드하는 개발자에게 가야 합니다. 그 흐름을 정하는
것이 API 연동보다 큰 일이라 실제로 필요한 앱이 나올 때 정합니다.

**App Store Connect 연동은 실제 키로 확인하지 못했습니다.** JWT 조립과 응답 해석,
만료 판단은 테스트로 확인했지만, Apple 이 그 토큰을 받아주는지는 키가 있어야 압니다.

## Phase 3. 별점 + 피드백 + 알림 (1\~2주) - 완료

- [x] 별점(1\~5, 버전별), 피드백(텍스트 + 스크린샷 첨부, [ADR-0016](adr/0016-server-handles-small-uploads.md))
- [x] 스토어 앱/웹에 별점·리뷰 UI
- [x] 알림 채널 추상화 + Slack Incoming Webhook, 앱별 알림 대상 설정
- [x] 신규 피드백·별점 등록 시 앱 오너에게 발송
- [x] 워커 하트비트 끊김 알림

**SMTP 는 넣지 않았습니다.** Swift 에 표준 클라이언트가 없어 의존성을 하나 더 지거나
직접 구현해야 하는데, 사내에서 Slack 을 쓰면 아무도 메일을 안 봅니다. 채널은 타입으로
추상화해두었으므로 필요해지면 `NotificationChannel` 을 따르는 타입 하나가 늡니다.

피드백은 **받아본 버전에만** 남길 수 있습니다. 다운로드 이력을 조건으로 씁니다.
익명은 화면에서만 익명이고 서버는 누가 남겼는지 계속 압니다. 본인이 고치고 지울 수
있어야 하고, 악용이 생기면 추적할 수 있어야 하기 때문입니다.

**익명 허용 여부는 관리자 화면에서 켜고 끕니다.** 조직마다 답이 다릅니다. 끄면
이름을 감춘 요청이 거절되고 화면에서 체크박스가 사라집니다. 조용히 실명으로 바꾸지
않습니다. 익명인 줄 알고 쓴 글에 이름이 붙는 것이 이 기능에서 가장 나쁜 실패입니다.
**이미 익명으로 남긴 글은 설정을 꺼도 익명으로 남습니다.** 남길 때의 약속을 나중에
뒤집으면 그 사람이 쓴 것이 다른 뜻이 됩니다.

스토어 앱은 지금 깔려 있는 버전이 최신 출시본과 같을 때만 폼을 띄웁니다. 앱이 아는
것이 "설치된 버전"뿐이라서입니다. 예전 버전에 남기려면 웹 콘솔을 씁니다.

## Phase 4. 마무리 (1\~2주) - 완료

- [x] Sparkle appcast 엔드포인트 + 앱별 피드 토큰
      ([ADR-0017](adr/0017-sparkle-feed-tokens.md))
- [x] 스토어 앱 자동 업데이트 (Sparkle 없이 자체 구현)
- [x] 관리 대상 앱 백그라운드 업데이트 확인
- [x] 다운로드 통계 대시보드
- [x] 공개 준비: LICENSE(MIT), 셀프호스팅 가이드, 시크릿 스캔, deny list

**스토어 앱에는 Sparkle 을 넣지 않았습니다.** 다른 앱들이 쓸 appcast 는 서버가
그대로 내주지만, 스토어 앱 자신은 이미 앱을 받아 검증하고 설치하는 코드를 갖고
있어서 프레임워크를 하나 더 얹을 이유가 없습니다. 실행 중인 자기를 갈아끼우는 것은
셸 스크립트 하나로 처리합니다.

**통계는 "설치"가 아니라 "다운로드"입니다.** 서버가 아는 것은 누군가 파일을
받아갔다는 사실까지입니다. 설치 완료를 알려면 스토어 앱이 따로 보고해야 하는데,
그렇게까지 해서 알게 되는 것이 많지 않다고 봤습니다.

## 운영 개선. 서명 실패 오류 코드 - 완료

- [x] `SigningFailureCode` 와 안내 문구를 `AlleyShared` 에 두고 워커가 오류 타입에서
      갈래를 뽑는다
- [x] `signing_jobs.failure_code` 열 추가 (마이그레이션 신규)
- [x] 재시도 판단을 `SigningRetryPolicy` 한 곳으로 모으고 보고된 실패와 멈춘 잡이

- [x] 잡 로그를 덮어쓰지 않고 쌓는다 (상한 16KB, 넘으면 앞을 버린다)
- [x] 관리 > 서명 워커와 앱 상세에 안내 문구와 코드를 함께 보여준다

([ADR-0023](adr/0023-signing-failure-codes.md))

**동작이 하나 바뀝니다.** 지금까지 워커가 보고한 실패는 무조건 버전을 `failed` 로
확정했습니다. 이제 네트워크·스토리지·공증 서비스·타임아웃은 잡을 큐로 되돌립니다.
그 외에는 시도 횟수를 쓰지 않고 곧장 실패로 확정합니다.

**분류하지 못한 실패는 다시 시도하지 않습니다.** 잘못된 재시도가 같은 버전을 공증에
두 번 올리기 때문이고, 자동으로 넘어가면 갈래를 늘려야 한다는 신호가 묻히기
때문입니다. `unknown` 이 자주 들어온다면 갈래를 하나 더 만들 때입니다.

## 운영 개선. 배포 전 보안 점검 반영 - 완료

사내 Kubernetes 샌드박스에 처음 올리기 전 플랫폼이 요구한 보안 점검에서 셋이
나왔습니다.

- [x] 피드 토큰을 질의 항목에서 경로 세그먼트로 옮기고, 옛 형식은 `Deprecation`
      헤더와 로그를 붙여 당분간 함께 받는다 ([ADR-0025](adr/0025-feed-token-in-path.md))
- [x] 보안 헤더 미들웨어를 스택 가장 바깥에 둔다. CSP 는 템플릿을 읽고 맞춘다
      ([ADR-0026](adr/0026-security-headers.md))
- [x] `PUBLIC_BASE_URL` 스킴과 `JWT_SECRET` 길이를 기동 시점에 검사하고, 어긋나면
      뜨지 않는다 ([ADR-0027](adr/0027-fail-fast-on-unsafe-config.md))

**셋 중 첫째는 문제를 없애지 못합니다.** 그 플랫폼의 액세스 로거는 경로와
쿼리스트링을 한 필드에 함께 적습니다. 토큰을 경로로 옮겨도 로그에서 사라지지
않습니다. 그 환경에서 실제로 기대는 것은 토큰이 읽기 전용이고 앱 하나에 묶여 있다는
것, 폐기가 즉시 반영된다는 것, 그리고 로그를 읽을 수 있는 사람을 좁게 두는 것입니다.
자세한 것은 ADR-0025 의 "나쁜 점" 에 적었습니다.

**동작이 둘 바뀝니다.** `JWT_SECRET` 이 32 바이트보다 짧으면 서버가 뜨지 않습니다.
`PUBLIC_BASE_URL` 이 loopback 이 아닌 http 여도 뜨지 않습니다. 기존 배포를 올릴 때
여기서 걸릴 수 있고, `JWT_SECRET` 을 바꾸면 이미 로그인한 사람이 전부 다시
로그인해야 합니다.

## 워커 자동 업데이트 - 완료 ([ADR-0042](adr/0042-worker-self-update.md))

- [x] 워커가 새 번들이 나왔는지 확인하고 받아온다
- [x] 잡을 잡고 있지 않을 때만 자기를 갈아끼운다 (잡을 **받기 전에** 본다)
- [x] 못 뜨는 빌드는 자리를 바꾸기 전에 걸러낸다 (`preflight` 로 한 번 띄워본다)
- [x] 번들 버전과 코드의 버전을 한 곳에서 관리한다 (`WorkerVersion.current`)
- [x] 워커 릴리스는 관리자가 관리자 화면에서 올린다. 그 행위가 승인이다
- [x] 워커가 하트비트에 자기 버전을 알리고, 낡으면 관리자 화면에 드러난다

워커를 고쳐도 사람이 각 맥에 가서 다시 설치해야 합니다. 워커 버그는 그 워커가 서명한
모든 앱의 배포 품질을 망치는데 고친 것을 퍼뜨릴 길이 없습니다
([ADR-0022](adr/0022-worker-as-signed-app-bundle.md)의 후속 과제).

**유휴일 때만 갈아끼웁니다.** 서명이나 공증 도중에 프로세스가 바뀌면 그 잡은 중간에
끊깁니다. 공증은 Apple 응답을 기다리는 구간이 길어서 그럴 확률이 낮지 않습니다.

**뜬 뒤 일정 시간 안에 하트비트를 못 보내면 스스로 이전 버전으로 되돌립니다.**
갈아끼운 워커가 뜨지 못하면 되돌릴 사람이 그 맥에 직접 가야 하는데, 그 맥은 원래
사람이 잘 가지 않는 머신입니다. 되돌릴 자리는 이미 있습니다. 설치 경로가 고정된
번들이라 이전 것을 옆에 두면 됩니다.

**사람이 확인하는 지점이 필요합니다.** 새 워커 번들을 서명하는 것이 지금 돌고 있는
워커입니다. 워커가 자기 다음 버전을 서명하고 그것으로 자기를 갈아끼우는 순환이
생깁니다. 잘못된 빌드가 나가면 그것을 되돌릴 워커도 그 빌드입니다. 승인을 어디에 둘지는
릴리스를 누가 만드는지와 함께 정합니다.

## 스토어 앱을 받는 공개 페이지 - 완료 ([ADR-0049](adr/0049-public-store-app-download-page.md))

- [x] `/get` 을 로그인 없이 연다. 출시된 스토어 앱 하나만 내준다
- [x] 받아간 사실을 남긴다. 세션이 있으면 그 사람으로, 없으면 익명으로
      (`downloads.user_id` 에서 `NOT NULL` 을 뗀다)
- [x] 스토어 앱이 없거나 아직 출시 전이면 화면은 열되 받기 링크를 그리지 않는다
- [x] 목록(`/apps`) 안내 줄에 올리는 사람이 다른 사람에게 알려줄 공개 주소를 적는다
- [x] 로그인 화면에 "앱을 받으러 오셨다면 여기" 를 둔다

받을 수 있는 자리가 콘솔 목록 맨 위 한 줄뿐이었습니다. 그 화면은 앱을 **올리는**
사람이 보는 곳인데, 스토어 앱이 필요한 사람은 **받는** 사람입니다. 사내 문서에 적을
주소가 없었습니다.

**로그인을 요구하면 순서가 막힙니다.** 세션을 만들어봐야 이 사람이 하려는 일은 앱을
받는 것 하나이고, 로그인해서 도착하는 곳은 개발자용 화면입니다.

**받아도 아무것도 볼 수 없습니다.** 앱은 빌드할 때 박힌 자기 서버에 붙고
([ADR-0044](adr/0044-store-app-knows-its-server.md)), 목록을 받으려면 조직 계정으로
로그인해야 합니다. 새로 열리는 것은 서명·공증된 바이너리 하나뿐입니다.

**"몇 명이 받았나" 가 부정확해집니다.** 익명 줄은 사람 수에 안 들어갑니다. 횟수는
맞습니다. 그 둘을 나란히 두는 통계 화면에서 어긋나 보일 수 있습니다.

## 스토어 앱을 dmg 로도 내보내기 - 완료 ([ADR-0050](adr/0050-store-app-ships-as-a-disk-image.md))

- [x] 서명 잡에 "dmg 도 만들어라" 를 싣는다. 서버가 스토어 앱 빌드에만 켠다
- [x] 워커가 `.app` 과 `/Applications` 별칭을 넣어 dmg 를 만들고, 껍데기도 서명·공증·스테이플한다
- [x] zip 을 먼저 올린다. dmg 를 만들다 실패해도 배포는 된다
- [x] 공개 페이지가 dmg 를 먼저 내주고, 없으면 서명된 zip 으로 물러선다
- [x] dmg 를 모르는 예전 워커가 끝낸 잡도 그대로 성공한다

zip 은 받은 사람에게 풀고 옮기는 일을 시킵니다. 안 옮기고 내려받기 폴더에서 그냥
실행하는 사람이 반드시 나오고, 그러면 폴더를 비울 때 앱이 사라지거나 자기 업데이트가
거기 있는 자기를 갈아끼웁니다.

**스토어 앱에만 있는 문제입니다.** 다른 앱은 스토어 앱이 받아서 `/Applications` 에
직접 넣습니다. 사람이 손으로 옮기는 것은 스토어 앱 자신뿐이고, 그때는 옮겨줄 스토어
앱이 아직 없습니다.

**워커는 여전히 앱의 정체를 모릅니다.** "이 잡은 스토어 앱이다" 가 아니라 "dmg 도
만들어라" 를 보냅니다. 정체를 알리면 그 조건문이 워커 안에서 자랍니다 (ADR-0046 이
일부러 만든 성질).

**공증이 한 번 더 돕니다.** `.app` 한 번, dmg 한 번입니다. 스토어 앱 릴리스 시간이
그만큼 늘어납니다.

## MVP 수용 기준

Phase 1을 완료로 판정하는 조건 일곱 가지입니다. 그중 **3, 4, 7 은 실제 인증서와 OAuth
클라이언트가 갖춰진 뒤에야 확인할 수 있습니다.** 나머지는 코드와 테스트로
확인했습니다.

1. `docker compose up`만으로 로컬에서 서버·DB·스토리지가 뜨고 브라우저에서
   로그인까지 동작한다
2. 허용 도메인 밖의 계정은 로그인이 서버 단에서 거부된다
3. developer가 미서명 빌드를 올리면 워커가 자동으로 서명·공증·스테이플을 수행하고
   상태가 `ready`가 된다
4. released 버전을 스토어 앱에서 로그인 후 다운로드하면 Gatekeeper 경고 없이
   실행된다
5. 다운로드 이력에 사용자·버전·시각이 기록된다
6. 코드에 조직 고유 명사가 검색되지 않는다 (CI deny list 통과)
7. 스토어 앱은 서버 주소만 입력하면 다른 조직 서버에도 그대로 붙는다

## 검증 방법

- **단위 테스트**: 상태 머신 전이, 번들 ID 검증, 설정 로딩, 권한 미들웨어,
  OAuth 도메인 검증
- **통합 테스트**: docker-compose 기반 API 시나리오
  (등록 → 업로드 → 잡 생성 → 상태 전이)
- **E2E**: 파일럿 앱 1개로 실제 서명·공증·다운로드·Gatekeeper 통과 확인
- **보안 점검**: 워커 토큰 없는 잡 API 접근 거부, 비로그인 다운로드 거부,
  presigned URL 만료 확인, 메타 응답에 비밀값 미포함

| 마이그레이션 실행 시점 | **기본은 사람이 `migrate` 를 돌립니다.** 그 명령을 실행할 수단이 없는 플랫폼을 위해 `MIGRATE_ON_BOOT` 를 열었습니다. 켜면 기동하면서 돌고, 여러 대가 동시에 도는 문제는 Postgres advisory lock 으로 막습니다 ([ADR-0028](adr/0028-migrate-on-boot-with-advisory-lock.md)) |

## 열려 있는 결정

착수 전에 정해야 하는 것들입니다.

| 항목 | 정해야 할 시점 | 내용 |
| --- | --- | --- |
| 재개 가능 업로드 | 실패가 잦아지면 | MVP는 단순 재시도로 간다. 대용량에서 실패가 잦으면 멀티파트로 확장한다 ([ADR-0009](adr/0009-presigned-artifact-transfer.md)) |
| 웹 콘솔 SPA 전환 | 통계·피드백 화면이 복잡해지면 | Leaf 서버 렌더링으로 시작한다. 통계·피드백 대시보드가 복잡해지면 재검토한다. 사내용 고급 화면이 먼저 필요해지면 같은 API 에 붙는 별도 프론트엔드를 다른 레포에서 만든다 |
| 설치 완료 보고 | 통계가 부족해지면 | 지금 통계는 "받아갔다"까지다. 스토어 앱이 설치 성공을 따로 보고하면 설치 수를 셀 수 있지만, 그 값이 큰지 아직 모른다 |
| 앱 단위 기본 entitlements | 같은 파일을 매번 첨부하는 것이 번거로워지면 | 지금은 버전마다 함께 올린다. 앱에 기본값을 두면 편하지만 바이너리와 권한이 따로 놀 수 있다 ([ADR-0020](adr/0020-uploader-provides-entitlements.md)) |
| 서버 이미지 멀티아키텍처 | arm 호스트에 올려야 할 때 | 지금은 linux/amd64 만 발행한다. QEMU 크로스빌드는 Swift 빌드에서 값이 너무 크고, 네이티브 arm 러너는 공개 레포에서만 무료다. 필요해지면 러너 매트릭스로 붙인다 ([ADR-0021](adr/0021-publish-server-container-image.md)) |
| 이미지 보관 정책 | 저장 용량이 문제가 될 때 | 커밋마다 sha 태그가 쌓이는데 지우는 규칙이 없다 ([ADR-0021](adr/0021-publish-server-container-image.md)) |
| 워커 설치 시 Team ID 확인 | 워커를 여러 조직이 쓰게 되면 | 설치 스크립트가 번들의 서명은 확인하지만 어느 팀이 서명했는지는 보지 않는다. 확인하려면 조직마다 다른 Team ID 를 환경변수로 받아야 하고, 안 넣은 사람에게는 아무 보호가 없다 ([ADR-0022](adr/0022-worker-as-signed-app-bundle.md)) |
| Electron 밖의 JIT 런타임 검사 | 그런 앱이 실제로 깨지면 | 지금 검사는 Electron Framework 하나만 본다. JVM·Mono 는 잡지 못한다. 일반화하려면 번들 안의 바이너리가 무엇을 링크했는지 봐야 한다 |
| 옛 피드 주소(`?token=`)를 언제 없앨지 | 옛 형식 요청이 그친 뒤 | 이미 배포된 앱의 `SUFeedURL` 에 옛 형식이 박혀 있을 수 있어 지금은 함께 받는다. 판단 근거는 `폐기 예정인 질의 형식 피드 주소 사용` 로그다. 날짜를 먼저 박으면 그날 무엇이 깨지는지 모르는 채로 지우게 된다 ([ADR-0025](adr/0025-feed-token-in-path.md)) |
| CSP 위반 보고 수집 | 화면이 CSP 로 깨지는 일이 잦아지면 | 지금은 위반이 브라우저 콘솔에만 남아 서버가 알지 못한다. `report-to` 를 붙이려면 보고를 받을 자리를 먼저 만들어야 한다 ([ADR-0026](adr/0026-security-headers.md)) |
| 주기적 훑기를 한 인스턴스만 돌게 잠글지 | 서버를 실제로 여러 대로 늘릴 때 | 잠금 장치는 부팅 시 마이그레이션에 쓰려고 이미 만들었다(`AdvisoryLock`). 훑기를 감싸는 것만 남았는데, 한 대인 지금은 걸릴 일이 없어 미뤄뒀다 ([ADR-0018](adr/0018-stalled-signing-job-recovery.md), [ADR-0028](adr/0028-migrate-on-boot-with-advisory-lock.md)) |
