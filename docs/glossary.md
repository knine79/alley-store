# 용어집

이 레포의 코드와 문서에 나오는 서버 쪽 용어를 모았습니다. iOS/macOS는 익숙한데
서버는 처음인 사람을 위한 것입니다.

교과서적 정의가 아니라 **Alley에서 이것이 무엇을 하는가**를 적습니다. 그래야
코드가 바뀔 때 같이 고칠 이유가 생기고, 문서가 덜 낡습니다.

macOS 코드 서명 용어(Developer ID, 공증, staple, entitlement)는 여기가 아니라
[설계 문서 2장](design.md)에 있습니다. 그쪽은 배경 설명이 길어야 해서입니다.

---

## 저장소

### 오브젝트 스토리지 (object storage)

HTTP API가 달린 파일 저장소. 파일 하나를 "오브젝트"라 부르고
`apps/앱ID/versions/버전ID/signed.zip` 같은 **키**로 식별합니다. 슬래시가 들어가
디렉터리처럼 보이지만 실제로는 그냥 이름입니다.

Alley는 앱 바이너리(zip)를 여기 둡니다. 서버 디스크에 두지 않는 이유는 서버를
재배포하면 날아가고, 서버를 늘리면 서로 못 보고, 무엇보다 클라이언트가 직접
받아갈 방법이 없기 때문입니다.

### 버킷 (bucket)

오브젝트가 사는 네임스페이스. Alley는 버킷 하나(`S3_BUCKET`)를 씁니다.

### S3 호환

AWS S3의 HTTP API를 흉내내는 것. S3 API가 사실상 표준이 되면서 여러 구현이
이걸 따릅니다. Alley 코드는 S3 API 하나만 알고, 어디에 붙을지는 `S3_ENDPOINT`
설정으로 정해집니다. 비우면 AWS S3, 채우면 그 주소.

이것이 [ADR-0004](adr/0004-docker-selfhosting-s3-abstraction.md)의
"특정 클라우드에 묶이지 않는다"가 지켜지는 방식입니다.

### MinIO

직접 설치해서 쓰는 S3 호환 오브젝트 스토리지. `docker-compose.yml`에 들어 있고,
로컬 개발과 셀프호스팅 양쪽에서 씁니다.

- **9000**: S3 API. 서버와 클라이언트가 붙는 곳
- **9001**: 웹 콘솔. 브라우저로 파일을 눈으로 확인
- **`mc`**: MinIO CLI. `minio-setup` 컨테이너가 이걸로 버킷을 한 번 만들고 끝납니다

MinIO는 **path style만** 씁니다(아래 참조). 그래서 `.env`의
`S3_USE_PATH_STYLE=true`가 필요합니다.

### path style / 가상 호스트

오브젝트 주소를 만드는 두 가지 형태입니다.

```
가상 호스트:  https://버킷.s3.리전.amazonaws.com/키    (AWS 기본)
path style:  http://minio:9000/버킷/키                (MinIO)
```

presigned URL의 서명은 URL 전체에 대해 계산되므로, **형태를 틀리면 서명은 맞는데
엉뚱한 곳을 가리키는 URL**이 나갑니다. `ArtifactStorage.objectBase`가 이 조립을
담당하고, 테스트가 붙어 있습니다.

### presigned URL

"이 파일 하나에 / 이 메서드로 / 이 시각까지만" 을 허용하는 서명된 URL입니다.

서버가 스토리지 시크릿으로 HMAC 서명을 만들어 쿼리 스트링에 붙입니다.
클라이언트는 그 URL로 스토리지에 **직접** 붙고, **스토리지가 스스로 서명을
검증합니다.** 우리 서버에 물어보지 않습니다.

핵심은 **URL 자체가 자격증명**이라는 것입니다. 다만 범위가 파일 하나 + 메서드
하나 + 시한으로 좁혀져 있고, 시크릿은 서버 밖으로 나가지 않습니다.

CloudKit에서 `CKAsset`을 받는 방식과 같은 구조입니다. 레코드 응답에 바이트가
실려 오는 게 아니라 스토리지를 가리키는 URL이 옵니다.

왜 이렇게 했는지는 [ADR-0009](adr/0009-presigned-artifact-transfer.md)에 있습니다.

### `HEAD` 요청

본문 없이 메타데이터만 받는 HTTP 메서드. Alley는 업로드 완료 통지를 받았을 때
스토리지에 `HEAD`를 던져 **파일이 진짜 있는지, 몇 바이트인지** 확인합니다.

클라이언트가 "다 올렸다"고 말하는 것만 믿으면 빈 버전이 출시될 수 있습니다.

## 데이터베이스

### PostgreSQL

서버로 도는 오픈소스 관계형 데이터베이스. **SQLite의 서버 버전**이라고 보면
대체로 맞습니다. 같은 SQL을 씁니다.

| | SQLite | PostgreSQL |
| --- | --- | --- |
| 형태 | 앱에 링크되는 라이브러리 | 별도로 도는 서버 프로세스 |
| 접근 | 파일을 직접 연다 | 네트워크 접속 (5432) |
| 동시 쓰기 | 사실상 한 번에 하나 | 수백 커넥션이 동시에 |

Alley에서는 **"무엇이 어디 있고 어떤 상태인가"** 를 담당합니다. 실제 파일은
오브젝트 스토리지에 있고, DB에는 그 주소와 크기와 해시만 있습니다.

### 유니크 제약 (unique constraint)

같은 값이 두 행에 들어가지 못하게 DB가 막는 것.

Alley에서 번들 ID와 (앱, 빌드 번호) 조합에 걸려 있습니다. **코드로는 못 막기
때문에** 필요합니다. "이미 있나?" 조회하고 없으면 저장하는 코드는 조회와 저장
사이에 다른 요청이 끼어들면 뚫립니다. DB 제약이 최종 방어선입니다.

### 외래키 (foreign key)

존재하지 않는 것을 가리키지 못하게 하는 제약. 삭제 정책이 함께 붙습니다.

| 정책 | 부모가 지워지면 | Alley에서 |
| --- | --- | --- |
| `cascade` | 자식도 같이 지워짐 | 앱 → 버전 → 아티팩트, 앱 → 멤버 |
| `restrict` | **삭제 자체가 실패** | 다운로드 이력 → 버전 |

다운로드 이력에 `restrict`를 건 이유는 감사 기록이기 때문입니다. 누가 받아간
버전은 삭제가 실패하는 편이 맞습니다.

### 마이그레이션 (migration)

스키마 변경 이력을 코드로 관리하는 것. Core Data 마이그레이션과 같은 개념인데
각 단계가 Swift 코드로 명시돼 있고 순서가 보장됩니다.

```bash
swift run alley-server migrate --yes
```

적용된 목록을 DB가 직접 들고 있어서 이미 돈 것은 다시 돌지 않습니다.
`configure.swift`의 등록 순서가 곧 의존 관계입니다.

### Fluent / ORM

ORM(Object-Relational Mapping)은 언어 타입 ↔ DB 테이블을 이어주는 계층입니다.
Core Data가 `NSManagedObject` ↔ SQLite를 잇는 것과 같은 역할입니다.
Fluent는 Vapor의 ORM입니다.

```swift
try await App.query(on: db).filter(\.$bundleID == id).first()
// → SELECT * FROM apps WHERE bundle_id = $1 LIMIT 1
```

`@Field`, `@Parent`, `@Children`가 `@NSManaged`와 relationship에 해당합니다.

### store_settings 와 씨앗

관리자가 화면에서 바꾸는 설정(스토어 이름, 로고, 강조색, 허용 로그인 도메인,
번들 ID 프리픽스)은 `store_settings` 테이블의 **행 하나**에 있습니다.

행이 없으면 환경변수 값으로 한 번 만들고(**씨앗**), 그 뒤로는 데이터베이스가
진실입니다. `.env`를 고쳐도 아무 일도 일어나지 않습니다. 그러지 않으면 화면에서
바꾼 값이 재시작마다 되돌아갑니다.

비밀값과 부팅에 필요한 값은 환경변수에 남습니다. 어느 쪽이 어디 있는지와 그 이유는
[ADR-0011](adr/0011-store-settings-in-database.md)에 있습니다.

## 인증

### JWT (JSON Web Token)

서명이 붙은 JSON 덩어리. 서버가 서명했으므로 위조할 수 없고, 서버가 상태를
저장하지 않아도 내용을 믿을 수 있습니다.

Alley는 세션 토큰과 OAuth `state`에 씁니다. 세션 토큰에 무엇을 담고 무엇을 담지
않는지는 [ADR-0008](adr/0008-session-token-design.md)에 있습니다.

### Bearer 토큰

`Authorization: Bearer <토큰>` 헤더로 실어 나르는 토큰. 스토어 앱이 쓰는
방식입니다. 앱이 토큰을 키체인에 두고 요청마다 직접 붙입니다.

"bearer"는 "가진 사람"이라는 뜻입니다. 가진 사람이면 누구나 쓸 수 있다는 의미라,
유출되면 그대로 신원이 됩니다.

### 쿠키 / HttpOnly

서버가 `Set-Cookie`로 심으면 브라우저가 저장했다가 **같은 출처로 가는 모든
요청에 자동으로 붙입니다.** 코드를 한 줄도 안 씁니다.

`HttpOnly`를 붙이면 자바스크립트가 읽지 못합니다(`document.cookie`에 안 보임).
그래서 페이지에 악성 스크립트가 주입돼도(XSS) 토큰을 훔쳐갈 수 없습니다.

Alley의 웹 콘솔이 `alley_session` 쿠키를 씁니다. 서버는 쿠키와 Bearer 헤더를
둘 다 받되 **헤더를 먼저** 봅니다. 이유는
[ADR-0010](adr/0010-cookie-and-bearer-authentication.md)에 있습니다.

### CSRF / SameSite

**CSRF**(Cross-Site Request Forgery)는 공격자 사이트가 피해자의 브라우저를 시켜
피해자 권한으로 우리 서버에 요청을 보내게 하는 공격입니다. **브라우저가 쿠키를
자동으로 붙이기 때문에** 성립합니다.

공격자는 응답을 읽지 못하지만(같은 출처 정책) **요청은 실행됩니다.** 검증 안 된
버전이 전사에 출시될 수 있다는 뜻입니다.

**`SameSite=Lax`** 로 막습니다. 이 속성이 붙은 쿠키는 다른 사이트에서 시작한
POST/PATCH/DELETE 요청에 붙지 않습니다. Alley에서 상태를 바꾸는 요청은 전부 그
메서드들이라 공격이 통하지 않습니다.

방어의 실체가 쿠키 설정 한 줄뿐이라 코드에 안 보이는 것이 이 방식의 약점입니다.

### OAuth 2.0 / OIDC

**OAuth 2.0**은 "이 앱이 당신 계정으로 무언가 하도록 허락하시겠습니까"를 다루는
규격이고, **OIDC**(OpenID Connect)는 그 위에서 "이 사람이 누구인가"를 알려주는
층입니다. Google 로그인은 OIDC입니다.

Alley는 **Authorization Code flow**를 씁니다. 브라우저가 Google로 가서 동의하면
Google이 우리 서버로 `code`를 보내고, 서버가 그 `code`를 Google에 다시 보내
토큰을 받습니다. 클라이언트 시크릿이 서버 밖으로 나가지 않습니다.

### `state` 파라미터

OAuth 왕복에서 두 가지를 합니다. CSRF 방어와, 인증 후 어디로 돌려보낼지
기억하기(웹/앱). Alley는 저장소를 두지 않으려고 서명된 10분짜리 JWT에 담습니다.

### `sub` claim

OIDC ID 토큰에 들어 있는 계정의 영구 식별자. Alley는 이메일이 아니라 이걸로
사용자를 식별합니다. 이메일은 조직 안에서 바뀔 수 있지만 `sub`는 계정이 살아
있는 한 안 바뀝니다.

### JWKS

토큰 발급자가 공개하는 공개키 묶음. Google ID 토큰의 서명을 검증할 때 씁니다.

## 서버 애플리케이션

### Vapor

Swift 웹 프레임워크. HTTP 서버, 라우팅, 미들웨어, DB 연동(Fluent), 템플릿(Leaf)이
들어 있습니다. 서버를 Swift로 쓰기로 한 배경은
[ADR-0001](adr/0001-swift-fullstack-monorepo.md)에 있습니다.

### 라우트 (route)

"이 경로로 이 메서드가 오면 이 함수를 부른다"는 등록. 경로 문자열이 서버와
클라이언트에 각각 박히면 어긋나므로, Alley는 `AlleyShared/APIPath.swift`에서만
정의합니다.

### 미들웨어 (middleware)

요청이 실제 처리 함수에 닿기 전에 지나가는 층. 인증, 로깅, 오류 변환 같은
공통 처리를 여기서 합니다.

Alley의 `SessionAuthenticator`가 미들웨어입니다. 토큰을 확인하고 요청에 사용자를
붙입니다. 권한 확인은 그 다음 단계입니다.

### Leaf

Vapor의 서버 사이드 템플릿 엔진. 웹 콘솔 화면을 서버에서 HTML로 만들어 내려줄 때
씁니다(Phase 1-4).
